# 第一部分 玩法总纲

## 1.1 一句话卖点与三条支柱

> **在微缩沙盘上带兵游历；遇到强敌就切进横版一对一，靠弹反 / 闪避 / 蓄力赢下它，再把战利品带回沙盘，滚成一方势力。**

| 支柱 | 玩家实际动作 | 爽点 | 落在哪 |
|---|---|---|---|
| **战斗** | 读招 → 精确输入 → 高回报 | 弹反成功 → 0.6s 内普攻 → 反击斩；闪避保住蓄力等级；蓄力出剑气/霸体 | M2 |
| **沙盘** | 选目标、行军、追逃、补给 | 「粮草见底、被两队追、冲向最近城镇」 | M1 |
| **成长** | 战利品 → 装备 / 兵员 → 更大的地图权限 | 从流寇到势力 | M3 / M4 / M5 |

三条支柱缺一条，游戏就变成另一种东西：缺战斗=纯走路模拟；缺沙盘=格斗试玩；缺成长=一遍就弃。

## 1.2 三层循环（时间尺度）

| 层 | 单次时长 | 玩家在做什么 | 张力来自 | 反馈 |
|---|---|---|---|---|
| **战斗循环** | 10–90 秒 | 观察起手、弹反或闪避、蓄力、处决 | 判定窗口只有 2–12 帧 | 顿帧、火花、反击斩、掉落 |
| **战役循环** | 15–40 分钟 | 选目标 → 行军 → 遭遇 → 战斗/谈判/逃 → 补给/升级 → 再选 | **粮草与时间一直在流逝** | 资源、声望、新选项 |
| **通关循环** | 10–20 小时 | 选边、讨伐 Boss、控区、扩军 | 势力格局随你的选择变化 | 新区域、新兵种、结局 |

三层必须**咬合**：战斗的产出（战利品）是战役的燃料；战役的推进（时间）决定战斗的难度；
通关的格局（势力）决定你在战役里能去哪。任何一层单独成立都不够。

## 1.3 资源与风险回路

| 资源 | 归属 | 产出 | 消耗 | 见底后果 |
|---|---|---|---|---|
| 钱 | 全局 | 战利品、任务、交易 | 招募、装备、贿赂 | 无法扩军、无法买补给 |
| 粮草 | 按队伍 | 补给点、战利品 | 每日按人数消耗 | 士气↓、速度↓、遭遇战更弱 |
| 补给 | 按队伍 | 城镇/村庄补给 | 战斗后恢复、行军消耗 | 无法恢复兵力 |
| 兵员 | 按队伍 | 招募、任务奖励 | 战斗损失 | 队伍变弱，可被 AI 追吃 |
| 声望 | 按势力 | 任务、战斗、选择 | 敌对行为、失约 | 被通缉、失去交易权限 |

**主回路（压力）**：粮草↓ → 必须回城 → 回城耗时 → 时间推移 → 敌人变强 / 任务超时 → 更缺资源。
**反回路（成长）**：打赢 → 战利品 → 补给/装备 → 更强 → 敢打更难的。

**设计红线**：不允许存在「零风险无限刷资源」的循环。每个收益点都必须挂一个代价（时间 / 风险 / 声望）。
这条比任何数值都重要 —— 它是沙盘能不能撑住 10 小时的根。

## 1.4 决策点密度（玩法密度的验收口径）

目标：**平均每分钟 ≥ 1 个有意义决策**。计入的只有这五类：
走哪条路 / 打还是谈还是逃 / 在哪补给 / 接哪个任务 / 强化哪件装备。

- 不计入：看动画、等行军、翻菜单。
- 验收：`D-` 试玩时由你主观判断，并记录一条「这次 30 分钟里我做了哪几个真正的选择」。
- 若密度不足，优先加**时间压力**（粮草更快耗尽 / 敌人更主动），而不是加系统。

## 1.5 成长与解锁节奏

| 已游玩时长 | 新出现的东西 | 玩家获得的能力 | 教学负担 |
|---|---|---|---|
| 0–30 分钟 | 移动、1 场遭遇战、补给 | 会走、会打、会补给 | 全部靠引导（S6.2） |
| 30 分钟–2 小时 | 任务、交易、追逃 | 会规划路线、会算钱 | 轻 |
| 2–6 小时 | 首个 Boss、装备强化、招募 | 会配装、会带兵 | 中 |
| 6–12 小时 | 势力战、军团战、第二/三 Boss | 会指挥、会选边 | 重（需引导） |
| 12–20 小时 | 终局、结局 | —— | —— |

**节奏红线**：前 30 分钟必须经历一次「打赢一场硬仗 + 带回战利品」。这是留存的分水岭。

## 1.6 失败、惩罚与「不死档」

| 情形 | 后果 | 不允许 |
|---|---|---|
| 普通战斗失败 | 被俘：损失部分金钱与兵员，被释放到最近聚落，游戏时间推进 | 删档、卡死、必须读档才能继续 |
| Boss 战失败 | 可重试；世界时间推进、Boss 恢复 | 用「读档」当唯一解法 |
| 粮草归零 | 士气与速度下降，可继续玩（不是即死） | 直接判负 |
| 任务失败 | 声望下降、失去奖励，任务进入 failed | 任务永久卡在 tracking |

「读档」是玩家的**选择**，不是**必需**。这条决定了游戏是否"耐玩"。

## 1.7 遭遇的三选一（每个选项都有代价）

| 选择 | 代价 | 收益 | 影响 |
|---|---|---|---|
| 交战 | 兵员损失、时间 | 战利品、声望 | 切战斗场景（M1 先占位结算） |
| 谈判 | 钱或物资 | 避免损失、可能结盟 | 势力 relation 变化 |
| 逃离 | 速度判定失败则被迫交战且士气↓ | 保全部队 | 追击方获得一次免费攻击窗口 |

## 1.8 M1（还没有战斗）阶段，玩家图什么

这是 M1 出口评审最容易被含糊过去的一环，必须先说清：

- **M1 的乐趣不是"打"，而是"探索 + 时间压力 + 追逃"。**
- 因此 **S1.6（AI 追击）与 S1.7（粮草）必须早于 S1.8（任务）打磨到位** —— 顺序写进 §2.5 关键路径。
- M1 出口的具体问题（写进 `D-` 记录）：
  > 「你是否有过一次『粮草见底、被两队追、冲向最近城镇』的经历？」
  有 ⇒ 循环成立；没有 ⇒ 先加压力，别急着加任务。

## 1.9 两套战斗如何并存（Boss 战 vs 军团战）

| 维度 | Boss 战（M2） | 军团战（M4） |
|---|---|---|
| 规模 | 1v1 | 3–6 小队 × 10–20 人（60–120） |
| 视角 | 横版正交侧视 | 上帝视角 |
| 爽点 | 精密操作、读招、反击 | 指挥、阵型、士气崩溃 |
| 共性 | 同一套角色成长（Q6 默认共用）、同一套装备 | 同上 |
| 缝合点 | **S4.7 亲自上阵**：军团战中切单挑，用 M2 的内核打 | 同一处 |

**铁律**：两套战斗共享内核与成长，不各做一套数值。否则 M3 的装备要写两遍、M5 的兵种要接两次。

# 第二部分 功能排期

## 2.1 排期原则

1. **每 2 周一个可运行构建**：能玩、能截图、`verify --all` 全绿。不可运行的中间态只允许留在本地提交。
2. **每个里程碑出口 = `D-` 人工试玩 + 全套 `A-/B-/C-`**；`D-` 不通过不算完成。
3. **先验证最大的未知**：本项目的两大未知是「手感」（M2）与「规模性能」（M4）。离这两件事越远，返工越贵。
4. **宁可薄而通，不要厚而断**：一个能走通全程的窄切片，比做厚了三分之一的某一段有价值。

## 2.2 三条路线（选一条）

| 路线 | 顺序 | 第一次"能给人玩" | 总工期 | 优点 / 代价 |
|---|---|---|---|---|
| **A 竖切片优先（推荐）** | M1 精简 → M2 内核 → 回补 M1 完整 → M2 完整 → M3/M4 → M5 → M6 | **约 25 人日（5 周）** | 约 155 人日 | 5 周就能判断"手感行不行、沙盘闷不闷"；代价是 M1 要回访一次 |
| B 按里程碑顺序 | M1 完整 → M2 → …（ROADMAP 现方案） | 约 33 人日（7 周） | 约 155 人日 | 流程最直；代价是两个月后才知道卖点成不成立 |
| C 战斗优先 | M2 内核 → M1 → … | 约 15 人日（3 周） | 约 155 人日 | 最快看到战斗；代价是 demo 像"格斗试玩"，沙盘缺席 |

**默认走 A**。理由：A 与 B 的总工期相同（都 155 人日），但 A 把「最大的两个未知」提前了 4 个月暴露；
如果手感不成立，A 只浪费 25 人日，B 会浪费 70+。
**改路线属范围变更，需你批准（ROADMAP §0.5）。**

## 2.3 人日估算与时间线

前提：单人 + AI、Windows 桌面、不含美术外包、含每步验收与文档。**误差 ±30%**。

| 阶段 | 内容 | 人日 | 累计 | 周（5 人日/周） |
|---|---|---|---|---|
| M0 收尾 | S0.4 批次 3（`F5`/`F9` + 菜单调试入口）+ S0.5 文档 | 4 | 4 | 1 |
| S1.0 | 场景与路由迁移（§4.5） | 2 | 6 | 1.2 |
| M1 | S1.1–S1.10 世界数据/地图/移动/时间/聚落/遭遇/经济/任务/存档/打磨 | 31 | 37 | 7.4 |
| M2 | S2.1–S2.11 横版内核、弹反/闪避/蓄力、Boss AI、表现、标定 | 40 | 77 | 15.4 |
| M3 | S3.1–S3.6 装备、属性管线、背包、绑定、强化、存档 | 14 | 91 | 18.2 |
| M4 | S4.1–S4.9 军团战场、单位架构、阵型、指挥、结算 | 30 | 121 | 24.2 |
| M5 | S5.1–S5.6 兵种树、招募、升级、编成、联动 | 14 | 135 | 27 |
| M6 | S6.1–S6.6 串联、引导、设置、回归、量产、导出 | 20 | 155 | 31 |

**结论：约 155 人日 ≈ 31 周 ≈ 7.5 个月**（加 10% 缓冲 ≈ 34 周）。V0 竖切片在第 5 周可玩。

分解可信度说明：M2 的 40 人日里含 **4 人日手感标定（至少 3 轮迭代）** —— 这部分历来被低估；
M4 的 30 人日里含 **5 人日单位渲染架构** —— 描边性能是 R3 高危项，先花 2 人日做 60 单位探针再决定。

## 2.4 V0 竖切片定义（约 25 人日 / 5 周）

| 项 | 范围 | 明确不在 V0 |

## 2.6 超预算时的砍功能顺序

按「砍了最不伤内核」排序，从下往上砍：

| 顺序 | 砍什么 | 砍完变成 | 影响 |
|---|---|---|---|
| 1 | M5 兵团升级 → 只留 2 条兵种线 | 兵种少但完整 | 内容量，不减体验 |
| 2 | M3 装备 → 只留 6 件 + 3 词条 | 配装深度变浅 | 战斗搭配变少 |
| 3 | M4 军团战 120 → 60 单位（或整块推迟） | 规模减半 | 卖点之一变弱，需你批准 |
| ✗ | **M2 三件套（弹反/闪避/蓄力）** | —— | 砍了就不是这款游戏 |
| ✗ | **M1 的粮草与追逃** | —— | 砍了沙盘就没有张力 |
| ✗ | **存档完整性与 9 槽** | —— | 砍了等于不可发售 |

**判据**：砍「量」可以，砍「是什么」不可以。

## 2.7 排期风险与缓冲

| 风险 | 触发信号 | 缓冲动作 |
|---|---|---|
| 手感标定失控（R1） | S2.11 两轮迭代后仍「不好玩」 | 停下来改设计，别加内容；预留 4 人日 |

| 范围膨胀（R6） | 里程碑出口评审时「还想加」 | 记录到 §5.2，不加进当前里程碑 |

# 第三部分 可扩张 / 可修改

> 用户明确要求：**默认细节可以先用，但必须写成"以后能改"的状态**。
> 这一部分就是"能改"的落地机制 —— 它不是代码风格问题，而是"改一个数要不要重编译、会不会静默改坏"。

## 3.1 六条参数外置规则

| id | 规则 | 反例（禁止） | 正例 |
|---|---|---|---|
| E-1 | 代码里只允许**结构常量**（60Hz、8 方向、9 槽），**一切玩法数值进 `data/**`** | `const PARRY_WINDOW := 2` 写在状态机里 | `frames/parry.json` 的 `perfect_window` |
| E-2 | 每张数据表带 `schema_version`，**加载即校验**，越界/缺字段报「文件名 + 行号」 | 表里少一个字段，运行到一半才崩 | 启动时 `校验失败：items.json 第 42 条缺 weight` |
| E-3 | 每个系统一个**注册表式扩张点**：加内容 = 加文件/加条目，不改内核 | 加一把武器要改 if/elif 链 | `weapons.json` 加条目 + `frames/<id>.json` |
| E-4 | 系统间**只经 §4.8 的接口缝**通信 | 战斗直接读 `WorldData.parties` | 战斗只读 `BattleContext` |
| E-5 | **可改的代价必须可见**：每张表在 §3.2 登记「默认值 / 安全区间 / 改了重跑哪个用例」 | 改完没人知道要重测什么 | 见 §3.2 |
| E-6 | 表值越界只 **clamp + 告警**，不崩 | 把遭遇半径改成 0，游戏直接除零 | `clamp(0, 0.5, 3.0)` 并存一条 warning |

## 3.2 参数登记表（改数值先查这里）

## 3.4 数据结构演进规则

1. **只加不改**：新字段必须带默认值；**改语义 = 一次 schema 迁移**，不是"顺手改"。
2. **链式迁移**：`migrations = {1: v1→v2, 2: v2→v3}`，读旧档逐级升级；用例覆盖「任意旧版 → 最新或明确拒绝」。
3. **废弃两步走**：先标 `deprecated` 并继续读，两个版本后才删。
4. **字段清单**：`GameState.FIELD_MANIFEST` / `WorldData.FIELD_MANIFEST` 与新字段同一次提交更新，否则 `s1_9_full` 失败 —— 这是"加了字段忘存档"的唯一拦截。

## 3.5 刻意**不**做成可配置的东西

可配置 ≠ 越多越好。以下必须写死，否则"可验证"就没了：

| 项 | 为什么写死 |
|---|---|
| 逻辑步 60Hz、固定步多重推进（§4.4） | 变速若按"放大 delta"实现，确定性断言全部失效 |
| 坐标轴约定（Y up / Z 纵深） | 跨系统不一致会静默错位 |
| 场景路由表的结构（`SceneRouter` 唯一入口） | 多入口 = 无法追踪切场景时序 |
| 存档原子写流程（tmp + rename + 重试） | 可配 = 可关 = 可能丢档 |
| 确定性时钟语义（`t = frame/hz`） | B- 门禁的基础 |
| `B-` 判定为 sha256 逐位一致 | 阈值可调等于门禁可关 |

## 4.4 数据契约

### `WorldData`（内存态 = `Dictionary`）

```
{ schema_version, seed, params{…},
  regions:    [{ id, name_key, biome, centroid:[x,z], area, neighbors:[id] }],
  settlements:[{ id, name_key, kind:village|town|fort, region_id, faction_id, pos:[x,z], tier, market_id }],
  roads:      { nodes:[[x,z]…], edges:[{a,b,len,cost}] },
  factions:   [{ id, name_key, color_hex, relation:{id:int}, at_war_with:[id] }],
  parties:    [{ id, kind:caravan|bandit|patrol|lord, faction_id, pos, target, state, troops, cargo }],
  anchors:    [{ id, kind, pos, name_key }] }
```

- **排序即契约**：数组按 `id`（无 id 按坐标字典序）、键按字典序输出 ⇒ 同一状态两次序列化字节相同。
- **名字不入档**：只存 `name_key`，文案走 `strings.csv`（A-7）⇒ 换语言不改存档。

### `Canon`（规范化序列化，新文件 `scripts/core/canon.gd`，纯静态）

键字典序、浮点 `%.6f`、整数无小数点、`\n`、UTF-8 无 BOM。**所有**确定性比对与落盘 JSON 都走它 ——
否则"字节一致"是空话。

### 存档 = seed + diff

```
{ schema_version:2, seed, saved_at_game_time, base:{params…},
  diff:{ date, factions, settlements:{id:{faction_id}},
         parties:{id:{pos,state,target,troops,cargo}},
         economy:{id:{good:{price,stock}}}, tasks:[…], flags:[…] } }
```

预算：单槽 < 256KB、读写各 < 150ms。迁移用 `SaveSystem.migrations`（v1 现状可用），S1.9 加 v1→v2。

### `BattleContext` / `BattleResult`（S1.6 冻结）

```
BattleContext = { version:1, source:"encounter"|"quest"|"story",
  terrain:{biome,pos}, time:{game_time,day,hour}, weather:{kind,intensity},
  attacker:{party_id,faction_id,troops,hero_id,morale},
  defender:{…同上}, stake:{loot_money,captives,war_score},
  rules:{kind:"skirmish"|"boss", seed} }

BattleResult = { version:1, winner:"attacker"|"defender", rounds,
  losses:{attacker,defender}, loot:{money,food,supply}, captives, flags:[…], placeholder:bool }
```

S1.6 占位结算 `placeholder:true`；S2.10 换真实战斗时字段不变。`hero_id` 现为空串（A-6），M3 起接装备。

### 日历与时间（A-4 核心）

- 1x：1 现实秒 = 1 游戏分 ⇒ 1 游戏日 = 1440 游戏秒 = 24 现实分。12 月 × 30 日 = 360 日/年。
- 派生：`day=floor(t/86400)+1`、`hour=floor(t/3600)%24`、`month=floor((day-1)/30)%12+1`。
- **变速 = 每帧执行 N 次完整固定步**（N=0/1/2/4），不放大 delta ⇒ 1x 与 4x 走同一条浮点路径。
- **`day_length` 语义变更（必须迁移）**：现状 `GameState.DEFAULT_DAY_LENGTH = 170.0` 是"一个昼夜循环 170 秒"；
  新语义由历法决定。v1→v2：旧 `game_time`（0..170 相位）映射为 `day=1, hour=round(t/170*24)`，
  旧值留 `visual_day_length`，读档一次性提示「时间已按新历法重标定」。
- `DayNight` 只改输入来源（读 game_time 相位），不改内部曲线；`Clock` 仍负责渲染平滑。

### 经济 / 任务（字段详见 §3.2 对应表）

```
market[sid][good] = { price, stock }；price' = clamp(price + (base-price)*k + noise(rng), base*0.6, base*1.6)
task = { id, template, state:accepted|tracking|done|failed, giver, target, deadline, reward, progress }
```
状态机只许 `accepted→tracking→(done|failed)` 单向；交易守恒（`s1_7_trade` 审计）。
