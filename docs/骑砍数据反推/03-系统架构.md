# 03 · 系统架构

> 本册描述《骑马与砍杀：战团》Windows 单机版的整体架构：模块系统如何加载、脚本虚拟机如何执行、引擎与脚本的边界在哪里、运行时对象如何组织，以及反编译 `mb_warband.exe` 得到的引擎实现观测。
>
> 标签沿用 [00-导读](00-导读与证据标准.md) 的定义：**【实证】** / **【推断】** / **【未解】**。

---

## 1. 总览：三层结构

这份游戏不是"一个程序"，而是**三层的组合**：

```
┌─────────────────────────────────────────────────────────────┐
│  引擎  mb_warband.exe（C++，符号已剥离）                      │
│  · 渲染 / 物理 / 音频 / 网络 / 输入                          │
│  · 大地图与战场模拟                                          │
│  · 脚本虚拟机（读取并执行编译后的 scripts.txt）              │
│  · 内置操作（脚本语言无法实现、只能由引擎提供的原语）        │
│  · 按名字解析并调用约 49 个"钩子脚本"                        │
│  · 读取 module.ini 的 145 个配置键                          │
└───────────────────────────┬─────────────────────────────────┘
                            │ 按名字调用 ↓ ／ 按 opcode 执行 →
┌───────────────────────────┴─────────────────────────────────┐
│  模块  Modules/Native/（纯数据，随文件发布）                 │
│  · 34 个编译后的数据文件（scripts/troops/items/parties/...） │
│  · module.ini（配置）                                        │
│  · 7 个资源目录（Textures/Sounds/Music/SceneObj/...）        │
└─────────────────────────────────────────────────────────────┘
```

**这个三层划分本身就是最重要的架构结论**，因为它决定了"规则写在哪里"：

- **玩法规则几乎全部写在模块的脚本里**（610 个脚本、36,740 条操作），因此它们是**数据**，可以被 MOD 任意改写。这是战团整个 MOD 生态的技术基础。
- **引擎只提供原语**：渲染、寻路、伤害结算的底层算术、经验曲线的形状、虚拟机本身。
- **引擎通过"按名字查脚本"来反向调用模块**——这就是让 MOD 能替换 UI、价格、战斗结果的机制。

## 2. 模块系统与加载

### 2.1 目录与文件清单

安装根目录下 `Modules/` 只含一个模块：**`Native`**。其顶层内容（实测）：

| 类别 | 文件 |
|---|---|
| 配置 | `module.ini`（11,345 字节） |
| 脚本与逻辑 | `scripts.txt`（1,163,507 字节）、`triggers.txt`、`simple_triggers.txt`、`mission_templates.txt`、`menus.txt`、`presentations.txt`、`conversation.txt`、`actions.txt`、`dialog_states.txt`、`quests.txt` |
| 实体数据 | `troops.txt`、`item_kinds1.txt`、`parties.txt`、`party_templates.txt`、`factions.txt`、`skills.txt`、`scenes.txt`、`scene_props.txt`、`map_icons.txt`、`meshes.txt`、`sounds.txt`、`music.txt`、`skins.txt`、`particle_systems.txt`、`postfx.txt`、`tableau_materials.txt` |
| 文本 | `strings.txt`、`quick_strings.txt`、`info_pages.txt`、`game_variables.txt`、`variables.txt`、`variable_uses.txt`、`tag_uses.txt` |
| 地图 | `map.txt`（1,636,114 字节）、`map_icons.txt`、`main.bmp` |
| 资源目录 | `Data/`、`Textures/`、`Sounds/`、`Music/`、`SceneObj/`、`Resource/`、`languages/` |

> **`variable_uses.txt`（4,023 B）与 `tag_uses.txt`（52 B）** 值得单独注意：它们是模块系统**构建期**的产物，用来记录全局变量与操作数 tag 的使用情况。它们的存在证明这套数据文件是由模块系统的 Python 工具链**编译生成**的（流程见 §2.4）。

### 2.2 `module.ini` 是唯一入口

引擎启动时读取 `Modules/<模块名>/module.ini`，从中获得：

1. **模块身份**：`module_name = Calradia`（第 1 行 —— 注意模块目录名是 `Native`，而模块**显示名**是 `Calradia`，两者不同）。
2. **兼容性声明**：`compatible_with_warband = 1`、`compatible_multiplayer_version_no = 1170`。
3. **地图坐标范围**：`map_min_x = -180`、`map_max_x = 180`、`map_min_y = -145`、`map_max_y = 145`（第 14–17 行）。
4. **全部可调参数**（战斗、成长、经济、AI）。
5. **资源加载清单**（`load_resource = ...`，第 113–368 行）。

### 2.3 资源加载顺序即资源 ID

`load_resource` 行的**顺序**决定资源在引擎内部的编号顺序。这不是风格问题：脚本引用网格（mesh）等资源时用的是裸下标，因此**重排 `load_resource` 行会改变所有资源的编号，从而破坏全部引用**。

【实证】`load_resource` 指令共 **214 条**，位于第 **113–368** 行（该区间共 256 行，其余为注释与空行）；另有 **1 条被注释**（第 230 行 `#load_resource = costumes_a`）。列表以 `test`、`textures_face_gen`、`shaders`、`textures` 开始，以 `ccoop_extra_ui_meshes` 结束（第 368 行），**无重名资源**。

> **一个解析陷阱**：重复出现 214 次的是**键名** `load_resource` 本身，不是资源名。因此把 `module.ini` 当作字典解析会**丢掉 213 条加载指令**——必须按行收集。

### 2.4 构建流程

【推断】结合 `variable_uses.txt` / `tag_uses.txt` 的存在与 `_rea/modulesys/` 中工具链（`process_*.py`、`header_*.py`）的形态，模块数据的生成流程是：

```
header_operations.py  →  操作码表（1054 项）
module_*.py           →  人类可读的实体定义
process_*.py          →  编译
   ↓
troops.txt / scripts.txt / ...（引擎实际读取的紧凑格式）
```

**但必须强调一个关键限制**：随文件发布的那套模块系统工具链是**多人/拿破仑世代**的产物。它的 `module_scripts.py`（676,527 字节）**不含任何一个单机 Native 脚本**（本册对 9 个典型脚本名做了精确匹配，命中数全部为 0），`module_constants.py` 里也只有极少量的 `slot_troop_*`、`slot_faction_*`。因此：**单机 Native 的脚本源码并未随游戏发布，只以编译后的 `scripts.txt` 形式存在。** 这是本套文档大量使用"反编译字节码"而非"读源码"的根本原因。

## 3. 引擎识别的配置键

### 3.1 发现方法

`module.ini` 的键名是**按字面字符串**在引擎里查找的，因此这些键名必须以字面串形式存在于 `mb_warband.exe` 中。引擎的配置键字符串集中在 `0x8155e0 .. 0x8168f8` 这一段连续区域。

【实证】该区域共 **144 个** `[a-z][a-z0-9_]*` 形态的键名；Native 的 `module.ini` 共有 **90 个去重键**（89 个真参数 + `load_resource` 加载指令）。其中 89 个出现在该区域；`supports_directx_7` 落在区域外，因为引擎以 `Bsupports_directx_7`（带 `B` 前缀）的形式存放它（地址 `0x7c1537`），但解析器确实引用它，故它仍被识别。

【实证 · 2026-10 本轮修正】**区块扫描是近似，走解析器分支才是权威。** 直接遍历解析器
`FUN_00573560` 的 145 个键查找分支（脚本 `G:\rea_tools\mkkeytable.py`），得到：

| 量 | 值 |
|---|---|
| 引擎识别的键 | **145** |
| 其中有直接存储地址 | 134 |
| 无直接存储（走共享分支或纯指令） | 10（含 `load_*` 5 个、`blood_multiplier`、`module_name`、`operation_set_version` 等） |
| 解析类型：`atoi` / `atof` / 其它 | 86 / 47 / 12 |
| **Native 未声明的键** | **53** |

上一版此处写 144 / 55，是区块扫描的产物；权威值以本轮解析器遍历为准。
`load_resource` 系列是**指令而非参数**（它们触发资源加载、不存值），把它们算进"键"会污染计数，
本节所有比例均已排除它们。

### 3.2 引擎没有"内置默认值表"：零初始化 + 使用点钳位

上一版这一节写的是「Native 的配平大量依赖引擎默认值」。**这个说法已被本轮推翻**，原因如下。

**事实一：这些设置全局量在 PE 镜像里根本没有字节。**

`.data` 节的几何是 `vsize = 0x2555438`（约 39 MB）而 `rawsize` 只有 `0xdc00`（56,320 B）。
全部设置全局量位于 `0x0a6f180`–`0x0a6f3xx`，即 `.data` 内约 6.3 MB 处——**远在文件字节之外**，
由加载器置零。`mbdis.py` 对 `0xa6f180` 报「未映射 / 零填充」是正确行为，不是工具缺陷。

**事实二：没有任何地方写默认值。**

对全 `.text`（`0x401000`–`0x7bdb6d`，1,225,011 条指令）扫描绝对寻址的立即数写入：
`mov dword ptr [0x0a6f...], <imm>` **一条都没有**；也不存在独立的初始化函数。
唯一的写入者是 `module.ini` 解析器本身。

> **结论【实证】**：一个既没有被 `module.ini` 声明、也没有在别处赋值的键，其全局量就是 **0**。
> 引擎没有内置默认值表。

**事实三：兜底发生在每一个使用点。**

引擎必须在读取处钳位，否则未设置的键会写出 `0.0` 这种破坏性数值。已完整读出的实例是
`attribute_required_per_skill_level`（存储 `0xa6f350`，int，Native **未设置**）：

```
0x58cb72  mov edi, dword ptr [0xa6f350]   ; edi = 该键的全局量
0x58cb7b  cmp edi, 1
0x58cb89  jg  0x58cb90
0x58cb8b  mov edi, 1                       ; ≤1（含未设置的 0）一律当 1 用
0x58cb9f  idiv edi
```

即 **未设置 ⇒ 有效值 1**，而不是上游文档常写的 3。

**给重建者的直接后果**：`module.ini` 里漏写一个键，得到的是「0 + 该使用点的钳位」，
**不是**引擎文档里写的那个默认值。要复现某条数值规则，必须去读使用点。
53 个 Native 未声明的键逐一的「有效默认值」因此是待办项（见 `05-未解项清单.md` A21）。

**成长相关键的真实存储地址**【实证：本轮 `mkkeytable.py` 实测】

| 键 | 存储地址 | 解析类型 | Native | 引擎读取点 |
|---|---|---|---|---|
| `skill_points_per_level` | `0x0a6f340` | float | 未设置 | 2 |
| `attribute_points_per_level` | `0x0a6f344` | float | 未设置 | 2 |
| `weapon_points_per_level` | `0x0a6f348` | float | 未设置 | 2 |
| `level_boundary_multiplier` | `0x0a6f34c` | float | 未设置 | 6 |
| `attribute_required_per_skill_level` | `0x0a6f350` | int | 未设置 | 1 |
| `battle_size_min` / `battle_size_max` | `0x0a6f334` / `0x0a6f338` | int | 未设置 | 1 / 1 |
| `far_plane_distance` | `0x0a6f1e8` | int | 未设置 | 0 |
| `starting_year` | `0x0a6f204` | int | 未设置 | 0 |
| `timid_modifier_speed_bonus` | `0x0a6f37c` | int | 未设置 | 1 |

> 上一版这张表列的是**键名字符串的地址**（`0x8159fc` 之类），那是查表用的字面串，
> 不是存储位置；本轮已换成真正的全局量地址。
>
> 「读取点 0」表示全 `.text` 内**没有绝对寻址的读取**。这足以说明该键在本 build 中
> 不被消费（例如 `starting_year`、`far_plane_distance`），但无法排除以寄存器基址相对寻址
> 的读取——这一点作为方法学限制记录。

### 3.3 一个曾被误判为未解的拼写问题（现已解决，且结论被进一步修正）

【实证】引擎的键名区域里**同时存在**两个只差一个字母的键：

| 键 | 地址 |
|---|---|
| `damage_interrupt_attack_threshold`（双 `s`） | `0x816530` |
| `damage_interrupt_attack_treshold`（单 `s`） | `0x816554` |

而 Native 的 `module.ini` 第 58 行设置的是**双 `s`** 版本（值 `3.0`）。

**【已解 · 实证】** 反编译 `module.ini` 解析器 `FUN_00573560` 后确认：引擎**依次检查这三个字面串**，它们是互为别名的兼容写法。解析器中的实际序列（汇编 `0x573a47` 起）：

```
PUSH 0x816554   ; "damage_interrupt_attack_treshold"      (单 s，遗留拼写，先查)
CALL 0x00453050 ; 键查找
TEST AL,AL
JNZ  0x0057564f ; 命中即跳转到共用处理分支
PUSH 0x816530   ; "damage_interrupt_attack_threshold"     (双 s，新拼写)
...
PUSH 0x816508   ; "damage_interrupt_attack_threshold_mp"  (联机)
```

前两个拼写命中后跳到**共用处理分支** `0x0057564f`；`_mp` 拼写有自己的分支（`0x573a83` 处 `je` 落空后顺序执行到 `0x573a97`）。

**结论（本轮修正）**：这三个拼写**不是**"同一项设置的三种写法"，而是**两个各自独立的设置**：

| 写法 | 存储地址 | 写入指令 | Native 值 | 读取点 |
|---|---|---|---|---|
| `damage_interrupt_attack_treshold`（单 `s`，遗留） | `0x0a6f210` | `0x575661`（共用分支 `0x57564f`） | 未设置 | — |
| `damage_interrupt_attack_threshold`（双 `s`） | `0x0a6f210` | 同上 | **3.0** | 3 |
| `damage_interrupt_attack_threshold_mp` | `0x0a6f214` | `0x573a97` | **1.0** | 3 |

两个地址的全部读取点（`xscan.py disp` 全 `.text` 扫描）成对出现在同两个函数里，相隔 8 字节：

```
0x4c05c2  fld dword ptr [0xa6f210]   ; 0x4c05ca  fld dword ptr [0xa6f214]
0x4c1c90  fld dword ptr [0xa6f210]   ; 0x4c1c98  fld dword ptr [0xa6f214]
```

即引擎把**单机阈值与联机阈值各存一份**，在同一段代码位置上按模式选用。
因此 Native 的 `3.0` 与 `1.0` **都生效，各自作用于自己的模式**。
上一版"三个键同为一项设置"的说法不准确——单 `s` 与双 `s` 才是别名，`_mp` 是另一项设置。

> 先前基于"字符串存在性"的怀疑（两个拼写都存在，无法判断哪个生效）已被函数级证据取代。
> 这说明**字符串存在性只能用于提出假设，判定必须落到比较代码上**——本轮又进一步说明，
> **"命中同一分支"也不等于"写入同一变量"，必须读到写入指令本身。**

### 3.4 完整键表

145 个引擎识别键的**存储地址、解析类型（`atoi`/`atof`）、Native 取值、读写点计数**完整列在
[04-数据字典](04-数据字典.md) 附录 C（§15）。生成脚本 `G:\rea_tools\mkkeytable.py` 可复现。

该方法学上的意义：**"某键到底有没有用"现在是一个可测量的事实**（读点计数），
不再依赖键名字义的推断。上一版那张表把"作用（【推断】自键名）"写进表里，本轮已全部删除。

## 4. 脚本虚拟机

### 4.1 编译格式与自校验

`scripts.txt` 把每个脚本存为：

```
<script_name> -1
 <op_count> (<opcode> <argc> <arg> ...) (<opcode> <argc> <arg> ...) ...
```

`op_count` 是**独立校验和**：只有把每个操作边界（含参数个数内联的可变参数操作）都切分正确，才能精确复现它。

【实证】全模块校验结果：

```
操作码表条目 : 1054
脚本数       : 610
解码操作数   : 36740
解码失败脚本 : 0
缺失名称操作 : 0
```

**0 失败**是"读对了"的充分证据：这套操作码表能精确复现随文件发布的每一个脚本。

### 4.2 操作数编码

操作数为 `tag << 56 | index`——高 8 位是类型标签，低 56 位是下标。

【实证】**引擎自己给出的权威操作数类型清单**来自它的越界校验字符串（`mb_warband.exe` 内，共 22 条）：

```
SCRIPT ERROR ON OPCODE %d: Invalid Animation ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Faction ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Group ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Info_page ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Item Kind ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Map Icon ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Menu ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Mesh ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Mission Template ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Overlay ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Party ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Party Template ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Presentation ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Quest ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Quick String ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Register ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Scene ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid Script Parameter ID: %d
SCRIPT ERROR ON OPCODE %d: Invalid String ID: %d

```

这张清单同时说明了虚拟机**运行时会做越界检查**（越界即打印 `SCRIPT ERROR`，而不是崩溃或静默），也说明了操作数空间的完整规模——比仅靠脚本层用法推断出的 tag 表更完整。

### 4.3 存储空间

脚本语言有五个互相独立的存储空间，它们的越界错误各有专门的消息（见 §4.2）：**寄存器**（`Invalid Register ID`）、**字符串寄存器**（`Invalid String Register ID`）、**脚本参数**、**触发器参数**、**快速字符串**。局部变量（`tag 17`）是全模块出现最多的操作数类型。

### 4.4 整数语义

**所有除法都是截断整除。** 这不是细节：多处规则会用连续多次整除做归一化，误差会累积。任何按浮点重算的实现都会与游戏实际行为不符。

### 4.5 引擎不携带操作码名表

【实证】对 `store_add`、`troop_get_level`、`party_get_slot`、`assign`、`store_script_param` 等操作名做精确匹配，在 7,890 条引擎字符串中**命中数全部为 0**。

**结论**：引擎里的操作码是**纯数字**，没有名字。所有"操作码 → 名称"的映射只能来自随文件发布的 `header_operations.py`（1,054 项），其正确性由 §4.1 的 `op_count` 校验保证。

## 5. 引擎 ↔ 脚本的接口

### 5.1 机制

引擎需要调用模块逻辑时（计算工资、询问价格、处理遭遇……），它**按脚本名查找**该脚本并调用。这就是战团 MOD 生态的核心扩展点：模块只要定义了约定名字的脚本，引擎就会调用它。

### 5.2 严格确定的接口清单

用**精确集合交集**确定：把 `scripts.txt` 里解析出的 **610 个脚本名**与引擎字符串集合求交，得到 **49 个**两者共有的名字。

【实证】这 49 个名字就是引擎按名字解析的接口：

**查询类（引擎向模块要一个值）**

`game_get_troop_wage`、`game_get_total_wage`、`game_get_join_cost`、`game_get_upgrade_xp`、`game_get_upgrade_cost`、`game_get_prisoner_price`、`game_get_item_buy_price_factor`、`game_get_item_sell_price_factor`、`game_get_morale_of_troops_from_faction`、`game_get_skill_modifier_for_troop`、`game_get_party_speed_multiplier`、`game_get_party_prisoner_limit`、`game_get_party_companion_limit`、`game_get_use_string`、`game_get_item_extra_text`、`game_get_money_text`、`game_get_date_text`、`game_get_statistics_line`

**笔记/命名类（引擎要一段显示文本）**

`game_get_center_note`、`game_get_troop_note`、`game_get_faction_note`、`game_get_quest_note`、`game_get_info_page_note`、`game_get_scene_name`、`game_get_mission_template_name`、`game_reset_player_party_name`

**事件类（引擎通知模块"发生了什么"）**

`game_event_party_encounter`、`game_event_simulate_battle`、`game_event_battle_end`、`game_event_buy_item`、`game_event_sell_item`、`game_event_detect_party`、`game_event_undetect_party`、`game_event_context_menu_button_clicked`

**动作/杂项类**

`game_check_prisoner_can_be_sold`、`game_get_cheat_mode`、`game_enable_cheat_menu`、`game_get_console_command`、`game_context_menu_get_buttons`、`game_on_disembark`、`game_quick_start`、`game_start`、`game_receive_url_response`、`game_receive_network_message`、`game_get_multiplayer_server_option_for_mission_template`、`game_multiplayer_server_option_for_mission_template_to_string`、`game_multiplayer_event_duel_offered`、`game_get_multiplayer_game_type_enum`、`game_multiplayer_get_game_type_mission_template`、`game_set_multiplayer_mission_end`

### 5.3 这张清单说明的三件事

1. **所有玩家可见的"数字"都是脚本给的。** 工资、升级费用、升级经验、赎金价格、买卖价格系数、士气——引擎一个一个地问脚本要。这是"数值设计写在脚本里"的直接证据。
2. **所有玩家可见的"文本"也是脚本给的。** 笔记、日期、金钱显示、物品额外说明都由脚本生成。
3. **单机与联机共用同一套接口。** 清单里混着 `game_multiplayer_*`，说明引擎用同一套钩子机制服务两种模式。

### 5.4 一个自洽性佐证

【实证】`get_level_boundary` 作为完整脚本名在引擎字符串中**命中数为 0**；`party_calculate_strength`、`get_trade_penalty`、`calculate_main_party_shares` 同样为 0。

这与本节结论一致：**它们是模块自己定义并互相调用的内部脚本，不是引擎钩子**，所以引擎没有理由持有它们的名字。反过来，凡是出现在引擎名表里的，就一定是引擎要调的（§5.2 的 49 个）。

> 这一点同时给出了"引擎内置操作 vs 模块脚本"的**判定方法**：名字出现在引擎字符串里 ⇒ 引擎按名解析 ⇒ 是钩子；不在 ⇒ 只能是模块内部调用或引擎内置操作。

## 6. 运行时对象模型

### 6.1 实体类型

由 §4.2 的校验清单，引擎在运行时把操作数解析为下列实体类型（这是**引擎自己承认**的类型集）：

| 类别 | 实体 |
|---|---|
| 人物 | 兵种（Troop） |
| 组织 | 部队（Party）、部队模板（Party Template）、阵营（Faction）、集团（Group） |
| 物品 | 物品（Item Kind） |
| 空间 | 场景（Scene）、网格（Mesh）、地图图标（Map Icon） |
| 界面 | 菜单（Menu）、界面元素（Overlay）、呈现（Presentation）、动画（Animation）、信息页（Info_page） |
| 任务 | 任务（Quest）、任务模板（Mission Template） |
| 文本 | 字符串（String）、快速字符串（Quick String） |
| 执行 | 寄存器（Register）、字符串寄存器（String Register）、脚本参数、触发器参数 |

### 6.2 数组下标即身份

编译后的数据文件**不携带名字**（名字只存在于开发期的 `module_*.py` 里）。引擎按**位置**解析记录，脚本引用实体时用的是**裸下标**。

**后果（对任何想改动这个游戏的人都是硬约束）**：

- `troops.txt` / `item_kinds1.txt` / `parties.txt` / `factions.txt` / `skills.txt` 的**记录顺序不可重排**。
- 在表中间**插入或删除**一条记录，会使其后所有记录的编号整体偏移，从而破坏所有脚本引用。
- 因此 MOD 只能在**表尾追加**记录，或整体重编（并同步更新所有脚本中的下标）。

### 6.3 槽位系统与"槽位无名"问题

实体除固定字段外，还带有若干**通用槽位**（slot），供脚本自由存放数据：`party_get_slot` / `party_set_slot`、`troop_get_slot`、`item_get_slot`、`faction_get_slot` 等。

**关键限制**【实证】：

- 随文件发布的模块常量文件是**多人/拿破仑世代**的，它包含 `base_export_percentage`、`max_food_amount`、`max_distance_to_loot`、`item_class_food` 等，却**不定义任何单机模式的槽位名**。
- 在 `_rea/modulesys/module_constants.py` 中做前缀检索：`slot_town_` / `slot_party_` / `slot_center_` 命中数均为 **0**；仅 `slot_troop_` 命中 12 次、`slot_faction_` 命中 17 次。

因此：**所有槽位号在脚本里都是裸整数，其用途只能从脚本用法反推，必须标【推断】。** 本套文档中凡出现槽位号处，均遵循这一纪律（槽位用途表见数值册与数据字典册）。

### 6.4 运行时播种、无法从模块数据恢复的部分

【实证】有几类数据在模块文件中**不存在**，只能在运行时生成：

| 现象 | 证据 |
|---|---|
| 中心点归属 | `parties.txt` 中全部 180 个中心点（22 城 / 48 堡 / 110 村）都写成 `fac_neutral` |
| 领主部队 | `parties.txt` 的 240 个部队中**没有任何领主部队** |
| 驻军、志愿兵池、繁荣度、物价指数 | 模块文件中无对应字段 |

**这是本套文档的一条硬边界**：上述内容的**初始值**无法从随文件发布的字节恢复。文档中凡涉及它们处，只描述**运行时规则**（脚本如何计算），不给出"初始值"。

## 7. 引擎实现观测（反编译）

### 7.1 目标与无符号事实

| 项目 | 值 |
|---|---|
| 目标 | `mb_warband.exe` |
| 大小 / 格式 | 5,362,688 字节，PE 32 位（x86） |
| SHA-256 | `FF4A28C51BED49FE4BBB4BB96389F7611894F6D031BF68FFF661EFDC946DAE13` |
| 分析工具 | Ghidra 12.1.4（经 REA 驱动），Microsoft C++ 名字还原已启用 |
| 函数总数 | **10,618** |
| 带真实名字的函数 | **353** |
| 其余 | 9,410 个 `FUN_*`、28 个 `thunk_*`、451 个 `_` 开头、以及 `Catch@`/`LAB_` 等 |

**坏消息（必须先说清）**：那 353 个带名字的函数**没有一个是游戏逻辑函数**——全部是 C 运行库（`strtoxq`、`xtoa`、`flsall`、`doexit`、`_sscanf`、`__set_dstbias` …）与异常处理/展开（`Catch@*`、`CatchGuardHandler`、`TranslatorGuardHandler`、`FindHandlerForForeignException`、`Unwind@*`）。**游戏主体代码已被完全剥离符号。**

**后果**：不存在"按名字查引擎函数"的捷径。引擎侧的一切还原都必须依靠**字符串锚点 → 交叉引用 → 所在函数**这条链。

### 7.2 定位方法学（可复用）

本项目确立的定位链条：

1. **找锚点字符串**：凡是模块要以名字指定的东西（`module.ini` 的键、引擎按名解析的脚本名、资源名），其字面串必然存在于引擎里。
2. **求交叉引用**：`xrefs <字符串地址>` 给出引用该串的**指令地址**。
3. **求所属函数**：把指令地址解析到包含它的函数入口。
4. **反编译该函数**：取伪代码与汇编，读实际算术。

【实证】以 `armor_soak_factor` 为例，锚点与引用全部落定：

| 字符串地址 | 内容 |
|---|---|
| `0x816788` | `Setting armor_soak_factor_against_blunt = ` |
| `0x8167b4` | `armor_soak_factor_against_blunt` |
| `0x8167d4` | `Setting armor_soak_factor_against_pierce = ` |
| `0x816800` | `armor_soak_factor_against_pierce` |
| `0x816824` | `Setting armor_soak_factor_against_cut = ` |
| `0x816850` | `armor_soak_factor_against_cut` |

它们全部被引用于 **`FUN_00573560`**（入口 `0x573560`，函数体 `0x573560–0x57572f`，8,656 字节）。

【推断】`FUN_00573560` 是 **`module.ini` 的配置解析器**——它集中读取这批键，并把结果写入某个设置结构体/全局。注意它读取的是**三个 soak 因子全部**，且伴有 `Setting ... = ` 形式的调试输出串，符合"加载配置并打印结果"的行为。

【未解】伤害公式**不在**这个函数里——它是**使用**解析结果的那段代码。要定位它，必须先从解析器解出设置结构体的存放位置，再对那个全局求交叉引用，找出读取者。这条链尚未走完。

### 7.3 引擎字符串中已确认的两张名表

| 名表 | 地址范围 | 规模 | 内容 |
|---|---|---|---|
| 引擎按名解析的脚本钩子 | `0x7c6718 .. 0x7c6d28` | 55 个 `game_*` | 与 `scripts.txt` 求交得 49 个真实脚本（§5.2） |
| 引擎识别的 `module.ini` 键 | `0x8155e0 .. 0x8168f8` | 144 个 | 由解析器直接走出的识别键为 **145 个**，差额 1 个是字面串落在该区块之外的键 |

两表的字符串都是**按名字长度紧凑排布**的连续区块（实测条目间距随名字长度取 20/24/28/32/36/40/48/56/64 字节），说明它们是成块布置的名称列表。

> 这里有一个值得记录的方法学教训：**字符串区块的边界是人为划定的，而解析器的分支结构是客观的**。
> 本轮改用「走解析器分支」来枚举键（`mkkeytable.py`），得到的 145 是权威值；
> 区块扫描得到的 144 只是它的一个近似，二者不应互相当作校验依据。

### 7.4 已读通的三条引擎流水线

本轮把三条此前只有"位置"、没有"内容"的引擎流水线逐指令读通。此处只给架构层面的形状与入口地址，
数值代数见 [01-数值设计](01-数值设计.md)，运行时对象字段见 §6。

**(1) `module.ini` 解析器** `FUN_00573560`，体 `0x573560–0x57572f`。
对所有 145 个键执行同一套四步惯用法：

```
push <键字面串>; call 0x453050        ; HasKey
test al,al; je <下一个键>
call 0x452f30                         ; 取 std::string 的 c_str
call 0x626c10 (atoi) | 0x626cdc (atof) ; ← 这一步决定该键是 int 还是 float
fstp/mov dword ptr [<0x0a6f...>], ...  ; 写入存储全局量
jmp 0x575714                           ; 完成
```

**每个键的解析类型因此是可测的**：86 个走 `atoi`，47 个走 `atof`，12 个走别的路径。
这是"引擎把该键当整数还是浮点"的唯一权威来源——与 `module.ini` 里写成 `1` 还是 `1.0` 无关。

**(2) 伤害结算** `FUN_004b3050`，体 `0x4b3050–0x4b36a5`，1,622 字节，58 个基本块，`RET 0x4`。
**全程序只有两个调用点**：

```
0x4bb2c8  ← FUN_004bb290    （战役 / 脚本路径；把结果拷进 agent 的 132 字节受击记录）
0x4ec1ba  ← FUN_004ec100    （场景内 agent 互伤；把 +0x44 作为返回值返回）
```

两条路径都把 `DamageInfo+0x44` 当作最终穿甲伤害。`FUN_004b3050` 的每个系数键
（soak/reduce × cut/pierce/blunt、extra_penetration、crush_through）**恰好只有 1 个读点**，
这本身就是"代数已被完整捕获、没有第三个读者"的强证据。

**(3) 经验入账 / 升级结算** `FUN_004acd60`（入口 `0x4acd60`）。
签名按用法为 `ECX = this`（角色/部队管理器单例），`[EBP+8] = 兵种下标`，`[EBP+0xc] = 经验增量`。
关键结构：

| 项 | 值 |
|---|---|
| 兵种记录步长 | `0xfc8`（4040 字节） |
| 兵种记录数组基址指针 | `this + 0x140f0` |
| 玩家的兵种下标 | `this + 0x6e0` |
| 累计经验 | 记录 `+0x2b4` |
| 等级下标 | 记录 `+0x2c8` |
| 等级门槛表 | `0x0080ecb4`（`.rdata`，int32 × 63） |
| 经验增量钳位 | `[0, 29999]`（`0x7530` 上界，超出则取 `0x752f`） |

**模块层无法定义经验曲线，只能整体缩放它**：曲线本体是编译期常量表，
`level_boundary_multiplier` 只作为乘数出现。这是"哪些设计参数被引擎锁定、哪些留给模块"
的一个典型样本——**曲线形状锁定，缩放开放，而 Native 连缩放也没用**。

## 9. 本册的复核方式

| 结论 | 复核方式 |
|---|---|
| 模块文件清单、`module.ini` 内容 | 直接列出/读取 `Modules/Native/` |
| 145 个引擎配置键、53 个未设置的键 | 遍历 `mb_warband.exe` 中解析器 `FUN_00573560` 的键查找分支（`G:\rea_tools\mkkeytable.py`），并与 `module.ini` 求差集；写入点与读点由全 `.text` 绝对寻址扫描计数 |
| 三条引擎流水线（配置解析 / 伤害结算 / 经验结算） | 逐指令读出，函数体范围、调用点、系数读取点均可复核（§7.4）；关键结论另有交叉验证：**每个伤害系数键恰好只有 1 个读点** |

| `FUN_00573560` 是配置解析器 | 对 6 个 soak 相关字符串求交叉引用，全部指向该函数 |
| 无符号、10,618 个函数 | 函数清单直接统计 |
