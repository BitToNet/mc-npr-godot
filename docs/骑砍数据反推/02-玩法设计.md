# 《骑马与砍杀：战团》Native 模块 — 玩法设计文档

> 目标读者：游戏设计师与程序。本文只回答四件事：**玩法怎么运转、由哪些规则驱动、设计意图是什么、玩家实际体验到什么。**
> 全文只用三种标签，贯穿每一节：

| 标签 | 判定标准 |
|---|---|
| **【实证】** | 来自本模块已解码的脚本字节码，或随模块发行的编译数据。可逐条复核，公式里每个常数都能定位到某条操作 |
| **【推断】** | 运算是实测的，但含义或命名是从用法反推的。例如「这个槽位是繁荣度」是推断，「它在 0…100 被钳制」是实测 |
| **【未解】** | 本模块的数据与脚本无法确定。只登记问题与影响，不给答案、不用社区公式顶替实测值 |

## 0. 证据基础与阅读约定

### 0.1 设计意图

本文不是玩法说明书，而是一份**规则考古报告**：把一台持续运行的模拟器的所有可测规则摊开，供重建时逐条对齐。因此本文的第一原则是**宁可记「不知道」，也不填一个看起来合理的数**。

### 0.2 证据来源与规模

操作码表 **1054** 个、脚本表 **610** 个脚本 / **36740** 条操作、其中**已还原 34 个**（经济、部队、士气、经验、战斗、战术）；`troops.json` **1072** 条、`parties.json` **240** 条、`party_templates.json` **63** 条、`factions.json` **34** 条、`items.json` **620** 条、`skills.json` **42** 条。以上全部 **【实证】**。

校验基线：`mb_module.py validate` 的结论是 **1054 个操作码、610 个脚本、36740 条操作、0 失败【实证】**。下文所有「已确证」都建立在这个基线上。

### 0.3 编译数据的身份规则

**数组顺序就是身份。** 编译后的数据文件不携带名字，脚本操作数里的兵种/部队/阵营/物品编号全是数组下标。

- 数据表**永远不能重排**。重建时若按名字排序部队，脚本引用的 `p_town_1`、`trp_looter` 会全部指错对象 **【实证】**。
- 脚本里的**范围比较**是最重要的结构信息。`trp_watchman <= troop < trp_mercenaries_end` 等价于「这个编号区间里的兵种」，区间边界本身就是设计者留下的分类标签 **【实证】**。
- 槽位号在数据里是**裸整数**，模块没有发行任何单机版槽位常量表 **【实证】**。所以全文槽位名都是 **【推断】**，槽位号本身是 **【实证】**。
- **「删除实体」必须实现成「标记 + 过滤」**，不能实现成「从数组移除」（见 §9.4）。

## 1. 总览：这台机器怎么转

### 1.1 设计意图

战团单机不是关卡制，而是一台**持续运行的模拟器**：时间在大地图上一直走，180 个据点、几十支部队各自按规则演化，玩家只是其中一支。所有系统挂在同一根时间轴上，用「每过一段固定时间跑一次」的脚本互相牵动。

这带来一条贯穿全文的约束：**没有任何一次交互是自足的交易。** 买一次粮会改士气、改物价、改地方繁荣度；打赢一次匪帮会同时产出生经验、金币、战利品和本地招募资源。设计任何一条规则时，都必须假设它会被反复调用成百上千次。

### 1.2 核心循环的四个交接点

```
大地图行军 ──遭遇──▶ 交涉 / 战斗 ──胜负──▶ 战利品 + 经验 + 金币
     ▲                                              │
     └────────── 招募 + 补给 + 升级 ◀───────────────┘
```

| 交接点 | 承载脚本 / 数据 | 标签 |
|---|---|---|
| 行军 → 遭遇 | 视野范围、地图距离上限（`module.ini`） | **【实证】** |
| 遭遇 → 战斗 | `game_event_simulate_battle`（396 条操作） | **【实证】** |
| 战斗 → 战利品 | `party_calculate_loot`、`party_give_xp_and_gold` | **【实证】** |
| 补给 → 行军 | `get_player_party_morale_values`、`consume_food` | **【实证】** |

四个环里**只有第三环是正向反馈**（打赢→变强）。另外三个都是负反馈：食物会吃完、士气被队伍规模压低、工资随等级平方增长。**这就是战团「越强越贵」的手感来源。**

### 1.3 时间与空间刻度

**【实证】** `module.ini`：`time_multiplier=0.25`、`seeing_range=6.5`、`track_spotting_multiplier=0.8`、`mission_object_prune_time=180`；地图框 `map_min_x=-180`、`map_max_x=180`、`map_min_y=-145`、`map_max_y=145`、`map_max_distance=175.0`。

**【实证】** 180 个据点的实际坐标范围：x ∈ [−146.3, 176.0]，y ∈ [−114.5, 127.5]——全部落在可玩矩形内，四周留出的余量是给部队绕行与刷怪点用的。22 个城镇中，最西 `p_town_15` Yalen (−132.8, −47.3)，最东 `p_town_22` Bariyye (165.0, −106.7)，最北 `p_town_13` Rivacheg (64.8, 113.7)，最南 `p_town_19` Shariz (15.0, −107.0)。**四个方向都有城镇 = 设计者有意做的远征距离梯度【推断】。**

**【实证】** 平均据点间距约 27 单位（由坐标均值估算 **【推断】**）；对照 `average_trade_good_prices` 里「距离 < 50 才发生价格扩散」的设定，可反推设计者认为 **50 单位 ≈ 两个相邻经济区**。

**【未解】** ①`time_multiplier=0.25` 换算成秒的规则在 `mb_warband.exe` 内，所以本文所有「每小时/每天」速率只能给**每次调用**的量，不能给真实秒数。②地图坐标单位与厘米/米的换算（`ENGINE_CONSTANTS.md` 亦列为未知）。③调用 `update_trade_good_prices` / `average_trade_good_prices` 的周期触发器不在 34 个脚本内，**所以物价每天漂移多少无法计算**。**这是本模块最大的「设计意图可见、手感不可算」的缺口，任何重建都必须自己决定「一天跑几次价格脚本」，而这个决定直接改变跑商收益曲线。**

### 1.4 一局游戏里真正被写进数据的东西

**【实证】** 240 条部队记录，**只有 16 条携带初始兵力**：

| 记录 | 阵营 | 初始兵力 | 性质 |
|---|---|---|---|
| `p_main_party` | `fac_player_faction` | 1 × `trp_player` | 玩家 |
| `p_camp_bandits` | `fac_outlaws` | 3 × `trp_temp_troop` | **唯一预置敌人** |
| 8 个 `p_*_bandit_spawn_point` | `fac_outlaws` | 15 × `trp_looter` | 刷怪点 |
| `p_spawn_points_end` + 5 × `p_reserved_*` | `fac_commoners` | 15 × `trp_looter` | 占位填充 |

**【实证】** `p_camp_bandits` 用的兵种是 `trp_temp_troop`（索引 3），一个内部临时兵种——**模块预置的那一场战斗，敌人本身是占位内容**。全部 240 条部队的 `personality`、`ai_behavior`、`ai_target` 都是 **0**。兵力成分表（63 条模板）里有 **40 条**带成员配置，但它们**不在** `parties.txt` 里，只能由运行时脚本实例化。

**设计结论【实证 + 推断】：**

1. **大地图上没有领主部队。** 按 id 检索 `lord` / `knight` / `patrol` / `caravan` / `merchant` / `merc`，命中数为 **0【实证】**。
2. 「几十支领主部队互相攻伐」的观感**完全来自运行时的模板刷兵**；模块数据只能证明模板的存在与规模（`pt_kingdom_1_reinforcements_a/b/c`、`pt_merchant_caravan`、`pt_looters`），**不能证明它们何时、在哪、刷多少【推断】**。
3. **把「运行时刷兵」当可选项省掉，大地图会变成只有玩家和一个训练用匪帮的空壳。这是本节最需要设计者接手的地方。**

## 2. 大地图与部队移动

### 2.1 设计意图

大地图只做两件事：**把玩家的资源压力（时间）摊开成距离**，**制造玩家无法完全掌控的相遇**。距离即成本（粮会吃完、工资按周结算），相遇即风险（视野是有限的量）。这要求地图**足够大以至一次远征要花掉多天**，又**不能大到据点失去地理意义**。

### 2.2 部队移动速度

**【未解】** **战役地图上的部队速度公式不在任何随模块发行的文件里**，它在 `mb_warband.exe` 内部（`RULES.md` 未知表第 9 项）。本文不给速度公式，只能给出**影响速度的输入**：

| 输入 | 证据 |
|---|---|
| `skl_pathfinding`——`skills.txt` 说明「每级 +3% 地图速度（队伍技能）」 | **【实证】** |
| 是否骑马（兵种表带 `is_mounted`；工资源码对骑乘兵种单独加权） | **【实证】** |
| 部队规模（士气公式里 `partySize` 被直接扣减） | **【推断】** |
| 地形/道路 | **【未解】** 无任何随模块发行的数据描述道路或地形速度 |

**重建提示**：`RECONSTRUCTION.md` 明确把这组常数标为**标定值而非还原值**——`MbParty.BASE_FOOT_SPEED = 14.0`、`MOUNTED_BASE_SPEED = 16.0`、`MOUNTED_SPEED_PER_RIDING = 1.6`、`Movement.UNITS_PER_SPEED_HOUR = 0.42`，依据只是「保证顺序：步兵慢于骑兵，骑兵随骑术提升」。**本文不把它们当作原游戏数值。**

### 2.3 视野与遭遇

**【实证】** `seeing_range = 6.5` 是基础视野；`skl_spotting`「每级 +10% 队伍视野」；`skl_tracking` 与 `track_spotting_multiplier = 0.8` 管痕迹信息。**【未解】** `seeing_range` 的单位，以及「视野 × 地形遮挡」的运算。

**设计意图【推断】**：视野是**只能靠技能提高、不能靠钱提高**的量。这与队伍容量、士气可以靠钱（粮、工资）维持形成对照——**设计者把「看得见」划进了成长系统，而不是经济系统。**

### 2.4 地图上的实体清单

**【实证】** 240 条部队按索引分块，全部有明确归属：

| 索引块 | 数量 | 身份 |
|---|---|---|
| 0 | 1 | `p_main_party`（玩家） |
| 1–19 | 19 | 引擎内部工作部队：`p_temp_party`、`p_temp_party_2`、`p_temp_casualties(_2/_3)`、`p_temp_wounded`、`p_temp_killed`、`p_main_party_backup`、`p_encountered_party_backup`、`p_collective_friends_backup`、`p_player_casualties`、`p_enemy_casualties`、`p_ally_casualties`、`p_collective_enemy/ally/friends`、`p_total_enemy_casualties`、`p_routed_enemies` |
| 20–200 | 181 | 据点：`p_zendar`(20) + 22 城镇(21–42) + 48 城堡(43–90) + 110 村庄(91–200) |
| 201–211 | 11 | `p_salt_mine`、`p_four_ways_inn`、`p_test_scene`、`p_battlefields`、`p_dhorak_keep`、`p_training_ground`、`p_training_ground_1…5` |

| 226–233 | 8 | 匪帮刷怪点 |

**【实证】** 按阵营统计：`fac_neutral`(3) **222** 条、`fac_outlaws`(2) **9** 条、`fac_commoners`(1) **8** 条、`fac_player_faction`(13) **1** 条。四者相加 222 + 9 + 8 + 1 = **240，完全对齐**。全部 240 条共 **23 种**不同图标旗标。

**设计结论：**

1. **19 条内部工作部队是可被脚本引用的真实部队【实证】**——`p_player_casualties`、`p_enemy_casualties`、`p_ally_casualties` 正是 `count_casualties_and_adjust_morale` 读的「伤亡账本」（§4.4）。**把战斗结算写成「就地减员」而不是「记账」的重建，会丢掉整条士气与政治链路。**
2. **14 座桥是独立部队记录【实证】**，有独立坐标与独立图标旗标（`541736` / `541737` / `541738` 三个变体）。桥的玩法作用（是否加速、是否阻挡）**在数据里看不到【未解】**。
3. **整个地图上的「坏人阵营」在初始状态下一共 9 个实体【实证】**（1 个 `p_camp_bandits` + 8 个刷怪点）。

## 3. 部队与补给

### 3.1 设计意图

这套系统只做一件事：**给玩家的队伍规模设一个软上限**。上限不由数字直接给出（没有「最多 100 人」这种规则），而是由三条互相独立的压力线共同挤压：

1. **士气随人数线性下降**（人手越多越难带）；
2. **工资随等级平方上升**（精锐越贵）；
3. **食物随时间消耗**（远征有硬成本）。

三条线任意一条单独存在都能被绕过，**必须同时成立才能形成「规模是一种资源」的手感**。这正是本模块把三者写在三个不同脚本里的原因。

### 3.2 编制、容量与战斗人数

**【实证】** `party_count_fit_for_battle(party)`：遍历每个兵种堆栈——**英雄未负伤计 1、负伤计 0**；**常规兵计「堆栈人数 − 该堆栈伤员数」**；求和返回。

**设计含义【实证】：**

- **一个英雄永远只算一个战斗力**，不管他带多少护卫。
- **一个负伤的英雄算零**。这是英雄唯一会被「削弱」的形态（他们不会死，见 §4.3），也解释了为什么「把英雄打伤」本身就是战术目标。
- **负伤的病号不占战斗位，但仍在编制里吃粮、领工资。**

**【实证】** `module.ini` 给的上限基值：`base_companion_limit = 20`、`skill_leadership_bonus = 3`、`skill_prisoner_management_bonus = 5`；以及两个击倒门槛 `player_wounded_treshold = 5`、`hero_wounded_treshold = 15`。

**【推断】** `skills.txt` 说明 `skl_leadership` 是「每点 +5 可指挥部队上限」、`skl_prisoner_management` 是「每级 +%d 最大俘虏数」，所以上表三个基值对应这两个上限与同伴上限。结合 §4.3 里英雄「每次被命中掉 45 点生命、下限锁死 1」的写法，**那两个 `wounded_treshold` 才是「英雄被击倒」的判定线【推断】**。

### 3.3 食物

#### 3.3.1 消耗

**【实证】** `consume_food(amount)`：

```
capacity = troop_get_inventory_capacity(trp_player)
for slot in 0 .. capacity:
    item = troop_get_inventory_slot(trp_player, slot)
    if itm_smoked_fish <= item < itm_siege_supply:          # 任何食物
        if modifier != 41 and item_get_slot(item, 0) == 0:
            item_set_slot(item, 0, 1)                       # 标记「本轮已吃」
            amount -= 1
            if amount < 0:                                  # 粮吃完了
                capacity = 0                                # 改循环上界来跳出
                troop_inventory_slot_set_item_amount(trp_player, slot, 该槽数量 - 1)
```

**【实证】** 食物区间是 `itm_smoked_fish`(110) ≤ item < `itm_siege_supply`(125)，即 **15 个物品**：

| 索引 | id | 名称 | 价值 | 重量 | `food` 标记 | 索引 | id | 名称 | 价值 | 重量 | `food` 标记 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 110 | `itm_smoked_fish` | Smoked Fish | 65 | 15.0 | 是 | 118 | `itm_raw_olives` | Olives | 100 | 40.0 | **否** |
| 111 | `itm_cheese` | Cheese | 60 | 15.0 | 是 | 119 | `itm_grain` | Grain | 30 | 30.0 | **否** |
| 112 | `itm_honey` | Honey | 120 | 15.0 | 是 | 120 | `itm_cattle_meat` | Beef | 80 | 20.0 | 是 |
| 113 | `itm_sausages` | Sausages | 90 | 15.0 | 是 | 121 | `itm_bread` | Bread | 50 | 30.0 | 是 |
| 114 | `itm_cabbages` | Cabbages | 30 | 15.0 | 是 | 122 | `itm_chicken` | Chicken | 95 | 10.0 | 是 |
| 115 | `itm_dried_meat` | Dried Meat | 85 | 15.0 | 是 | 123 | `itm_pork` | Pork | 75 | 15.0 | 是 |
| 116 | `itm_apples` | Fruit | 44 | 20.0 | 是 | 124 | `itm_butter` | Butter | 150 | 6.0 | 是 |
| 117 | `itm_raw_grapes` | Grapes | 75 | 40.0 | **否** | — | — | — | — | — | — |

（全部 **【实证】**，逐条取自 `items.json`。）

**两个必须知道的设计事实【实证】：**

1. **「什么是食物」在模块里有两种互不相同的定义。** Grapes / Olives / Grain 被脚本当食物，却在物品表里没有 `food` 标记；反过来 `itm_horse_meat`(16) 与 `itm_raw_date_fruit`(106) **有 `food` 标记却落在脚本食物区间之外**。带 `food` 标记的共 **14 个**，脚本区间内共 **15 个**，只在 12 个物品上重合。⇒ **只按 `food` 标记做食物系统的重建，会让 Grapes / Olives / Grain 失效、并让 Horse Meat 凭空变成军粮。这是最容易踩的坑之一。**
2. **`modifier == 41` 的食物不能吃**，同一个 41 也在士气公式里（§3.4.2）用来跳过被排除的食物。**【推断】** 41 是一个腐坏/非食用标记，但名字与合法范围本模块不提供。

**【实证】** `item_get_slot(item, 0)` 是「本轮已吃过」的瞬时标记，由本脚本写入；**谁负责清零不在 34 个脚本里【未解】**。

**【推断】** 脚本把**循环上界变量**本身改成 0，靠模块系统在下一次迭代重测上界来终止，而不是用 `break`——这不是笔误，是模块系统的惯用法。

**【未解】** `consume_food(amount)` 的调用者不在 34 个脚本内，**所以「一个 100 人的部队每天吃多少粮」无法从本模块算出**，只知道单位是「食物物品的件数」。

#### 3.3.2 据点也在吃粮

**【实证】** `center_get_food_consumption(centre)`：类型 `3` 返回 **500**（城镇）；类型 `2` 返回 **50**（城堡）；其余返回 **0**（村庄）。**城镇是城堡的十倍，村庄为零。**

**设计意图【推断】**：据点也在吃粮，而城镇是个巨大的粮仓黑洞。这解释了为什么「养活一座城市」在原游戏里是负担而不是纯收益。

**【推断】** `party_slot(centre, 0)` 是据点的**类型**字段，`3 = 城镇`、`2 = 城堡`、其余为 0。同一槽位在别处还被拿去和 `11`、`15`、`13`、`18` 比较（§4.5、§6.6），**所以完整枚举是【未解】**，本文只能锚定 2 与 3。

### 3.4 士气

士气是补给系统里唯一「双向」的量：可以被带上去，也可以被压下来，且有明确的可视化分档。

#### 3.4.1 两个写入函数

**【实证】** `change_party_morale(party, delta)`：把 `morale + delta` 钳到 `[0, 100]` 后写回，把变化量的**绝对值**放进 `reg1`。

**【实证】** `change_player_party_morale(delta)`：**先把读到的士气钳到 `[0, 100]`**，再加 delta、再钳一次、再写回；下降显示 `str_party_lost_morale`，上升显示 `str_party_gained_morale`。

**设计含义【实证】**：第二个函数在加 delta **之前**先钳一次输入。这是一道防御——即使存档或别的脚本塞进一个越界值（比如 300），它也不会泄漏进新值。**重建时省掉这次预钳制，一个坏数据就能让士气永久锁死在 100。**

#### 3.4.2 主公式

**【实证】** `get_player_party_morale_values()`：

```
partySize = Σ 主队堆栈人数（从堆栈 1 开始；英雄按 1 计，常规兵按实际人数计）
leadership = store_skill_level(skl_leadership, trp_player)
若 $players_kingdom == fac_player_supporters_faction
   且 faction_get_slot($players_kingdom, 11) == trp_player:   # 玩家自己当国王
    leadershipMod = leadership * 15
否则: leadershipMod = leadership * 12

morale = leadershipMod − partySize + 50

# 食物：遍历 itm_smoked_fish .. itm_siege_supply，排除修饰 41
foodMod = Σ item_get_slot(item, 1) * 3 / 2
morale += foodMod
若 foodMod == 0: morale −= 30                                  # 断粮

# 欠薪
若 $g_player_debt_to_party_members > 0:
    morale −= clamp($g_player_debt_to_party_members * 10 / max(周薪, 1), 1, 31)

morale = clamp(morale, 0, 100)
```

**【实证】** 常数：领导力 **×15（自立为王）/ ×12（否则）**；基数 **+50**；食物值 **×3/2**；断粮 **−30**；欠薪项 **债×10 / 周薪**，钳 **[1, 31]**；最终钳 **[0, 100]**。

**设计结论：**

1. **`partySize` 从堆栈 1 开始累加，玩家本人不计入【实证】** —— 惩罚衡量的是「你带了多少人」，不含你自己。
2. **英雄按 1 人计，常规兵按实际人数计【实证】**。20 个英雄与 20 个民兵的士气代价相同，但战斗力与维护成本完全不同——**英雄在士气上是「人数」，在工资上是「等级²」**。
3. **领导力 12 与 15 的差别就是「自立与否」【实证】。这是本模块里最直接的一条政治-玩法耦合**：当国王不只是外交上的事，它直接给每点领导力多 3 点士气。
4. **队伍规模与士气是 1 : 1，领导力是 1 : 12 / 15【实证】**。取整数解：**领导力 10 在自立情况下抵 150 人**（`15 × 10`），非自立抵 120 人。加上基数 50，非自立领导力 10、无食物、100 人的部队士气是 `120 − 100 + 50 − 30 = 40`——**离溃散只有 40 点余量，且还没算欠薪。**
5. **断粮只有 −30，不是致命惩罚【实证】**，所以「饿着赶一天路」是可接受的：**设计者故意让断粮成为一个可管理的风险，而不是一次失败。**

**【推断】** `item_get_slot(item, 1)` 是食物的**营养值**；`cf_player_has_item_without_modifier(item, 41)` 是「有此食物且未被 41 号修饰排除」。

**【未解】** ①**食物营养值不在任何随模块发行的文件里**，所以「一件 `itm_bread` 提供多少士气」不可算——**这是本模块士气的最大缺口**。②`$g_player_debt_to_party_members` 与 `calculate_player_faction_wage` 都由范围外脚本写入/定义，**欠薪项的实际数值无法在本模块内评估**。

#### 3.4.3 同伴士气读数

**【实证】** `npc_morale(troop)`：`m1 = troop_get_slot(troop, 69)`、`m2 = troop_get_slot(troop, 77)`；`raw = clamp((队伍士气 − m1 − m2 + 50) * 3 / 4, 0, 100)`。

**【实证】** 文字分档有两组：`m1` / `m2` 用 `< 3 / < 15 / < 30 / < 45`（Happy / Content / Concerned / Not happy / Miserable）；最终值用 `> 80 / > 60 / > 40 / > 20`，并对应条形图标签 `bar_enthusiastic / bar_content / bar_weary / bar_disgruntled / bar_miserable`。

**设计含义【实证】**：同伴士气是从队伍士气里**减出去**的（`− m1 − m2`），**两个槽位代表的是让这个同伴不开心的两件事**，50 是中性点。显示值再打 3/4，等于把偏差压缩——**同伴报告比真实士气「温和」25%【推断】**。

**【未解】** 谁写 troop 槽位 69 与 77，合法范围是什么。

### 3.5 工资与欠薪

工资是本模块**唯一一条平方增长的成本线**，也是「精锐化」的真正代价。

#### 3.5.1 两条互不相同的工资曲线

**【实证】** `game_get_troop_wage(troop, party)`——带领导力折扣：

```
若 troop == trp_player 或 troop == trp_kidnapped_girl:                      wage = 0   # 不再缩放
否则若 trp_kingdom_1_pretender <= troop < trp_knight_1_1_wife:              wage = 0   # 不再缩放
否则:
    level = store_character_level(troop)
    wage  = (level + 3) * (level + 3) / 25          # ← 是平方
若 troop 不在英雄区间 且 骑马:                      wage = wage * 5 / 3
若 trp_watchman <= troop < trp_mercenaries_end:    wage = wage * 3 / 2
若 trp_npc1 <= troop < trp_kingdom_1_lord:         wage = wage * 2
wage = wage * (100 − 5 * leadership) / 100
若 troop 既不是玩家、也不是被绑少女、也不在伪王区间: wage = max(wage, 1)
```

**【实证】** `npc_get_troop_wage(troop)`——不带折扣，且**英雄返回 0**：`wage = (level * level + 50) / 30`，骑马再 `× 5/4`。

**【实证】** `calculate_weekly_party_wage(party)` = Σ `npc_get_troop_wage(troop) × 堆栈人数`。

**三条设计结论【实证】：**

1. **两条曲线完全不同：`(level+3)²/25` 与 `(level²+50)/30`。** 一个是**含英雄**（`game_get_troop_wage` 只豁免玩家、被绑少女与 6 个伪王），另一个**把英雄算成 0**（`npc_get_troop_wage`）。**把两者混用或合并的重建都会算错工资。**
2. **平方就是精锐化的定价机制。** 基础项 `(level+3)²/25` 让 4 级到 28 级的工资从 1 涨到 63。
3. **`(level+3)²/25` 与社区流传的 `(level+3)×level/25` 不一致。** `RULES.md` 用原始操作码手工反查过（`assign :2 :3`、`val_add :2 3`、`val_mul :2 :2`、`val_div :2 25`），确认是**平方**，【实证】到字节码层面；**社区公式在本版本上是错的。**

## 4. 遭遇与战斗

### 4.1 设计意图

战团的战斗分两层，**两层用的规则完全不同**：

| 层 | 触发 | 判定方式 | 承载脚本 |
|---|---|---|---|
| **战役层** | 大地图上两支敌对部队接触 | 纯算术，无空间概念 | `game_event_simulate_battle` |
| **战场层** | 玩家选择亲自参战 | 逐 agent 的距离与等级抽签 | `simulate_battle_with_agents_aux` |

**设计意图【推断】：战役层负责「世界怎么演化」，战场层负责「玩家怎么体验」。** 领主之间的战争、援军消耗、攻城判断全由战役层决定，**玩家是否在场不影响结果**；玩家亲自打只是把同一场战斗的表现形式换成可操作的版本。**所以「亲自打」与「自动结算」在数学上不是同一套规则——这是重建时最容易做错的地方。**

### 4.2 战斗优势

**【实证】** `calculate_battle_advantage()`：

```
friends = party_count_fit_for_battle(p_collective_friends) + 1
enemies = party_count_fit_for_battle(p_collective_enemy) + 1      # 两边都 +1，保证比值有限
若 friends >= enemies: advantage = friends*100/enemies − 100       # ≥ 0
否则:                  advantage = 100 − enemies*100/friends       # < 0
advantage = advantage * 2
advantage = advantage + 30 * max(主队战术, 友方战术) − 30 * 敌方战术
advantage = advantage / 100                                        # 截断整除
```

**【实证】** 关键常数：**每级战术 = 30 点优势**；兵力比放大 2 倍；最后除以 100。

**设计结论：**

1. **兵力比与战术是两个可加的量【实证】**：1 点兵力比优势 ≈ 6.7 点比值，约合 1/4.5 级战术；反过来说，**战术 10 对战术 0 相当于 300 点比值优势，也就是 4 倍兵力**。**这解释了为什么「战术」在战役层是压倒性技能。**
2. **`/ 100` 是截断整除【实证】**，小的正优势会被抹成 0。**重建提示：不要悄悄改成浮点**——原实现的取整行为直接决定「同一场战斗在两台机器上是否一致」。
3. **【未解】** `qstr_Battle_Advantage_=_{` 这条消息是用**未绑定**的 `reg0` 显示的（脚本从没把值绑到那个变量）。**战场内这条提示显示什么无法确定**（`RULES.md` 未知表第 17 项）。
4. **【推断】** 两边各 +1 是除零保护。

### 4.3 伤亡抽取：谁能死、谁只能伤

**【实证】** `inflict_casualties_to_party(party, kills)`：

```
party_clear(p_temp_casualties)
fit = party_count_fit_regulars(party)         # 注意：常规兵，不含英雄
循环 kills 次：
    若 fit <= 0: 跳过本次
    stack = get_stack_with_rank(party, random(0, fit))
    troop = party_stack_get_troop_id(party, stack)
    若 random(0, 10000) < 10000 / (等级(troop) + 5):
        若 troop 是英雄:  设生命(troop, max(生命(troop) − 45, 1))
        否则若 random(0, 2) < 1:   把 troop 记入 p_temp_casualties 并标伤（部队与账本两处）
        否则:                     把 troop 记入 p_temp_casualties 并从 party 移除 1 个
        fit −= 1
```

**【实证】** 命中概率 = `1 / (等级 + 5)`：0 级 **20.0%**、5 级 10.0%、10 级 6.7%、25 级 3.3%、41 级 2.2%。常规兵**受伤 1/2、死亡 1/2**；英雄**永不死**，每次被命中掉 **45 点生命**、下限锁 **1**。

**设计结论：**

1. **等级是唯一保护【实证】**：0 级到 25 级，被打掉的概率降到 1/6。**「精锐不易损耗」是数学事实，不是观感。**
2. **英雄只能被打伤，不能被打死【实证】**，所以「英雄被俘」是战役层独有的结果（§4.5），战场层永远不会杀死英雄。
3. **注意 `fit` 只在成功命中后减 1【实证】**：**未命中的抽签不会缩小采样池**。下一次抽签的分母 `random(0, fit)` 变小，`get_stack_with_rank` 会在**缩小后的池子**里重新取秩。**重建提示：把「未命中」也当作消耗来缩小池子，实际伤亡会比原版低；反之则高。**
4. **`party_count_fit_regulars` 与 `party_count_fit_for_battle` 是两个不同的脚本【实证 + 推断】**：前者不含英雄，后者把英雄算 1，而 `inflict_casualties_to_party` 用的是前者。**两个「能战斗人数」并存，混用会同时算错战斗优势和伤亡上限。**
5. **【未解】** `random(0, 2)` 的取值约定（推断是 `{0, 1}`）；`party_count_fit_regulars`、`get_stack_with_rank` 都定义在 34 个脚本之外。

### 4.4 战后结算与士气：`count_casualties_and_adjust_morale`

这是 34 个脚本里第二长的（253 条操作），做四件事：算战斗损失比、按损失比改双方士气、给政治账本记账。

#### 4.4.1 损失权重

**【实证】** 对 `p_player_casualties` 每个堆栈：

```
numWounded = 该堆栈伤员数 ;  doubled = 2 * 堆栈人数
store_sub(:8, :6)                        # ← 见 §9.7：这里只有 2 个参数
perPerson = 等级(troop) + 3
若 troop == trp_player: level += 75
否则若 troop 是英雄:    level += 50
perPerson = perPerson * perPerson / 10
contribution = perPerson * 堆栈人数
若 troop 不是英雄: contribution = contribution * :8 / doubled     # 按健康比例缩放
playerGain += contribution
```

敌方分支用同样算术，只是 `:8 = :7 − :6`（3 参数形式）且**没有玩家的 +75 特例**；友方分支用与玩家分支相同的 2 参数形式。

**【实证】** 每人权重 = `(等级 + 3)² / 10`；英雄加成 **+75（玩家）/ +50（其他英雄）**。

**【未解】重要。** 按已解码的排布，`+75` / `+50` 加进的是 `level`，而 `perPerson` **在此之前**就已从 `level + 3` 算好，之后也只用 `perPerson` 自乘。**因此这两条英雄加成看起来不参与最终数值**——可能是死代码，也可能只是反编译渲染顺序造成的假象，**本模块无法判定，需要运行时探针**（见 §10）。

#### 4.4.2 士气增减

**【实证】** 续：

```
totalGain = (playerGain + allyGain) * 100
lossRatio = (enemyCount > 0) ? totalGain / enemyCount : 1000      # 1000 是「没有敌人」的哨兵值
moraleDelta = (敌方不是据点) ? 60 − lossRatio : 100 − lossRatio
若 moraleDelta < 0: moraleDelta /= 2
moraleDelta = max(moraleDelta, −60)
moraleDelta = moraleDelta * enemyCount / 100

enemyMoraleGain   = moraleDelta * −1
playerMoraleDelta = moraleDelta * $g_strength_contribution_of_player / 100
```

**【实证】** 若敌方仍活跃：

```
enemyPopulation = 10 + Σ 敌主队堆栈人数 + Σ 各附属部队 (10 + Σ 堆栈人数)
set_fixed_point_multiplier(100) ; root = sqrt(enemyPopulation * 100) / 100
enemyMoraleGain /= root * 4                                       # 平方根阻尼 + 1/4
change_party_morale(敌主队, enemyMoraleGain * initial / finalPopulation)
对每个附属部队: change_party_morale(附属, enemyMoraleGain * 它的规模 / finalPopulation)
change_player_party_morale(playerMoraleDelta / shares)
```

**【实证】** 常数：野战场合基数 **60**、据点场合 **100**；负值减半；下限 **−60**；阻尼 **1/4**；`set_fixed_point_multiplier(100)` 是模块系统做整数开方的标准手法。

**设计结论：**

1. **平方根阻尼 + 初始/最终人口比，共同实现「小部队的伤亡更痛」【实证】**。⇒ 同样损失 10 人，对 20 人部队的士气打击远大于对 200 人部队。**这正是「骚扰式打法」的数学基础【推断】**——反复给大部队制造小伤亡，士气收益递减但永远为正；反过来大部队打小部队，一次就能把小部队压垮。
2. **「打据点」的士气基数比野战高 40 点（100 : 60）【实证】**——攻下据点对防守方是更重的打击。
3. **士气变化会同时施加给敌方主队与它的每个附属部队，按规模分摊【实证】**。⇒ **附属部队（援军、巡逻队）不是装饰，它们会分担母队的士气变化。**

**政治后果【实证】**：

```
influence = min(enemyCount * $g_strength_contribution_of_player / 8, 2000)
若 $g_ally_party >= 0:            faction_get_slot(盟友阵营, 99) += (influence / 3) * 2
若 敌方不活跃 且 $current_town >= 0:
    influence *= 2
    faction_get_slot(城镇阵营, 99) += influence
否则若 敌方活跃 且 玩家没有领导 fac_player_supporters_faction:
    faction_get_slot(敌方阵营, 99) −= (influence / 3) * 2
```

**【推断】** faction 槽位 `99` 是一本**每阵营的「战争贡献账本」**（友军加、敌军减）；槽位 `11` 是阵营的**领袖兵种**（用是否等于 `trp_player` 判断玩家是否自立为王）；槽位 `8` 是**元帅**（`game_event_simulate_battle` 读它判断元帅是否战败）。

**【未解】** faction 槽位 98/99 的合法范围；`$any_allies_at_the_last_battle`、`$g_ally_party`、`$g_strength_contribution_of_player` 都由范围外脚本写入。

### 4.5 战役层裁决：`game_event_simulate_battle`

396 条操作，是 34 个脚本里最长的。执行顺序：

**1) 记账**【实证】——清 `$marshall_defeated_in_battle`，给每支部队写槽位 `68 = store_current_hours()`（战斗开始时刻）。

**2) 合法性**【实证】——任一方不活跃，或**双方关系 ≥ 0**，战斗不发生。

**3) 取消**【实证】——`$g_battle_simulation_cancel_for_party` 指名任一方则取消；若 `$g_battle_simulation_auto_enter_town_after_battle` 为真，把玩家移进据点。

**4) 汇合**【实证】——附属部队折进 `p_collective_ally` 与 `p_collective_enemy`。

**5) 强度比较与减员**【实证】：

```
allyStrength  = clamp(party_calculate_strength(p_collective_ally) / 20, 1, 50)
enemyStrength = min(party_calculate_strength(p_collective_enemy) / 20, 50) + 1
若任一方类型是 2 或 3:               # 城镇或城堡在防守
    allyStrength  = allyStrength  * 123 / 100
    enemyStrength = enemyStrength * 100 / 123
# 只有夜里才直接施加减员
若 遭遇对象是城镇/村庄 且 夜晚 且 敌方兵力 > 0:
    inflict_casualties_to_party_group(g_enemy_party, allyStrength, p_temp_casualties)
若是夜晚:
    enemyFit = party_count_fit_for_battle(p_collective_enemy)
    若 enemyFit > 0: inflict_casualties_to_party_group(p_collective_ally, enemyStrength, p_temp_casualties)
allyFit = party_count_fit_for_battle(p_collective_ally)
若 enemyFit == 0 或 allyFit == 0: → 判定胜者、处理英雄与据点
```

**【实证】** 常数：强度除数 **20**、上限 **50**、据点攻防不对称 **123/100**。

**设计结论：**

1. **据点防守方 `×123/100`、进攻方 `×100/123`【实证】**，即防守方相对获得约 **1.51 倍**强度优势（`1.23 ÷ 0.81`）。⇒ **强攻据点的兵力门槛约为野战的 1.5 倍。这是「据点难攻」的算术来源。**
2. **减员只在夜晚生效【实证】**——白天发生战役层接触时不直接死人。**这解释了原游戏里「白天遭遇往往僵持、夜里才决出胜负」的手感。**
3. **敌人强度无条件 `+1`，盟友强度先钳后取 `max(…, 1)`【实证】**⇒ 两支零强度部队相遇时盟友仍能以 1 对 1，胜负取决于后面的随机与援军。

**6) 英雄俘虏判定**【实证】：

```
对败方每个英雄：remove_troop_from_prison(hero) ; troop_set_slot(hero, 10, −1)
若 random(0, 100) >= 70:                    # 30 % 被俘
    胜方 +1 名俘虏 ; troop_set_slot(hero, 8, 俘虏方) ; 显示 "hero taken prisoner"
    若 cf_prisoner_offered_parole(hero): 胜方领袖与该英雄关系 +3 ; $total_battle_enemy_changes += 3
    否则:                                胜方领袖与该英雄关系 −5 ; $total_battle_enemy_changes += −5
    写 update_troop_location_notes_prisoned(hero, 俘虏阵营)
否则: 显示 "{s1} of {s3} was defeated …"     # 逃脱
```

**【实证】** 常数：**捕获门槛 70（即 30% 概率）**；**假释 +3 / 拒绝 −5**。

**设计结论**：英雄战败有 **70% 概率只是逃脱【实证】**，**所以战役层的胜负很少真正削掉对方的英雄资源——长线战争必然打成消耗战而不是斩首战**。「是否假释」由 `cf_prisoner_offered_parole` 决定（范围外脚本 **【未解】**），而两种结果的关系差是 **8 点**（+3 对 −5），**假释与否是一次不可忽视的外交决策**。

**7) 元帅检测**【实证】——若被击败的英雄所属阵营是王国（`fac_player_supporters_faction <= faction < fac_kingdoms_end`）且该阵营槽位 `8` 就是他，则 `$marshall_defeated_in_battle = hero`、`$g_recalculate_ais = 1`。

**8) 释放俘虏、占领据点、繁荣度**【实证】——被打下的据点调用 `battle_political_consequences`，写 `faction_set_slot(faction, 98, 当前小时)`，**非城堡**还要 `change_center_prosperity(centre, −5)` 且 `$newglob_total_prosperity_from_townloot += −5`。

**设计结论【实证】：攻下城镇或村庄会让它变穷 5 点繁荣度，城堡不吃这一刀。** ⇒ 设计者认为**城堡是军事资产（占下来就赚），城镇/村庄是经济资产（占下来先亏）**，与 §8 里城堡不参与物价模型是同一个设计方向。

**9) 战后升级**【实证】——类型为 `13` 的部队走 `upgrade_hero_party(party, budget)`，初始预算 **200**，由 `game_get_reduce_campaign_ai` 缩放：0 → `×3/2`、1 → 不变、2 → `/2`。

**10) 攻城决断**【实证】（操作 368–392）——对进攻方，比较 `13/10 × 防守方驻军槽位` 与 `进攻方槽位 56 + 57 + 59`，并以 `random(0, 100) < 15` 掷骰决定是否强攻。

**设计结论【实证】：攻城是「兵力够 1.3 倍 + 15% 概率」才发生的。** ⇒ 15% 的骰子意味着**即使兵力充足，AI 也常常围而不攻**——这解释了为什么原游戏里围城会拖很久。

**【未解】** `party_calculate_strength`、`game_get_reduce_campaign_ai` 都是引擎操作，**输出范围不随模块发行**，所以「多少兵力算 50 强度上限」无法在本模块算出；`$battle_simulation_*` 系列全局变量也由范围外脚本写入；**`13/10` 这个攻城比的完整含义在任何随模块发行的数据里都没有文档**。

### 4.6 战场层：自动结算与撤退

#### 4.6.1 `simulate_battle_with_agents_aux(side, damageScale)`

**【实证】**

```
对 side 上每个「待模拟」的 agent A（agent_slot(A, 3) == 1）：
    target = 对面的最近存活人类 agent（$pin_player_fallen == 0 时排除玩家）
    若 target < 0: 跳过
    distance = 距离(A, target) + 3000
    shots    = 18000 / distance * 2
    shots    = shots * 攻击方职业系数 / 目标方职业系数 + 目标方职业加成
    damageChance = damageScale + (等级(target) − 等级(A)) / 5
    若 A 是玩家: damageChance /= 2
    重复 shots 次: 若 random(0, 100) < damageChance: agent_deliver_damage_to_agent(target, A)
# 记账：归入 p_temp_party（side 0）或 p_temp_party_2（side 1），受伤标记为伤
```

**【实证】** 常数：距离偏移 **3000**、基数 **18000**、**×2**、等级差除数 **5**、玩家 **÷2**；职业 1 → 目标加成 = 2，职业 2 → 攻击系数 = 2。

**设计结论：**

1. **`shots ∝ 1 / 距离`【实证】**——近战能打出的次数远多于远距离，**距离本身就是输出量**。
2. **等级差通过 `/5` 直接改命中率【实证】**：等级差 10 = 命中率差 2 点。⇒ **等级优势在战场层是「概率」而不是「伤害」**，与战役层的 `1/(等级+5)` 相比温和得多。
3. **玩家本人的命中率被砍半【实证】**（`damageChance /= 2`）。**这是一个相当罕见的设定：玩家在「自动结算」里的输出被刻意压低，把玩家推向「亲自下场打」。**
4. **【未解】** 场景距离单位（`18000 / (d + 3000)` 的形状与厘米一致，但没有文件说明）；`agent_deliver_damage_to_agent` 内部伤害模型。

#### 4.6.2 `simulate_retreat(param1, param2, param3)`

**【实证】**

```
对每个存活人类 agent A：agent_set_slot(A, 3, 1) ; value = 等级(A) + 5 + (英雄再 +5)
    value 累加进 allyLevelSum 或 enemyLevelSum
若 $pin_player_fallen == 0 且 不是 (enemyLevelSum >= allyLevelSum) 且 param3 == 1: doRetreat = 0
若 doRetreat:
    $g_last_mission_player_damage = 0 ; party_clear(p_temp_party) ; party_clear(p_temp_party_2)
    simulate_battle_with_agents_aux(0, param1) ; simulate_battle_with_agents_aux(1, param2)
    … 用 p_temp_party / p_temp_party_2 拼出伤亡对话 …
# 士气惩罚
若 (allyDead + enemyDead) > 0:
    share = (allyDead * 100 / (allyDead + enemyDead)) * allyDead / allyTotal
    change_player_party_morale(share * −30 / 100)
```

**【实证】** 常数：英雄在比较里额外 **+5**；士气系数 **−30**，作用在 `(友军占阵亡比例) × (友军损失比例)` 这个复合量上。

**设计结论：**

1. **撤退与否取决于「双方等级总和」的比较，而玩家在场时（`$pin_player_fallen == 0`）逻辑会反转【实证】**。⇒ **玩家在场这件事会改变撤退判定，这是「玩家亲自参战」与「旁观」在结果层唯一的显式差别。**
2. **撤退的士气代价是双重比例的乘积【实证】**：既要「死的人里有多少是自己人」，又要「自己人里死了多少」。**惩罚因此不线性**——一支小队死了 2 人（占比高、损失率高）可能和一支大队死 20 人扣一样多。
3. **【未解】** `$pin_player_fallen` 的写入者；`param1/2/3` 的含义（它们直接当伤害缩放传给 `simulate_battle_with_agents_aux`）。

#### 4.6.3 战术调度与战斗结束清理

**【实证】** `select_battle_tactic()`：判断场上 AI 队伍数（`num_active_teams_le(2)`），决定 `$ai_team_1 / $ai_team_2`；第一队用 `select_battle_tactic_aux($ai_team_1, 0)` 选战术，第二队在**第一队选了战术 1 时**传入 `counter = 1` 去选克制战术。`battle_tactic_apply()` 把选好的战术交给 `battle_tactic_apply_aux` 执行。

**【未解】** 战术枚举本身、`select_battle_tactic_aux` 与 `battle_tactic_apply_aux` 的逻辑（都不在 34 个脚本内）。**所以「AI 会选哪些战术、怎么克制」在本文里无法给出。**

**【实证】** `game_event_battle_end()` 遍历所有同伴英雄（`trp_npc1` … `trp_knight_1_1_wife`），对每个「本场参战」的英雄（troop 槽位 2 == 2）：若它的 troop 槽位 10 指向一个不活跃或已不含它的部队，清成 `−1`；若它是俘虏（troop 槽位 8）而捕获者已消失，就地释放（治疗、清俘虏标记），然后按 **`p_main_party` → 其他英雄的部队 → 城镇** 的顺序找一个**有位置且不敌对**的容器，写回槽位 8 与 10。

**【推断】** troop 槽位 `2` = 「本场参战」标记（`== 2`）；槽位 `8` = **捕获者部队**；槽位 `10` = **所在部队**——8 与 10 都被 `game_event_simulate_battle` 独立写过一次，互相印证。

**设计含义【推断】：这是一个「防挂空引用」的收尾脚本**，处理「英雄的捕获者被消灭了，俘虏该去哪」这种边缘状态。**任何重建都必须实现它**，否则会出现「英雄属于一支不存在的部队」这种存档。

## 5. 招募与升级

### 5.1 设计意图

这一节是核心循环的**唯一正向环**：玩家的兵力从哪里来、怎么变强、代价是什么。

| 来源 | 落点 | 代价 |
|---|---|---|
| 村庄招募 | `village_recruit_volunteers_recruit` | **10 金币/人【实证】** |
| 战场升级 | 升级图 + `game_get_upgrade_cost` | 每级 10…200 金币 **【实证】** |
| 雇佣兵 | `trp_watchman..trp_mercenaries_end` 区间 | 周薪 27…76 **【实证】** |

**设计意图【推断】：三条来源的「时间尺度」不同。** 招募是按天刷新的稀缺资源，升级是无限但昂贵的一次性投入，雇佣兵是即买即用的现金换战力。**玩家在不同阶段被迫切换主来源**，这就是「早期靠招募、中期靠升级、后期靠雇佣兵填坑」的节奏来源。

### 5.2 村庄招募

**【实证】** `village_recruit_volunteers_recruit()`（8 条操作）：

```
troop = party_get_slot($current_town, 92)          # 可招兵种
count = min(party_get_slot($current_town, 93),    # 可招数量
            party_get_free_companions_capacity(p_main_party),
            troop_get_gold(trp_player) / 10)
party_add_members(p_main_party, troop, count)
party_set_slot($current_town, 93, −1)              # 标记已招
troop_remove_gold(trp_player, count * 10)
```

**【实证】** 常数：**每人 10 金币**；数量被**队伍空位**与**`金币/10`** 双重钳制；槽位 93 写 **`−1`**（不是 0）作为「今天已招」的标记。

**设计结论：**

1. **招募同时受限「钱」与「编制空位」【实证】**⇒ 玩家花钱扩容（或升领导力）与攒钱同等重要，两条线都不能偏废。
2. **`−1` 而不是 `0`【实证】**：条件脚本检查的是 `>= 0`。**若实现成 0，一个「今天已招」的村庄会被误判为「可招 0 人」而不是「今天不可招」**，导致菜单显示错误。这是一处极容易做错、且只在 UI 上可见的细节。
3. **【推断】** 槽位 `92` = 可招兵种 id、槽位 `93` = 可招数量，两者都由范围外脚本写入（村庄每天刷新志愿者池），**所以「一个村庄一天刷几个人」在本文里无法给出。**

**【实证】** `cf_village_recruit_volunteers_cond()` 的全部条件：

```
party_slot($current_town, 35) != 2 且 != 1 且 party_slot($current_town, 39) < 1
standing = party_get_slot($current_town, 26) >= 0
( standing >= 5 或 据点阵营 == $players_kingdom
  或 store_relation(据点阵营, fac_player_faction) >= 0
  或 据点阵营 == $supported_pretender_old_faction
  或 $players_kingdom == fac[0] )                        # ← 五个条件是一个 OR
party_slot($current_town, 93) >= 0 且 party_slot($current_town, 92) >= 1
```

**【实证】** 中间那组五个条件是 `this_or_next` 前缀连成的**一个 OR**。

**设计结论【推断】：招募有两条门槛**——**地方声望门槛**（`standing >= 5`，或据点跟玩家/玩家支持的伪王关系够好，或**玩家还没有国家**）；**两条状态封锁**（槽位 35 为 `1` 或 `2`、槽位 39 `>= 1` 时不能招）。其中 `$players_kingdom == fac[0]` 即 `fac_no_faction`，**「玩家还没有立国」是一张无条件通行证**——这是给新手期的保护。**一旦立国，玩家就失去了这张免费通行证**，招募开始真正依赖声望与外交。

**【未解】** 槽位 35 与 39 的名字与合法范围；谁写它们。

> **重要元数据（引用时务必保留）**：`culture_troops.json` 自己声明，其中**城镇分组是「公开的游戏知识」，与发行的城镇列表及其地理一致，但不是从任何发行文件还原的。**

**【实证】** `game_get_upgrade_xp(troop)`：

```

reg0 = reg0 * 6 / 1000 + 30
若 trp_bandit <= troop < trp_black_khergit_horseman: reg0 = reg0 * 2      # 匪帮翻倍
```

**【实证】** 常数：`+3` 级偏移、`6/1000` 缩放、`+30` 下限、匪帮 **×2**。

**手工反查【实证】**：`RULES.md` 用原始操作码独立复核过这一段（操作 0–13），确认：①操作 3 是一条**单独的** `store_add`（`0x0848`，三操作数 `:1, :2, 3`），不是 assign 与 add 的融合——**甜化渲染器没有凭空造第四个操作数，也没有合并相邻操作**；②操作 10 的 `neg|` 位（`0x80000000`）与 `this_or_next` 位（`0x40000000`）写在**同一个字**里，所以 `try_begin` 块里两个条件是**合取**。⇒ 规则确定为 `upgradeXP = levelBoundary(level+3) × 6 / 1000 + 30`，匪帮翻倍。

**设计结论：匪帮的经验收益是双倍【实证】**——这是设计者第二条鼓励剿匪的机制（第一条是 §5.3 的兵源）。**剿匪在战团里不是支线，它是主循环的一部分。**

**【未解】** `get_level_boundary` 是**引擎操作码**，它返回达到某等级所需的累计经验，但**经验曲线本身不在任何随模块发行的数据文件里**。⇒ `game_get_upgrade_xp` 的具体数值无法在本模块算出。**重建必须自己提供一条曲线，这个公式才会表现一致**（`RULES.md` 未知表第 1 项）。

### 5.6 战后的经验与金币

**【实证】** `party_give_xp_and_gold(party)`：

```
shares = calculate_main_party_shares()
xpPool = Σ over 败方非英雄堆栈: (等级 + 10)² / 10 * 堆栈人数
xpPool = xpPool * $g_strength_contribution_of_player / 100
xpPool = min(xpPool, 40000)
party_add_xp(p_main_party, xpPool * random(50, 100) / 100)
goldPerHero = min(xpPool * 10, 60000) * random(50, 100) / 100 / shares
对主队每个英雄堆栈: troop_add_gold(hero, goldPerHero)
```

**【实证】** 常数：每人值 **`(等级 + 10)² / 10`**；经验上限 **40000**；金币倍率 **×10**；金币上限 **60000**；**±50% 随机**（`random(50, 100) / 100`）。

**设计结论：**

1. **经验与金币来自同一个 `xpPool`，金币是经验的 10 倍后再封顶【实证】**⇒ 一次战斗最多给 **60000 金币**。参照 §5.4 的升级费（10…200），**上限意味着「打一场大仗能顶几百次升级」**，但也意味着**收益在超过 40000 经验池后完全不再增长**（两个上限同时生效）。
2. **`(等级 + 10)² / 10` 也是平方【实证】**⇒ **打精锐敌人的收益是超线性的**：20 级给 `30²/10 = 90`，10 级给 `20²/10 = 40`，等级翻倍收益翻 2.25 倍。
3. **±50% 的随机【实证】**：`random(50, 100)/100` 落在 `[0.50, 1.00)`——这是个**纯扣减**的随机，不是「有时多有时少」。**同样的战斗，收益最多相差一倍。**
4. **金币只发给英雄【实证】**：`goldPerHero` 给主队的**每个英雄堆栈**。⇒ 玩家的收入与队伍里的英雄数量线性相关，**带更多同伴不只是战力，也是收入。**

**【未解】** `$g_strength_contribution_of_player` 由范围外脚本写入，它**同时缩放战利品、经验、金币和士气**（§4.4、§5.6、§6.6）——**这是整个模块里影响面最广的一个未知量**（`RULES.md` 未知表第 4 项）。**【推断】** `random(a, b) / 100` 的边界约定（`b` 开区间）是从模块内一致用法推断的。

## 6. 交易与物价

### 6.1 设计意图

经济系统的目标不是「让玩家赚钱」，而是**把地理变成收益**。整个物价模型建立在一个反直觉的起点上：

> **每种交易品在全世界有一个固定的基准价 `1000`，而系统会持续把各地价格往这个基准上拉。**

这意味**不存在「某地永久便宜」**。利润的唯一来源是**信息差与时间差**：必须在价格被拉回基准之前把货运到。

### 6.2 交易惩罚 `get_trade_penalty(item)`

**【实证】**（43 条操作）

```
若 itm_spice <= item < itm_siege_supply:  penalty = max(12 − 1 * skl_trade, 3)     # 交易品
否则:                                     penalty = 100 − 5 * skl_trade             # 其他商品

modifier = 1000
若 p_town_1 <= 据点 < p_salt_mine:                     # [21, 201)：所有据点，含城堡
    standing = party_get_slot(据点, 26)
    modifier += (−3) * standing
    若 standing < 0: modifier = modifier * (100 − standing) / 100
若 玩家与 g_talk_troop 的关系 < 0: modifier += 20 * (−关系)
若 p_village_1 <= 据点 < p_salt_mine: penalty = penalty * 5 / 4     # [91, 201)：只含村庄
penalty = max(penalty * modifier / 1000, 1)
```

**【实证】** 常数：交易品底数 **12**、每级交易 **−1**、下限 **3**；普通商品底数 **100**、每级 **−5**；修正基数 **1000**、声望 **−3/点**、负面关系 **20/点**、村庄加价 **×5/4**。

**设计结论：**

1. **交易品与普通商品是两套完全不同的定价【实证】**：交易品是 **12 − 交易技能**（3…12），普通商品是 **100 − 5×交易技能**（50…100）。⇒ **交易技能对普通商品的影响（每级 −5）远大于对交易品（每级 −1）**，但普通商品底数是 100，所以**交易技能真正的作用是「让买卖装备不再被抽 100% 的税」，而不是「让跑商更赚」。**
2. **两个范围测试覆盖的集合不同，而这个差异是有意的【实证】**：操作 16 的测试是 `[21, 201)`（**含城堡**），操作 36 的测试是 `[91, 201)`（**只含村庄**）。⇒ **城堡能拿到槽位 26 的价格修正，但拿不到 `×5/4` 的村庄加价。** 对照 §6.4：`update_trade_good_prices` 的城镇测试会**跳过城堡**。**两个脚本对「城堡算不算据点」的处理不一致——这是原代码的真实行为，不是本文的简化。**
3. **村庄加价 25%【实证】**⇒ **在村庄卖东西永远比在城镇亏**，这是数据里唯一一处「村庄更差」的显式定价。
4. **地方声望槽位 26 是非对称的【推断】**：正值每点减 3 点修正（线性），负值还要**额外**乘 `(100 − standing)/100`。⇒ **声望为负时惩罚增长是超线性的**，声望 −50 会把修正放大到 `(1000 + 150) × 1.5 = 1725`。

**【实证】** 按上式算出的实际取值：

| 维度 | 取值 → 惩罚 |
|---|---|
| `skl_trade` 0 / 5 / 10，城镇·交易品 | 12 / 7 / **3**（技能 9 即触底） |
| `skl_trade` 0 / 5 / 10，村庄·交易品 | 15 / 8 / **3** |
| `skl_trade` 0 / 5 / 10，城镇·普通商品 | 100 / 75 / 50 |
| 地方声望 −50 / −30 / −10 / 0 / 10 / 40 | **20** / 17 / 13 / 12 / 11 / 10 |
| 对话关系 −100 / −50 / −20 / −10 / −1 / 0 | **36** / 24 / 16 / 14 / 12 / 12 |

**【实证】** 交易品下限 3 在技能 9 就触底（`12 − 9 = 3`）⇒ **交易技能超过 9 对交易品毫无意义**（但对普通商品仍有意义，它到技能 10 才到 50）。**这是一处很容易被误解的技能收益断点。**

### 6.3 买卖价因子

**【实证】**

```
买：factor = 100
    若据点∈{城镇,村庄} 且 物品是交易品: factor = party_get_slot(据点, (item − itm_spice) + 250) * 100 / 1000
    factor = factor * (100 + penalty) / 100
卖：factor = 100
    若据点∈{城镇,村庄} 且 物品是交易品: factor = party_get_slot(据点, (item − itm_spice) + 250) * 100 / 1000
    否则: penalty = penalty * 4                    # ← ×4 只走非交易品的分支
    factor = factor * 100 / (100 + penalty)
```

**这条不对称是本模块经济系统最重要的发现【实证】：买入路径除以 `100`，卖出路径除以 `100 + penalty`；`×4` 的惩罚放大只在物品不是交易品时生效。**

**【实证】** 直接算出的价因子：

| `skl_trade` | 杂货买 | 杂货卖 | 交易品（基准价）买 | 交易品（基准价）卖 |
|---|---|---|---|---|
| 0 | **200%** | **20%** | 112% | 89% |
| 5 | 175% | 25% | 107% | 93% |
| 10 | 150% | 33% | 103% | 97% |

**设计结论：**

1. **无技能时装备买双倍价、卖两成价【实证】**，买卖价差 **10 倍**。⇒ **这是「不要买装备、去捡」这条强烈手感的算术来源。**
2. **交易品的买卖价差极小（112% : 89%，约 1.26 倍）【实证】**⇒ **交易品才是真正的生意**，装备只是消耗品。
3. **交易品的价格几乎完全由「据点本地价格槽位」决定【实证】**：`slot = item − itm_spice + 250`，即槽位 **250…283**（34 个交易品各占一个槽）。⇒ **跑商赚多少，取决于各地槽位 250–283 的当前值，而不是物品表里的 `value`。**
4. **`1000` 是交易品的规范基准价【推断】**：买入把它除成 100，卖出用 `value/1000` 换算。**物品表里的 `value`（30…1025）与槽位里的 250…283 是两个不同的量。**

> **陷阱提示**【实证】：**一个无条件套用 `×4` 的重建会把交易品价格算错。** 这是 `RULES.md` 特意标出的「单条最重要的经济发现」。

**【实证】** 交易品范围是 `itm_spice`(91) ≤ item < `itm_siege_supply`(125)，即 **34 个物品**，与槽位基址 `250 + (item − itm_spice)` = **250–283** 完全对齐。

### 6.4 价格的自我平衡 `update_trade_good_prices()`

**【实证】** 两阶段模型：

```
# 阶段 1：逐据点刷新（城镇与村庄；跳过城堡）
for centre in p_town_1 .. p_salt_mine: 若是城镇或村庄: update_trade_good_price_for_party(centre)

# 阶段 2：按交易品逐个全局再归一
for good in itm_spice .. itm_siege_supply:
    先算（不写）: weightedSum = Σ price * weight ; weightTotal = Σ weight      # 城镇 5，村庄 1
    再统一写回:   price = clamp(party_get_slot(centre, good + 250) * 1000 * weightTotal / weightedSum, 100, 10000)
```

**【实证】** 权重：**城镇 5、村庄 1**；基准 **1000**；钳制 **[100, 10000]**；槽位基址 **250**；城镇区间 `[21, 43)`、村庄区间 `[91, 201)`。

> **城堡落在两个区间之间的空隙里（`p_castle_1` … `p_village_1 − 1`，即 `[43, 91)`），因此阶段 1 与阶段 2 都跳过城堡。⇒ 战利品与贸易价格是一个「只有城镇和村庄」的模型；城堡不维护任何交易品价格槽位。**

**设计结论：**

1. **阶段 2 的代数是在把各地价格往「加权均值 = 1000」上拉【推断】**：`price × 1000 × Σw / Σ(w·price)` 会把每个据点重标定，使加权平均价正好等于 1000。⇒ **`1000` 就是设计者定义的交易品基准价。**
2. **钳制 `[100, 10000]` ⇒ 相对基准的偏离上限是 10 倍【实证】**——这是价格波动的硬边界。
3. **城镇权重 5、村庄权重 1【实证】**⇒ 城镇对全局均值的影响是村庄的 5 倍，**城镇主导定价权**，并让「在小村庄捡漏」在经济上可行（村庄被拉回均值的力量只有城镇的 1/5）。
4. **阶段 1 与阶段 2 都是「先算后写」的分离循环【实证】**⇒ **这是必要的**：若边算边写，先被写入的据点会污染后面的加权和，结果依赖于遍历顺序。
5. **【实证】** 权重分支可无歧义读出：能走到 `else_try` 的据点必然是村庄，因为外层条件已把城镇与村庄以外的全部排除。

**【未解】** 这个脚本的运行周期（调用它的触发器不在 34 个脚本内）⇒ **「价格一天漂移多少」无法计算。**

### 6.5 价格的空间扩散 `average_trade_good_prices()`

**【实证】**

```
for centreA in p_town_1 .. p_castle_1:                 # 只遍历城镇
    若 centreA 是城镇或村庄:                            # 操作 2–3 重新测 centreA：此处恒真
        for centreB in p_town_1 .. p_salt_mine:        # centreB 没有类型测试
            若 centreB 是城镇或村庄 且 centreB != centreA:
                distance = store_distance_to_party_from_party(centreA, centreB)
                若 distance < 50:
                    rate = 50 − distance
                    for good in itm_spice .. itm_siege_supply:
                        delta = priceA − priceB ; move = delta * rate / 1000
                        party_set_slot(centreB, slot, priceB + move)
                        party_set_slot(centreA, slot, priceA − move)
```

**【实证】** 半径 **50**、速率分母 **1000**、槽位偏移 **`250 − itm_spice`**。

**【实证】一处值得原样复刻的发行缺陷**：内层循环的类型测试（操作 5–6）读的是 `:1`（centreA），而周围逻辑显然想读 `:2`（centreB）。因为 `:1` 已被外层循环约束，这个测试是**恒真式**，所以 **centreB 完全没有被类型过滤**。又因 `p_town_1`、`p_castle_1`、`p_village_1`、`p_salt_mine` 连续编号，`centreB` 会**同时遍历城镇、城堡和村庄**。

> **⇒ 城堡会作为被动方（B 侧）参与价格扩散，尽管 `update_trade_good_prices` 跳过了它们。一个按类型过滤 centreB 的重建会与原版产生偏差。**

**设计结论：**

1. **这是一个真正的收敛步骤【实证】**：每次按 `(50 − distance)/1000` 的比例同时抬高 B、压低 A 相同的量。
2. **距离 1 单位的两地每次收敛 4.9%，距离 49 单位的每次收敛 0.1%【实证】**⇒ **价格差异的寿命约为「1 / 收敛率」次调用**：相邻两地约 20 次调用后趋于一致，远距离两地要约 1000 次。**这是「跑商必须跑远路」的算术来源——近处的价差会自己消失。**
3. **【推断】** `distance` 的单位是战役地图距离单位（`store_distance_to_party_from_party`）。

**【未解】** 这个脚本的运行周期。

### 6.6 战利品 `party_calculate_loot(party)`

**【实证】** 四段结构（常数：战利品物品槽 **110–114**、数量槽 **115–119**、金币槽 **109**；部队类型 **11 / 18 / 15**；基础 **300**、每人 **30**、掠夺偏移 **+10**）：

```
(a) 把敌方的战利品槽 110–114 搬进 trp_temp_troop（数量取自 115–119），清空槽 109
(b) 只有 部队类型 ∈ {11, 18, 15} 才走商品掷骰：
    amount = 300 * $g_strength_contribution_of_player / 100 / shares
    类型 11: reset_item_probabilities(100); goods = itm_spice .. itm_siege_supply       # 满额
    类型 18: amount /= 2; reset_item_probabilities(1); goods = itm_smoked_fish .. 125   # 减半
    类型 15: amount /= 5; reset_item_probabilities(1); goods = itm_smoked_fish .. 125   # 五分之一
    for good in goods:
        price = (类型 != 18) ? party_get_slot(g_enemy_party, good + 250) : (10000 + 1000) / 3   # = 3666
        set_item_probability_in_merchandise(good, 100 * 1000 / price)
    troop_add_merchandise(trp_temp_troop, 11, amount)
(c) 每个被击败的常规兵的个人战利品：
    lootPerMan = 30 * $g_strength_contribution_of_player * (skl_looting + 10) / 10 / shares
    对败方每个非英雄堆栈的每个兵: troop_loot_troop(trp_temp_troop, 该 troop, lootPerMan)
(d) 数出实际产出：trp_temp_troop 里每个 >= 0 的栏位使 totalLootValue += 1
```

**设计结论：**

1. **战利品分「商品」和「个人物品」两条独立路径【实证】**：只有**匪类部队（类型 11/18/15）**才走商品掷骰，其他敌人只给个人物品。
2. **个人物品产量由掠夺技能线性放大【实证】**：掠夺 0 时是 1.0 倍，掠夺 10 时是 **2.0 倍**⇒ **掠夺 10 让战利品翻倍**，这是它「每级 +10%」说明的算术来源。
3. **`÷1` / `÷2` / `÷5` 的三档差异【实证】**：类型 11 拿满额 300 并用**全部交易品**范围，类型 18 减半，类型 15 减到五分之一。⇒ **「打的敌人种类」直接决定战利品档次，类型 11 是最好的目标。**
4. **`probability = 100 × 1000 / price`【实证】**：物品越贵、出现概率越低⇒ **战利品是按价值反比抽的**，所以「打一场大仗必出好东西」不成立。
5. **类型 18 用固定价 3666【实证】**，其他类型读据点价格槽⇒ 类型 18 的战利品抽签**不受地方经济影响**。

**【推断】** 类型 `11` 读作**匪帮/劫掠者部队**（用全部交易品范围 + `reset_item_probabilities(100)`）；`18` 与 `15` 是较弱的部队（战利品减半/五分之一 + 便宜的食物范围 + `reset_item_probabilities(1)`）。

**【未解】** `reset_item_probabilities` 与 `set_item_probability_in_merchandise` 的**具体加权规则**（引擎操作）⇒ 战利品成分只能部分确定（`RULES.md` 未知表第 11 项）；`$g_strength_contribution_of_player`（§5.6）。

### 7.3 关系刻度：×100 的坑

**【实证】** `factions.txt` 里的关系是**浮点数**（`"%f"` 格式），而**脚本读到的是 ×100 的整数**：`−0.150000` → **`−15`**；`+0.500000` → **`+50`**；`+0.900000` → **`+90`**。

**这是一处必须实现正确的换算【实证】。若把浮点值直接塞进整数关系里，所有外交判断都会退化成 0（全部中立），整个战争系统会静默失效。**

**【实证】** 关键关系对（原始 → ×100）：

| 关系对 | 原始 | ×100 | 关系对 | 原始 | ×100 |
|---|---|---|---|---|---|
| `fac_no_faction` → 自身 | +0.90 | **+90** | `fac_outlaws` → `fac_player_faction` | −0.15 | **−15** |
| `fac_commoners` → `fac_outlaws` | −0.60 | **−60** | `fac_outlaws` → `fac_kingdom_1..6` | 各 −0.05 | **各 −5** |
| `fac_commoners` → `fac_undeads` | −0.70 | **−70** | `fac_dark_knights` → `fac_innocents` | −0.90 | **−90** |
| `fac_culture_N` → 自身 | +0.90 | **+90** | `fac_dark_knights` → `fac_player_faction` | −0.40 | **−40** |
| `fac_outlaws` → 自身 | +0.50 | **+50** | `fac_player_faction` ↔ `fac_player_supporters_faction` | +1.00 / +0.90 | **+100 / +90** |
| `fac_outlaws` → `fac_commoners` | −0.60 | **−60** | `fac_outlaws` → `fac_merchants` / `fac_manhunters` | −0.50 / −0.60 | **−50 / −60** |

2. **`fac_outlaws` 对自己的关系是 +50【实证】**，不是 +100⇒ **匪帮内部也互不信任**，这是一个明显有意为之的细节。
3. **各国之间的关系基本都是 0【实证】。** 唯一有内容的行是 `fac_kingdom_1`（斯瓦迪亚）：对 `fac_kingdom_2`(16) **+90**，对 `fac_kingdom_3`(17) / `fac_kingdom_5`(19) / `fac_kingdom_6`(20) 各 **−5**，对 `fac_black_khergits`(24) / `fac_deserters`(26) 各 **−2**，对 `fac_peasant_rebels`(31) **−10**。
   ⇒ **开局时斯瓦迪亚与维吉亚是联盟（+90），与库吉特/罗多克/萨兰德是轻度敌对（−5）。这就是原版开局「斯瓦迪亚 vs 库吉特」格局的数据来源。**
4. **`fac_deserters` / `fac_mountain_bandits` / `fac_forest_bandits` 对六国是 −2 / −5 / −5，而 `fac_peasant_rebels` 对六国是 −10、对玩家是 −40【实证】**⇒ **农民起义军对玩家比匪帮更敌对（−40 对 −15）**，这是一个反直觉但明确的设计选择：**设计者不希望玩家跟叛军结盟。**

**【未解】** 关系矩阵的完整值（部分行在提取时被截断，需要重新导出才能得到全表）。

### 7.4 战争影响账本与政治后果

**【实证 + 推断】** 结合 §4.4 与 §4.5，阵营槽位构成一本极简的政治账本：

| 槽位 | 观测到的用法 | 暂定名（**【推断】**） |
|---|---|---|
| 8 | `game_event_simulate_battle` 读它判断「战败的英雄是不是元帅」 | **元帅** |
| 11 | 与 `trp_player` 比较以判断玩家是否自立为王；参与士气加成档位选择 | **领袖** |
| 98 | 据点被攻下时写 `store_current_hours()` | **最近占领时刻** |
| 99 | 友军加、敌军减，上限 2000 | **战争影响账本** |

**【实证】** 政治后果的完整公式：

```
influence = min(enemyCount * $g_strength_contribution_of_player / 8, 2000)
若 $g_ally_party >= 0:  faction_get_slot(盟友阵营, 99) += (influence / 3) * 2            # 即 2/3
若 敌方不活跃 且 $current_town >= 0:
    faction_get_slot(城镇阵营, 99) += influence * 2                                       # 打下据点翻倍
否则若 敌方活跃 且 玩家没有领导 fac_player_supporters_faction:
    faction_get_slot(敌方阵营, 99) −= (influence / 3) * 2
```

**设计结论：**

1. **影响力按「击败的敌人数」算，`/8` 后封顶 2000【实证】**⇒ 一场战斗最多产生 **2000 点影响力**。
2. **「打下据点」让影响力翻倍【实证】**⇒ **占领据点的政治收益是两倍**，这是设计者对「攻城比野战重要」的定价。
3. **玩家自立为王之后，敌方阵营不再被扣影响力【实证】**（只在「玩家没有领导 `fac_player_supporters_faction`」时才执行扣减）⇒ **当国王是一个「豁免惩罚」的特权**，与 §3.4.2 的士气加成（×15 对 ×12）方向一致。
4. **友军只拿 2/3（`(influence/3)*2`）【实证】**⇒ **自己打下来的战功比盟友代打的更值钱。**

**【未解】** faction 槽位 98/99 的合法范围；以及**影响力（槽位 99）最终被谁消费**——消费它的脚本不在 34 个脚本内，**所以「攒影响力有什么用」在本模块内无法确定**。

## 8. 据点类型与功能差异

### 8.1 设计意图

180 个据点在数据上分成三块，而这三块在玩法上是**三种完全不同的东西**：**城镇 22**（经济中心、大市场、吃粮大户）、**城堡 48**（纯军事资产、不参与经济模型）、**村庄 110**（兵源、粮食产地、价格被动接受者）。

**设计意图【实证 + 推断】：**

> **城堡是本模块里唯一一个「被经济系统排除在外」的据点类型。**

三条独立证据都指向这一点：①`update_trade_good_prices` 的城镇区间 `[21,43)` 与村庄区间 `[91,201)` **把城堡 `[43,91)` 留在了空隙里【实证】**；②`change_center_prosperity` **不对城堡发通知**【实证】；③攻下据点时**非城堡**才扣 5 点繁荣度【实证】（§4.5 步骤 8）。

⇒ **设计者对城堡的定位是「占下来就赚的军事道具」，对城镇/村庄的定位是「占下来先亏的经济资产」。**

### 8.2 180 个据点的索引块

**【实证】** `parties.json` 布局：`p_zendar`(20) + 城镇 `p_town_1…22`(21–42) + 城堡 `p_castle_1…48`(43–90) + 村庄 `p_village_1…110`(91–200) + `p_salt_mine`(201，经济模型的上界哨兵)。22 + 48 + 110 = **180**。

**【实证】** **所有 180 个据点的 `faction` 都是 `fac_neutral`(3)**；全部 240 条部队的 `personality`、`ai_behavior`、`ai_target` 都是 **0**；据点的 `menu` 与 `template` 也是 0。

⇒ **据点归属、驻军、志愿者池、繁荣度全部是运行时种下的，模块数据里只有「中立白板」。** 已登记在 `RECONSTRUCTION.md` §4。

**设计结论：这是本模块最需要设计者接手的空缺。** 重建必须自己决定：**谁拥有哪个据点**（原版是运行时按文化/地理分配的）；**驻军从哪来**（`pt_center_reinforcements` 是唯一相关模板：`trp_townsman` 5–30 + `trp_watchman` 4–20 **【实证】**）；**志愿者池怎么刷**（`RECONSTRUCTION.md` 记录的标定做法是「按部队索引确定性推导」）。

### 8.6 据点的运行时状态

**【实证 + 推断】** 与据点相关的槽位（名称全部 **【推断】**）：

| 槽位 | 观测到的用法 | 暂定名 |
|---|---|---|
| 0 | `== 3` 城镇、`== 2` 城堡；另见 `11/15/18/13`（§4.5、§6.6） | **部队/据点类型** |
| 7 | 据点归属阵营 | **所有者** |
| 26 | 参与交易惩罚修正（×−3）；`>= 0` 是招募门槛 | **声望 / 价格修正** |
| 35 | `!= 1` 且 `!= 2` 才能招募 | **村庄状态**（推断 1/2 是「被烧/被劫」） |
| 39 | `< 1` 才能招募 | **村庄阻塞标记** |
| 50 | 繁荣度，钳 `[0,100]`，5 个 20 点分档 | **繁荣度** |
| 92 / 93 | 可招兵种 id / 可招数量（招募后写 `−1`） | **志愿者兵种 / 数量** |
| 98 / 99 | faction 槽位：占领时刻 / 影响账本（上限 2000） | **占领时刻 / 影响力** |
| 250–283 | 34 个交易品的本地价格 | **交易品价格** |

**【实证】** `get_prosperity_text_to_s50(centre)` 把繁荣度分成 **5 档各 20 点**并返回文字描述；`change_center_prosperity(centre, delta)` 把值钳到 `[0, 100]`，**只在跨过 20 点档位时发通知，且城堡不发通知**。

**设计结论：**

1. **繁荣度是一个 5 档的量，而不是 100 档【实证】**——玩家能感知到的只有 5 个状态。⇒ **±5 的变化有 3/4 的概率不产生任何可见反馈**（100 点分 5 档、每档 20 点，而一次战败扣 5 点）。**这是「占领村庄的代价玩家感觉不到」的算术原因。**
2. **槽位 26 同时承担「声望」与「价格修正」两个角色【推断】**：`get_trade_penalty` 用它当价格修正（× −3），招募条件用它当声望门槛（`>= 5`）。⇒ **跟一个地方做买卖和在那里招兵，用的是同一个数值。**
3. **【未解】** 槽位 26 / 35 / 39 的名字与合法范围；槽位 92 / 93 的写入者（刷新志愿者池的脚本不在 34 个脚本内）。

## 9. 玩家可见的已知缺陷

### 9.1 为什么要记录这些

本节只收录**在当前重建中实际观察到、且会直接影响玩家体验**的缺陷，全部来自 `RECONSTRUCTION.md` §5。它们不是引擎的未知，而是**重建过程中的实现错误**，因此对设计师有直接价值：**它们说明了「这套规则在实现时，哪些地方最容易走样」。**

### 9.2 尸骸被释放后仍被引用（悬空引用）

**症状**：战斗进行到一定时长后，阵型里的某个单位会突然报出「引用了已释放的对象」，战斗中断。

**根因【实证】**：`BattleAgent._corpse_tick` 在尸骸计时结束后**释放了 agent 对象**，但**阵型（`BattleFormation`）的 `agents` 数组里还留着这个对象的引用**；之后任何一次 `is_alive()` 调用都会命中一个已释放的对象。

**修法**：在释放之前先调用 `BattleFormation.remove_agent` 把它从数组里摘掉；并给所有遍历 `agents` 的地方加 `is_instance_valid` 守卫。

**设计师价值**：这是**「对象生命周期」与「数据数组」两套所有权同时存在**时的典型故障。战团的阵型系统是「按秩取人」的（§4.3 的 `get_stack_with_rank`），**所以数组的完整性是玩法的一部分**，不能用「弱引用 + 定期清理」代替。

### 9.3 遭遇面板高度正好是 0 像素

**症状**：大地图上接触敌军后，遭遇面板**完全不显示**，但交互已经生效（玩家会觉得游戏卡住）。

**根因【实证】**：面板容器调用了 `Control.set_anchors_preset(PRESET_BOTTOM_WIDE)`，但这次调用**只设置了锚点，没有设置偏移量**，所以 `offset_top` / `offset_bottom` 都还是 0，容器的 `size.y` 正好等于 **0**。

**修法**：显式设置偏移量，并把 `grow_vertical` 设为 `GROW_DIRECTION_BEGIN`。

**设计师价值**：这是一个**纯 UI 缺陷，但它伪装成了玩法缺陷**（「遇到敌人没反应」）。**任何重建的验收流程都必须包含「空状态截图」，否则这类问题会一直被当成逻辑 bug 排查。**

### 9.4 被击败的部队仍留在地图上

**症状**：打赢一场战斗后，敌人在地图上消失（标记被隐藏），但**玩家再次走到那个位置时会再次触发遭遇**，而场上没有任何敌人。

**根因【实证】**：`Main._on_battle_finished` 隐藏了敌方标记，但 `hide_party` **只把 `visible` 设为 `false`**，并没有把部队从 `GameState.parties` 里移除，所以「遭遇判定」仍然会命中这支部队。

**修法**：加一个 `defeated` 标记，并且让 `parties_near` **跳过 `defeated` 的部队**。

> **注意：数组本身不能被压缩（compact）。** 因为**发行数据的索引就是身份**（§0.3），删掉一个元素会让后面所有部队的索引错位，脚本引用的 `p_town_1` 之类会全部指错。

**设计师价值**：这是本文最关键的一条工程教训——**「删除一个实体」在这个模块里必须实现成「标记 + 过滤」，不能实现成「从数组移除」。这条约束同样适用于兵种、物品、阵营表。**

### 9.5 另外两个让战斗无法进行的问题

**【实证】** `RECONSTRUCTION.md` 还记录了两条同类缺陷：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 5.1 | 双方的军队永远碰不上；发起进攻时没有冲锋命令 | 遭遇判定与 AI 指令没有接上 | 补上遭遇触发与冲锋指令 |
| 5.2 | 战役地图的碰撞体把战场整个包住，玩家出不去 | 战役地图碰撞体被错误地复用到战场 | 战场不继承战役地图的碰撞几何 |

**共同点【推断】：5.1、5.2 与 §9.4 是同一类问题——「两个系统各自正确，接缝处缺失」。** 战役地图与战场、遭遇判定与 AI 指令、隐藏与移除，都是**成对的概念**，只实现一半就会出现「看起来能跑，但玩不下去」的故障。

**给重建的检查清单【推断】：** ①每实现一个「显示/隐藏」，都要问「另一侧的滤除做了吗」；②每实现一个「进入战场」，都要问「战场的坐标系与碰撞体是新的吗」；③每实现一个「销毁」，都要问「还有谁在引用它」。

### 9.6 名称里的 `{!}` 标记

**【实证】** 兵种、阵营、部队、物品的名字字段里存在一种占位标记 `{!}`，出现次数与载体数量：`troops.txt` **537 次 / 132 个兵种**、`parties.txt` **40 条部队**、`factions.txt` 15 次、`item_kinds1.txt` 1 次。

**【实证】** 132 个承载者的身份分布（按 id 模式计数）：

| id 模式 | 数量 | id 模式 | 数量 |
|---|---|---|---|
| `trp_castle_N_seneschal` | **48** | `trp_tutorial_student_N` | 4 |
| `trp_town_N_seneschal` | **22** | `trp_bonus_chest_N` | 3 |
| `trp_town_N_master_craftsman` | **22** | `trp_tutorial_chest_N` / `trp_notification_menu_varN` | 各 2 |
| `trp_coop_companion_equipment_ui_N` / `_N_f` | 各 2 | `trp_heroes_end` | 1（索引 **463**） |
| `trp_zendar_chest` / `trp_household_possessions` | 各 1 | `trp_temp_array_a/b/c` | 各 1 |
| `trp_stack_selection_amounts/ids` | 各 1 | `trp_notification_menu_types` | 1 |
| `trp_banner_background_color_array` / `trp_multiplayer_data` | 各 1 | `trp_quick_battle_N_player` | 1 |
| `trp_multiplayer_end` | 1 | `trp_log_array_*`（8 个） | 各 1 |
| `trp_quick_battle_troops_end` | 1 | `trp_coop_faction_troop_templates_end` | 1 |
| `trp_coop_companion_equipment_sets_end` | 1 | — | — |

**【实证】** 具体例子：`p_camp_bandits` 在 `parties.txt` 里的名字字段存的是 `{!}camp bandits`，而提取出来的 JSON 的 `name` 字段已经是 `"camp bandits"`（**标记被剥掉了**）；`parties.json` 只保留 `name`，`troops.json` 则同时保留 `name` 与 `raw_name`。又：`trp_heroes_end` 的名字字面上就是 `'{!}heroes_end'`（索引 463）；`trp_kingdom_heroes_including_player_begin` 在索引 **193**。

**设计结论【推断】：**

1. **`{!}` 出现在「名字要在运行时拼接」的实体上**（总管要拼城镇/城堡名，工匠要拼城镇名）⇒ **它是一个「这个名字不是字面量」的标记。**
2. **它也出现在全部的内部占位数组上**（`trp_temp_array_*`、`trp_log_array_*`、`trp_*_end` 哨兵）⇒ 第二层含义是**「这不是给玩家看的实体」。**
3. **重建时必须剥掉这个标记**（或按它触发拼接），否则玩家会看到 `{!}camp bandits` 这种名字。**提取脚本已经做了剥离，所以 JSON 里的 `name` 是干净的。**
4. **`{!}` 是一个极好的「这个兵种是设施还是活人」的判别信号【推断】**：132 个承载者里，除了内部数组，全部都是**据点设施或教程设施**，没有一个是战斗兵种。

### 9.7 数据本身的异常：2 参数的 `store_sub`

**【实证】** `count_casualties_and_adjust_morale` 里有两处操作**只带了 2 个参数**，而操作码声明需要 3 个：操作 **9**（`<local8> (local6)`，玩家伤亡分支）与操作 **78**（同形，友军伤亡分支）。操作码表自己的声明是 `store_sub = 2121 # (store_sub,<destination>,<value_1>,<value_2>), destination = value_1 - value_2`。

**【实证】** 三条证据表明这是发行脚本里的真实异常，而不是解码错误：

1. **敌方分支（操作 44）是 3 参数形式**（`store_sub :8 :7 :6`），而它周围的算术与其他两个分支**完全相同**⇒ **不对称在脚本内部，不在读取器里。**
2. **整个 610 个脚本的语料里，`store_sub` 只有这两处 `argc = 2`**，且两处操作数形状一致；其他所有 `store_*` 操作（`store_add`、`store_mul`、`store_div`、`store_mod`）**只以 `argc = 3` 出现**⇒ 可以排除编译器窥孔优化。
3. **`2121` 不是发行头文件里那两个重复操作码之一**（重复的是 `0x460` tutorial_box/dialog_box 与 `0x87d` store_troop_faction/store_faction_of_troop）。

**引擎在缺少第三个操作数时会做什么：【未解】。**

**【推断】** 最可能的意图是 `:8 = :7 − :6`（两个参数按 `value_2`、`value_1` 读取，第三个寄存器重复），因为这样该分支就与敌方分支完全一致。**但这是对意图的推断，不是观测到的行为，任何重建都不应该默认采用它。** 应当记录下来并在运行时探测。

**设计价值**：这是一个**「数据里有洞，但洞不影响玩法路径」**的例子——它位于士气结算的分支上，而那个分支的数值影响很小。**它提醒设计者：即使拿到了「0 失败」的校验结论，仍然需要逐条核对操作数个数。**

## 附录：给设计师的三条最重要结论

1. **这套玩法的骨架是「三条负反馈挤出一个编制上限」**：工资按 `(等级+3)²/25` 平方增长、士气按队伍人数 1:1 扣减、食物按件数线性消耗。三者中任意一条都能被绕过，**必须同时存在才能形成「规模是一种资源」的手感。领导力是唯一同时缓解两条线的技能**（每级 +12/+15 士气、每级 −5% 工资），因此它是本模块性价比最高的成长点。

2. **正向循环完全建立在「剿匪」上**：升级图的 11 个根全部是农民、市民、难民、女性和匪帮；四个匪帮直接通向四个国家的 1 级兵；匪帮的升级经验是 **×2**。⇒ **打匪帮同时提供金币、经验、战利品和兵源，是四条收益线的交汇点。任何削弱剿匪收益的改动，都会让整个循环失去引擎。**

3. **城堡被刻意排除在经济系统之外**：`update_trade_good_prices` 的两个区间把城堡 `[43,91)` 留成空隙、繁荣度通知跳过城堡、被攻下时不扣繁荣度。⇒ **城堡是「占下来就赚」，城镇/村庄是「占下来先亏」。** 这个不对称是设计者对「军事目标」与「经济目标」的定价；**重建时若把城堡并入经济模型，整个战略地图的价值梯度会消失。**
