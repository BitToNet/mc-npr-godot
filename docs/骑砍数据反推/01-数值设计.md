## 导读：证据来源与标签用法

### 这份文档是什么

本册的每一个数字都来自**已安装游戏自带的文件**，逐条解码得到，不引用 wiki、不凭记忆。一级来源是 `scripts.txt`（模块系统编译后的脚本字节码），每条脚本形如：

```
<script_name> -1
 <op_count> (<opcode> <argc> <arg> ...) (<opcode> <argc> <arg> ...) ...
```

`op_count` 是**独立的校验和**：只有解码器把每个操作边界（含参数个数内联的可变长操作）都切对了，重算出的操作条数才会与它一致。全模块校验：

```
opcode table entries : 1054
scripts parsed       : 610
operations decoded   : 36740
scripts w/ failure   : 0
opcodes missing name : 0
```

### 三种标签，全文严格不混用

| 标签 | 含义 | 怎么用 |
| --- | --- | --- |
| **【实证】** | 公式的每一步都是解码出的操作码，文中给出脚本名与 **op 序号**，可回 `scripts.txt` 复核 | 可直接照抄 |
| **【推断】** | 算术是【实证】的，但名字/单位/含义是推断的 | 公式照抄；**命名与语义**需策划确认 |
| **【未解】** | 字节码与随包数据都无法确定；**本册不给任何猜测值** | 需运行时探针或反编译 `mb_warband.exe` |

补充标记 **【演算】**：把【实证】公式代入选定输入后得到的算术结果。它不是新证据，也不是猜测。

### 一件贯穿全文的事：全程截断整除

模块系统的整数运算**全程是截断整除**（`a / b` 丢弃余数、向零取整）。原版有**多处连续整除把截断误差累积起来**：

1. **物价三段式归一化**（§1.6）——先乘后除的顺序决定截断点；每个中心、每个交易品各截断一次，§1.7 的扩散又把结果当作下一轮输入继续截断。价格是**累积漂移**的，不会每次都回到理论值。
2. **工资链**（§2.2）——`(level+3)²/25` 截断一次，`×5/3`、`×3/2`、`×2`、`×(100−5L)/100` 各再截断一次。同样的数学值，不同乘法顺序会差 1–2 金。
3. **战场优势**（§5.2）——最后的 `/100` 是截断的，所以**小的正优势会被截成 0，而同样大小的负优势保留负号**。原版行为不对称。

**给程序的硬性要求**：复刻时必须用整数运算，并**保持原版运算顺序**（尤其是 `a * b / c` 不要改写成 `a * (b / c)`）。本册凡写 `× A / B`，都表示"先乘 A 再整除 B"。

### 一个必须提前说明的坑：slot 问题

`party_get_slot` / `troop_get_slot` / `item_get_slot` / `faction_get_slot` 的槽位编号在本 build 里是**裸整数**。游戏模块树里能恢复出来的模块常量文件属于**多人 / Napoleonic 世代**，只含 `base_export_percentage`、`max_food_amount`、`max_distance_to_loot`、`item_class_food`，**没有定义任何一个单机 slot 名**。因此本册所有 slot 编号都写成**字面整数**，角色由脚本用法反推，**一律标【推断】**。汇总见 §8。

# 1. 经济与物价

## 1.1 本节设计结论汇总

| 项 | 内容 |
| --- | --- |
| **最重要** | 买入与卖出公式**结构不对称**：惩罚项对买入是 `×(100+p)/100`，对卖出是 `×100/(100+p)`；而且卖出侧对**非交易品**额外 `p *= 4`，所以普通商品的买卖差价是 **10 倍**而不是 1.26 倍。 |
| **第二条** | 交易品的价格**不读 `value` 字段**。它走一条独立的 `1000` 基线 → 两阶段加权归一化 → 空间扩散的模型；`value` 只在非交易品上生效。 |

## 1.2 `get_trade_penalty(item)` → `reg0`（op 1–43）

一个有符号、无量纲的惩罚/加价百分比，被买入与卖出因子消费。

```
skl_trade = party_get_skill_level(p_main_party, skl_trade)      # 技能索引 0

if itm_spice <= item < itm_siege_supply:        # 交易品
    penalty = 12 - 1 * skl_trade
    penalty = max(penalty, 3)
else:                                            # 其他商品
    penalty = 100 - 5 * skl_trade

modifier = 1000
if p_town_1 <= g_encountered_party < p_salt_mine:      # 城镇/城堡/村庄，[21, 201)
    standing = party_get_slot(g_encountered_party, 26)
    modifier += (-3) * standing
    if standing < 0:
        modifier = modifier * (100 - standing) / 100

if relation(player, g_talk_troop) < 0:
    modifier += 20 * (-relation)

if p_village_1 <= g_encountered_party < p_salt_mine:   # 仅村庄，[91, 201)
    penalty = penalty * 5 / 4                          # 注意：在乘 modifier 之前

penalty = penalty * modifier / 1000
penalty = max(penalty, 1)
```

**两个范围测试覆盖不同集合，这个差异是承重的**：op 16 的 `[21, 201)` 覆盖**所有**中心（含城堡），op 36 的 `[91, 201)` **只覆盖村庄**。所以**城堡享受 slot 26 的价格调整，但不吃 `×5/4` 加价**。对照 §1.6，那里的城镇测试是 `is_between(centre, p_town_1, p_castle_1)` 且确实跳过城堡。

`5%/级` 的交易惩罚折减与随包 `skills.json` 索引 0 的文案 *"Every level of this skill reduces your trade penalty by 5%."* 精确吻合——两个独立工件互证。

| 项 | 内容 |
| --- | --- |
| **结论** | 交易品吃 `−1/级`（下限 3，即最多降到 3），普通商品吃 `−5/级`（下限 0，因为 `100 − 50 = 50`）。**交易品的惩罚起点低、下降慢；普通商品的惩罚起点高、下降快。** |
| **公式** | 见上 |
| **常数** | `12`、`3`（下限）、`1`/级、`100`、`5`/级、`1000`（modifier 基）、`−3×声望`、`20×` 负关系、村庄 `×5/4`、下限 `1` |
| **证据等级** | **【实证】**（op 1–43，本次独立复核一致）/ **【推断】**（slot 26 = 中心声望/交易修正；`×5/4` 是"村庄卖得贵"） |
| **出处** | `RULES.md` §1.1；`data/skills.json` |

| 0 | 12 | 100 |

| 5 | 7 | 75 |

## 1.3 `game_get_item_buy_price_factor(item)` → `reg0`（op 0–17）

返回**标价的百分比**。

```
factor = 100
penalty = get_trade_penalty(item)

if centre is a town/village and item is a trade good:
    factor = party_get_slot(centre, (item - itm_spice) + 250)     # 中心本地价格槽
    factor = factor * 100 / 1000                                  # 1000 = 基准价

factor = factor * (100 + penalty) / 100
```

| 项 | 内容 |
| --- | --- |
| **结论** | 交易品在中心里买入 = `价格槽/10`（因为 `×100/1000`），再乘 `(100+惩罚)/100`。**非交易品在城镇的买入因子恒为 `(100+惩罚)`**，技能 0 时是 200，即**双倍标价**。 |
| **公式** | 见上 |
| **常数** | 基 `100`；价格槽基址 `250`；基准价 `1000` |
| **证据等级** | **【实证】**（op 0–17）/ **【推断】**（`1000` 是交易品基准价；slot `item − itm_spice + 250` 是该品在该中心的现价） |
| **出处** | `RULES.md` §1.2 |

## 1.4 `game_get_item_sell_price_factor(item)` → `reg0`

```
factor = 100
penalty = get_trade_penalty(item)

if centre is a town/village and item is a trade good:
    factor = party_get_slot(centre, (item - itm_spice) + 250) * 100 / 1000
else:
    penalty = penalty * 4                     # ← 只作用于非交易品

```

| 项 | 内容 |
| --- | --- |
| **结论** | 交易品不额外乘 4；**非交易品在卖出侧把惩罚乘 4**，再取倒数。这是买卖差价的主要来源。 |
| **公式** | 见上 |
| **常数** | `4`（非交易品惩罚倍率）；其余同 §1.3 |
| **证据等级** | **【实证】** / **【推断】**（`×4` 是刻意的"商店吃差价"手段） |
| **出处** | `RULES.md` §1.3 |

**买卖差价对照【演算】：**

| 情形 | 买入 | 卖出 | 买卖比 |
| --- | --- | --- | --- |
| 交易品，槽值 1000，交易 0 | 112% | 89% | 1.26× |
| 交易品，槽值 1000，交易 10 | 103% | 97% | 1.06× |
| 普通商品，交易 0 | 200% | 20% | **10.0×** |
| 普通商品，交易 5 | 175% | 29% | 6.1× |
| 普通商品，交易 10 | 150% | 33% | 4.5× |

## 1.6 `update_trade_good_prices()` —— 两阶段价格模型

**阶段 1（逐中心刷新）**：

```
for each centre:
    if centre is a town (21..42) or village (91..200):     # 城堡被跳过
        weight = 5 if town else 1
        for each trade good (itm_spice .. itm_siege_supply):
            price = party_get_slot(centre, 250 + good - itm_spice)
            price = clamp(price, 100, 10000)
            # 单次消费/生产的随机调整，然后写回
```

**阶段 2（全局归一化，按交易品逐个做）**：

```
for each trade good G:
    total = 0; weighted = 0
    for each centre:
        price  = party_get_slot(centre, 250 + G - itm_spice)
        total  += weight
        weighted += weight * price
    for each centre:
        price = party_get_slot(centre, 250 + G - itm_spice)
        price = price * 1000 * total / weighted          # 目标均值 1000
        price = clamp(price, 100, 10000)
        party_set_slot(centre, 250 + G - itm_spice, price)
```

| 项 | 内容 |
| --- | --- |
| **结论（权重）** | 城镇权重 **5**、村庄 **1**。归一化的目标是**全局加权均值 = 1000**，所以单个中心的价格是相对全图的。 |
| **结论（城堡被跳过）** | 城镇测试用的是 `[p_town_1, p_castle_1)`，**城堡不参与归一化，其价格槽保持阶段 1 的原值**。这是一处原版怪癖。 |
| **结论（夹取）** | 价格被夹在 `[100, 10000]`，即 **0.1× 到 10× 基准价**。 |
| **公式** | 见上 |
| **常数** | 权重 `5` / `1`；目标均值 `1000`；夹取 `[100, 10000]`；价格槽基址 `250` |
| **证据等级** | **【实证】**（算术与范围测试）/ **【推断】**（城堡被跳过是"疏忽"还是"刻意"）/ **【未解】**（触发周期；中间量是否溢出 32 位，见 §9.3） |
| **出处** | `RULES.md` §1.5a |

**溢出提示【未解】**：以本册核到的中心数（22 城镇 + 110 村庄）算 `total = 22×5 + 110×1 = 220`；`price` 上限 10000，则 `price × 1000 × total` 最大为 **2,200,000,000**，**超过 2³¹−1 = 2,147,483,647**。引擎的整数宽度与回绕行为未知。

## 1.7 `average_trade_good_prices()` —— 空间扩散

```
r = 50
rate = 1000
for each centre A in towns (21..42):                     # A 侧只遍历城镇
    for each centre B in all centres [21, 201):
        d = distance(A, B)
        if d < r:
            for each trade good G:
                if A is a town/village and G is a trade good:     # 注意：读的是 A
                    pA = party_get_slot(A, 250 + G - itm_spice)
                    pB = party_get_slot(B, 250 + G - itm_spice)
                    if pB > pA:
                        move = (pB - pA) * (r - d) / rate
                        party_set_slot(B, 250 + G - itm_spice, pB - move)
```

| 项 | 内容 |
| --- | --- |

## 1.11 经济系统伪代码

```python
ITM_SPICE, ITM_SIEGE_SUPPLY, SLOT_PRICE_BASE = 91, 125, 250
TOWN_1, CASTLE_1, VILLAGE_1, SALT_MINE = 21, 43, 91, 201
is_trade_good = lambda it: ITM_SPICE <= it < ITM_SIEGE_SUPPLY
is_centre    = lambda p:  TOWN_1 <= p < SALT_MINE
is_village   = lambda p:  VILLAGE_1 <= p < SALT_MINE
is_town      = lambda p:  TOWN_1 <= p < CASTLE_1
price_slot   = lambda it: SLOT_PRICE_BASE + it - ITM_SPICE     # 只有交易品有价格槽

def trade_penalty(item, centre, standing, relation, skl_trade):
    penalty = max(12 - skl_trade, 3) if is_trade_good(item) else 100 - 5 * skl_trade
    modifier = 1000
    if is_centre(centre):
        modifier += -3 * standing
        if standing < 0:
            modifier = modifier * (100 - standing) // 100
    if relation < 0:
        modifier += 20 * (-relation)
    if is_village(centre):                      # 只有村庄有 5/4 上浮，城堡没有
        penalty = penalty * 5 // 4
    return max(penalty * modifier // 1000, 1)

def buy_factor(item, centre, penalty):
    factor = 100
    if (is_town(centre) or is_village(centre)) and is_trade_good(item):
        factor = get_slot(centre, price_slot(item)) * 100 // 1000   # 交易品：读中心现价
    return factor * (100 + penalty) // 100                          # 非交易品 factor 恒为 100

def sell_factor(item, centre, penalty):
    factor = 100
    if (is_town(centre) or is_village(centre)) and is_trade_good(item):
        factor = get_slot(centre, price_slot(item)) * 100 // 1000
    else:
        penalty = penalty * 4                   # 只有非交易品乘 4
    return factor * 100 // (100 + penalty)

def update_trade_good_prices():
    for centre in centres():
        if is_town(centre) or is_village(centre):        # 城堡被跳过（原版怪癖）
            for g in range(ITM_SPICE, ITM_SIEGE_SUPPLY):
                p = clamp(get_slot(centre, price_slot(g)), 100, 10000)
                set_slot(centre, price_slot(g), p)
    for g in range(ITM_SPICE, ITM_SIEGE_SUPPLY):
        total = weighted = 0
        for centre in centres():
            w = 5 if is_town(centre) else (1 if is_village(centre) else 0)
            total += w;  weighted += w * get_slot(centre, price_slot(g))
        for centre in centres():
            p = get_slot(centre, price_slot(g)) * 1000 * total // weighted
            set_slot(centre, price_slot(g), clamp(p, 100, 10000))   # 目标：加权均值 1000

def average_trade_good_prices(radius=50, rate=1000):
    for a in [c for c in centres() if is_town(c)]:       # A 侧只遍历城镇
        for b in centres():                              # B 侧不过滤类型（城堡也参与）
            d = distance(a, b)
            if d >= radius: continue
            for g in range(ITM_SPICE, ITM_SIEGE_SUPPLY):
                pa, pb = get_slot(a, price_slot(g)), get_slot(b, price_slot(g))
                if pb > pa:
                    set_slot(b, price_slot(g), pb - (pb - pa) * (radius - d) // rate)

def center_get_food_consumption(centre):
    t = get_slot(centre, 0)                     # 中心类型
    return 500 if t == 3 else (50 if t == 2 else 0)
```

### 本次 raw 复核发现的一件事（必须写进设计文档）

用 `--raw` 复核，op 27（`call_script(cf_player_has_item_without_modifier, item, 41)`）与 op 28 之间**没有任何带条件标志的操作码**（无 `this_or_next` / `neg` 位，也无 `try_begin`）。也就是说：

- **【实证】** 循环体在**每一个食物物品类型**上无条件执行 `item_get_slot(item, 1) × 3/2` 并累加。
- **【推断】** 设计意图显然是"只统计真正携带、且不带 modifier 41 的食物"——`cf_player_has_item_without_modifier` 与 `consume_food` 用的是**同一个禁食标记 41**，这个一致性不是巧合。
- **【未解】** `cf_` 脚本返回的条件结果**是否被引擎用来抑制随后的 28–31**。如果**不**抑制，食物士气项就等于"所有食物类型的 `item_get_slot(·,1)` 之和 × 3/2"，**与玩家实际带什么、带多少完全无关**。

**对本册的直接影响**：食物士气项**无法从随包数据算出数值**。原因有两层——① `item_get_slot(item, 1)`（食物营养值）的**写入方不在这 34 个脚本里**；② 上面那条条件语义未定。因此本册**不给出**食物士气加成表。见 §9.3。

```
reg0 = reg0 + 30
if trp_bandit <= troop < trp_black_khergit_horseman:
    reg0 = reg0 * 2
```

**手算复核的意义**：op 3 是单个 `store_add`（三操作数），渲染器**没有**把它与 op 2 融合；op 10 的 `neg|` 位与 opcode 在同一个字里（`this_or_next = 0x40000000`、`neg = 0x80000000`），所以 op 9–10 是**合取**。结论：

```
upgradeXP(troop) = ( levelBoundary(level(troop) + 3) × 6 / 1000 ) + 30,  强盗再 × 2
```

| --- | --- |
| **结论** | 升级 XP **不是**独立曲线，而是**引擎等级门槛表的一个 0.6% 切片再加 30**（表见 §4.8）。上一版写"对等级几乎不敏感（除非曲线本身增长极快）"——现已可判定：**曲线确实增长极快**，所以它并不迟钝。 |

**发点逻辑**【实证：结构，部分字段语义为推断】

`FUN_004acd60` 在通过门槛检查后，对同一个兵种对象连做三次同构处理，
分别累加到 `+0x2bc`、`+0x2c0`、`+0x2c4`：

- 若 `×_points_per_level == 1.0` → 每级加 1 点（`cmp edi,1` 分支）。
- 若该值 < 1.0 → 走 `fld1 / fdivrp` 分支，算出 `1 / 值`，再用
  `cdq; idiv` 与余数测试决定进位 —— 即**允许把「每级点数」写成小数，
  含义是「每 `1/值` 级发 1 点」**。这是一个刻意留下的分数化设计。

三个计数器与 `+0x2b4`（经验）、`+0x2c8`（等级下标）**[推断]** 的对应关系，
由它们在 `0x4acf02` / `0x4acfbf` / 后续第三块的累加位置推出；
哪一个对应「技能点 / 属性点 / 武器点」没有符号可依。

**为什么 Native 不写这些键也能跑**

这些键的全局量在 `.data` 的零填充区，未声明就是 `0.0`。引擎在每个使用点自带钳位：

```
0x58cb72  mov edi, dword ptr [0xa6f350]   ; attribute_required_per_skill_level
0x58cb7b  cmp edi, 1
0x58cb89  jg  0x58cb90
0x58cb8b  mov edi, 1                       ; ≤1（含未设置的 0）一律当 1
0x58cb9f  idiv edi
```

所以 **`attribute_required_per_skill_level` 未设置时的有效值是 1**，
而不是上游文档常写的 3。**这一条对 MOD 数值复现是致命的**：
漏写一个键得到的是「0 + 使用点钳位」，不是引擎文档里的默认值。
53 个 Native 未声明的键逐一的「有效默认值」需要逐个读使用点，属未解项。

**给策划的直接结论**

1. `level_boundary_multiplier` 未设置时全局为 0，于是 `本级门槛 = 0`，
   门槛检查恒通过——但此时三个 `*_points_per_level` 也是 0，发点为 0，
   **净效果是「升级但不发点」**。任何自建模块必须自己声明这几个键。
2. 升级曲线本体是**编译期常量表**，`module.ini` 只能整体缩放它，
   不能改形状。想改形状必须改 exe（或由脚本接管发点）。

## 5.2 `calculate_battle_advantage()` → `reg0`（op 0–26）

```
friends      = party_count_fit_for_battle(p_collective_friends)
enemies      = party_count_fit_for_battle(p_collective_enemy)
tactics      = max(party_get_skill_level(p_main_party,        skl_tactics),
                   party_get_skill_level(p_collective_friends, skl_tactics))
enemyTactics = party_get_skill_level(p_collective_enemy, skl_tactics)
friends += 1;  enemies += 1
advantage = (friends * 100 / enemies - 100) if friends >= enemies else (100 - enemies * 100 / friends)
advantage = advantage * 2
advantage = advantage + 30 * tactics - 30 * enemyTactics
advantage = advantage / 100
```

| 项 | 内容 |
| --- | --- |
| **结论（合取形式）** | `advantage = ( 2·sign·(|friends×100/enemies| − 100) + 30·(tactics − enemyTactics) ) / 100`。 |
| **结论（`+1` 的作用）** | **【推断】** 是除零保护：同时保证 `ratio` 有限，并让"双方都是 0 人"时 `ratio = 100`、优势为 0。 |
| **结论（截断不对称）** | 最后 `/100` 截断。`(0 − 30)/100 = 0`，但 `−130/100 = −1`——**正负两侧的"第一格"宽度不同**。 |
| **公式** | 见上 |
| **常数** | `+1`；`×100`；`×2`；每级战术 `30`（双方各 30）；`/100` |
| **证据等级** | **【实证】**（op 0–26）/ **【推断】**（`+1` 是防零除） |
| **出处** | `RULES.md` §5.1 |

**演算示例【演算】：**

| 我方 | 敌方 | 我方战术 | 敌方战术 | `ratio` | 优势项 | 战术项 | 结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 100 | 100 | 0 | 0 | 100 | 0 | 0 | **0** |
| 100 | 100 | 1 | 0 | 100 | 0 | 30 | **0**（截断吃掉） |
| 100 | 100 | 5 / 10 | 0 | 100 | 0 | 150 / 300 | **1 / 3** |

## 5.3 `inflict_casualties_to_party(party, kills)`（op 0–37）

```
party_clear(p_temp_casualties)
fit = party_count_fit_regulars(party)     # 注意：regulars，不是 party_count_fit_for_battle
for i in 0 .. kills:
    if fit <= 0: continue
    troop = party_stack_get_troop_id(party, get_stack_with_rank(party, random(0, fit)))
    if random(0, 10000) < 10000 / (store_character_level(troop) + 5):
        if troop is a hero:
            troop_set_health(troop, max(troop_get_health(troop) - 45, 1))   # 本函数内不会死
        else:
            party_add_members(p_temp_casualties, troop, 1)
            if random(0, 2) < 1:                                 # 受伤（也记入伤亡部队）
                party_wound_members(p_temp_casualties, troop, 1)
                party_wound_members(party, troop, 1)
            else:                                                # 阵亡
                party_remove_members(party, troop, 1)
        fit -= 1                          # 受伤与阵亡都减 1
```

| 项 | 内容 |
| --- | --- |
| **结论（命中率）** | `1/(level+5)`：0 级 20%，5 级 10%，25 级 3.33%，43 级 2.08%。**这是"等级即防护"的核心机制。** |
| **结论（英雄）** | **本函数内英雄不可能死亡**：只掉 45 生命并保底 1。英雄死亡由别的机制决定。 |
| **结论（普通兵）** | `random(0, 2)` 推断取值 `{0, 1}` → **50% 受伤 / 50% 阵亡**。 |
| **结论（采样人口会缩）** | `fit -= 1` **在受伤时也执行**。所以抽样的是一个不断缩小的可战人口，**不是从固定名单独立重抽**。重制版若"每次从原始人口重抽"，伤亡分布会明显偏移（会重复击杀同一人）。 |
| **公式** | 见上 |
| **常数** | 等级偏移 `+5`；分母 `10000`；英雄伤害 `45`；生命下限 `1`；掷骰 `random(0, 2)` |
| **证据等级** | **【实证】**（op 0–37）/ **【推断】**（`random(0,2)` 值域）/ **【未解】**（`party_count_fit_regulars`、`get_stack_with_rank` 的定义） |

## 5.4 `count_casualties_and_adjust_morale()` —— 战后计分（op 0–252）

## 5.6 `simulate_battle_with_agents_aux(side, damageScale)`（op 0–98）

```
for each agent A marked for simulation (agent_slot(A, 3) == 1) on side:
    target = nearest live human agent on the other side
             （当 $pin_player_fallen == 0 时排除玩家）
    distance = distance(A, target) + 3000
    shots = 18000 / distance * 2
    shots = shots * attackerClassFactor / targetClassFactor
    shots = shots + targetClassBonus
    # class 1 -> targetClassBonus  = 2
    # class 2 -> attackerClassFactor = 2
    damageChance = damageScale + (level(target) - level(A)) / 5
    if A is the player: damageChance /= 2
    for i in 0 .. shots:
        if random(0, 100) < damageChance:
            agent_deliver_damage_to_agent(target, A)
```

| 项 | 内容 |
| --- | --- |
| **结论（核心形状）** | 伤害量由 **`18000 / (distance + 3000) × 2`** 决定，即**距离越近、出手次数越多**。距离 0 时约 12 次，距离 15000 时约 2 次。 |
| **结论（等级差方向反直觉）** | `damageChance = damageScale + (targetLevel − attackerLevel) / 5`。**目标等级高则更容易被打中**（每 5 级 +1 个百分点）。这是原版的实际方向。 |
| **结论（玩家）** | 玩家作攻击者时 `damageChance /= 2`；`$pin_player_fallen == 0` 时玩家**不会被选为目标**。 |
| **常数** | 距离偏移 `3000`；基数 `18000`；`×2`；等级差 `/5`；玩家 `÷2`；class 加成 `2` |
| **证据等级** | **【实证】**（op 0–98）/ **【推断】**（class 1/2 = 骑乘类）/ **【未解】**（场景距离单位；`agent_deliver_damage_to_agent` 的伤害模型） |

### 6.7.1 伤害结算的完整代数【实证】

上一版这一节写的是「这套代数全部编译在 exe 里，从随包数据不可知」。这句话已被推翻：结算函数
已定位，逐条指令读出，并用两个独立反编译会话 + 脚本侧口径双向交叉验证。

**函数定位**

| 项 | 值 |
| --- | --- |
| 函数 | `FUN_004b3050(this /*ECX*/, DamageInfo *param_1 /*[EBP+8]*/)` |
| 函数体 | `0x4b3050`–`0x4b36a5`，1,622 字节，58 个基本块，`SUB ESP,0x1c4`，`RET 0x4` |
| 调用点 | **全程序仅 2 处**：`0x4bb2c8`（在 `FUN_004bb290` 内）、`0x4ec1ba`（在 `FUN_004ec100` 内） |
| 模式字段 | `this+0x28`：**0 = 单机，1 = 联机** |
| 护甲来源 | `this+0x854 + r*4`，按命中部位区 `r` 取整数护甲值 |

`FUN_004ec100` 把 `*(float*)(struct+0x44)` 原样**作为返回值**返回，`FUN_004bb290` 把它拷进
本 agent 的 132 字节「上次受击记录」（`+0x5ea4` 起，`rep movsd` 33 个 dword）。
两条路径都证明 **`+0x44` 就是最终穿甲后伤害**，不是中间量。

**`DamageInfo` 字段表【实证】**

| 偏移 | 含义 | 方向 |
| --- | --- | --- |
| `+0x38` | 命中部位编号 | 输入 |
| `+0x40` | 原始伤害（进函数前已被钳到 ≤ 1000.0） | 输入 |
| `+0x44` | **最终伤害** | 输出 |
| `+0x48` | **被护甲吸收掉的量** | 输出 |
| `+0x4c` | 伤害类型：0=cut，1=pierce，2=blunt | 输入 |
| `+0x50` | 施加者 agent 下标（`>= 0` 才查施加者装备标志） | 输入 |
| `+0x5c` | 门控单机「背向/高度」加成的字节标志 | 输入 |
| dword 0 | 标志字，位 `0x10`/`0x20` 在 5 处被测试 | 输入 |

**结算步骤（按指令顺序）**

1. `D = *(float*)(param_1 + 0x40)`。
2. **部位区** `r`：联机（`this+0x28 == 1`）恒为 `1`；单机按命中部位 `+0x38`：`9` → `0`，
   `{1,4,2,5,3,6}` → `2`，其余 → `1`。
   即单机把身体分成三个区，联机只用一个总护甲值。
3. `A = (float)*(int*)(this + 0x854 + r*4)` —— 该区的**整数**护甲值，转成浮点。
4. **单机背向/高度加成**（门控 `mode == 0 && FUN_004a2c80() >= 0 && *(char*)(param_1+0x5c) != 0`）：
   取施加者 `agent = *(int*)0x008b8554 + (*(int*)(param_1+0x50)) * 0xc38`；
   若方向点积 `param_1[0x68]*x + param_1[0x60]*y + param_1[100]*z < -0.5`（背后命中）
   且 `fVar8 < (float)*(int*)(agent+0xc10) * 0.01`，则
   **`A += (float)(FUN_004a13d0(ecx) + 10)`**（把某一装备/护甲分量加进护甲值）。
5. **按伤害类型取系数**：`0` → `soakF = [0xa6f218]`, `redF = [0xa6f224]`；
   `1` → `[0xa6f21c]` / `[0xa6f228]`；`2` → `[0xa6f220]` / `[0xa6f22c]`；其它 → 两者都 0。
6. **额外穿透**：若 `*(int*)(param_1+0x50) >= 0` 且
   `(*(uint*)(agent + 0xbd4) & 0x1000) != 0`，则 `soakF *= [0xa6f314]`、`redF *= [0xa6f318]`。
7. **三次伪随机抽样**（LCG，状态在 `0x0085f3a0`）：
   `state = state * 0x343fd + 0x269ec3`；`n = (state >> 16) & 0x7fff`；
   **`u = (n % 15817) / 15817.0`** —— 所以 `u` 是 `[0,1)` 上的 15817 等分格点，不是连续均匀分布。
   取 `u1, u2, u3` 三次。
8. `roll = D * (0.9 + 0.1 * u2)` ∈ `[0.90, 1.00) * D` —— **±10% 伤害浮动**。
9. `soak = A * soakF * (0.45 + 0.55 * u1)` ∈ `[0.45, 1.00) * A * soakF` —— **第一步：吸收**。
10. `net = max(0, roll - soak)`。
11. `k = 0.45 + 0.55 * u3` ∈ `[0.45, 1.00)`。
12. `red = A * redF * 0.014 * k`，`pen = 1 - e^(-red)` —— **第二步：按比例减免**。
    `A * redF < 1e-4` 时特判为 `pen = 0`（避免精度与除零）。
13. `absorbed = soak + pen * net` —— 命中量中**被吸收**的部分。
14. **拆分**：`*(int*)(param_1+0x48) = N = round_half_down(absorbed)`；
    `*(float*)(param_1+0x44) = roll - (float)N`。
    **`+0x44` 与 `+0x48` 严格互补**，两者之和恒等于 `roll`。
15. **后置倍率**（作用在 `+0x44` 上）：
    - 联机且部位 `7`，或单机且部位 `9` → `× 1.2`（`0x007c5308`）；
      若同时施加者存在且 `(*(uint*)(agent+0xbd0) & 0xff) ∈ {8,9,10,0x10,0x11}` → 再 `× 1.75`（`0x00810320`）。
    - 否则单机且部位 ∈ `{1,4,2,5}` → `× 0.9`。
    - 其余情况不缩放。
16. **钳位**：`v <= 0` → `0.0`；`v >= 500.0` → `500.0`。

**舍入用的是「四舍五入向下」**（`0x4b3582`–`0x4b35b7`）：`FLD`、`CALL 0x624870`（CRT `_ftol2`）、
`FSUBR`、`FCOMP qword [0x007c09b8]`（0.5）、`FNSTSW AX`、`TEST AH,0x41`、`JP`。
`JP` 在「小数部分 > 0.5」或「无序」时跳走并 `INC`，落空则保留截断值。
所以恰好 `0.5` 时**不进位**。Ghidra 把这段渲染成 `(x < 0.5) == (x == 0.5)`，与之等价。

**三条自洽性验证【实证】**

1. **钳位为什么存在**：因为 `pen = 1 - e^(-red) < 1`，所以 `absorbed <= roll` 恒成立。
   当 `roll >= soak` 时 `+0x44 = roll - round(absorbed) >= 0`；当 `roll < soak`（被完全吸收）时
   `absorbed = soak > roll`，`+0x44` 会算出负数——**`[0, 500]` 钳位正是把这种负值压成 0 的机制**。
   这与 `module.ini` 第 66–68 行的自述完全吻合：「前三个值**直接扣减**，后三个值**按百分比减免**」。
2. **无甲目标**：`A = 0` ⇒ `soak = 0`、`red = 0`、`pen = 0` ⇒ 伤害 `= D * (0.9 + 0.1*u2)`，
   即原始伤害 ±10%。这是「裸体吃满伤害」的精确形式。
3. **单调性**：`absorbed` 对 `A` 单调递增，`+0x44` 对 `A` 单调递减；
   `0.45` 与 `0.55` 保证 soak 最低只能吸收 45%，即**再高的护甲也不会 100% 免疫**，
   但减免项 `1 - e^(-0.014*A*redF*k)` 会随 `A` 饱和——这解释了为什么重甲在高伤武器面前仍会掉血。

**必须记录的 x87 陷阱（本节结论曾因此写错两次）**

x87 的 `D8 C8+i`（`FMUL ST(0),ST(i)`）与 `DC C8+i`（`FMUL ST(i),ST(0)`）**字节不同，但
Capstone 对两者都打印 `fmul st(i)`**，因此只看反汇编文本无法判断方向，必须看编码字节：

| 字节 | 真实语义 |
| --- | --- |
| `dcc9` | `FMUL ST(1), ST(0)` → **ST1 = ST1 × ST0** |
| `dcc2` | `FADD ST(2), ST(0)` |
| `decb` | `FMULP ST(3), ST(0)` |
| `deca` | `FMULP ST(2), ST(0)` |
| `dec1` | `FADDP ST(1), ST(0)` |
| `d9ca` | `FXCH ST(2)` |

用 `capstone` 的 `md.detail = True` + `ins.bytes.hex()` 才能消歧；`op.access` 对 x87 不可靠
（两个操作数都报 `R`）。本轮曾据此把 soak 误写成 `A*soakF*(0.45 + u1)`，
正确形式是 **`A*soakF*(0.45 + 0.55*u1)`**；`k` 也只用第三次抽样 `u3`，**不是** `u1*u3`。

**仍未定的一项**：`this` 指向的那个 >0x6008 字节的单例对象**叫什么**没有符号可依。
可以确定的是它携带 `+0x28`（模式）、`+0x854/858/85c`（三个部位区的护甲值）、
`+0x5ea0`（受击记录有效标志）、`+0x5ee8`（上次 `+0x44`）、`+0x5ffc`、`+0x6000`。
它**不是** agent 结构（agent 步长 `0xc38`，而该对象的字段偏移超过 `0xc38` 仍在增长），
更像「战斗/伤害子系统」的单例。见 `05-未解项清单.md`。

**`no_friendly_fire_for_bots` 的去向也在这一轮查明**：它就是伤害入口 `FUN_004ec100` 里的
`DAT_00a6f28c`（存储地址 `0x0a6f28c`）。判断形式为
`DAT_00a6f28c != 0 && *(int*)(agent + 0x270) == 1` → 直接跳过伤害结算，
即**开启该键时，命中同阵营目标（`+0x270 == 1`）不结算伤害**。

## 9.5 一条必须原样保留的字节码异常：2 参数 `store_sub`

`count_casualties_and_adjust_morale` 里有两处操作**只带 2 个参数**，而该操作码自己声明需要 3 个：

```
op  9   <local8> (local6)              # 我方伤亡分支
op 78   <local8> (local6)              # 友军伤亡分支
```

操作码头声明：`store_sub = 2121 # (store_sub,<destination>,<value_1>,<value_2>), destination = value_1 - value_2`。

**它是真实的、不是解码伪影的证据：**

1. **敌方分支（op 44）是 3 参数形式**（`store_sub :8 :7 :6`），而它周围的算术与另外两支**完全相同**。所以不对称在**脚本内部**，不在读取器里。
2. **全 610 个脚本里，`store_sub` 以 `argc = 2` 出现恰好两次**——就是这两处，操作数形状相同。其他所有 `store_*` 运算符（`store_add`/`store_mul`/`store_div`/`store_mod`）**只以 `argc = 3` 出现**。因此可排除编译器 peephole。
3. **2121 不是随包头部里那两个重复的 opcode 编号**（重复的是 `0x460` tutorial_box/dialog_box 与 `0x87d` store_troop_faction/store_faction_of_troop）。

**引擎拿到缺失的第三个操作数会做什么，是未解。** 意图几乎肯定是 `:8 = :7 − :6`（两参数形式的操作数读作 `value_2` 与 `value_1`，即第三个寄存器重复），因为那样这一支就与敌方分支完全一致——**但这是对意图的【推断】，不是观察到的行为，任何重建都不应默默假定它。** 记录它，并在运行时探针里验证。

| 项 | 内容 |
| --- | --- |
| **结论** | 原版在计算我方与友军的"健康比例"时，把 `(2×stackSize − wounded)` 这个减法写成了缺少一个操作数的形式。**我方士气的最终值因此带有不确定性**；敌方分支不受影响。 |
| **公式** | 意图：`:8 = :7 − :6`；实际行为未定 |
| **常数** | op 9、op 78（2 参数）；op 44（3 参数，对照组）；opcode 号 `2121` |
| **证据等级** | **【实证】**（异常存在且可复核）/ **【未解】**（引擎行为）/ **【推断】**（意图） |
| **出处** | `RULES.md` §8.1 |

# 附录 A：复现方法

```powershell
cd G:\godot_project\MountAndBladeWarband
python tools\mb_decompile.py get_trade_penalty --sugar   # 人类可读的中缀形式
python tools\mb_decompile.py get_trade_penalty --raw     # 原始操作码（核对操作数身份与标志位）
python tools\mb_module.py validate                       # 全模块校验
```

`--raw` 与 `--sugar` **必须逐行一一对应**（每条解码操作恰好一行），这正是"渲染器没有伪造中缀算式"的证据。本册对以下 8 个脚本做过这一比对，结果与 `RULES.md` 一致：`game_get_upgrade_cost`、`game_get_troop_wage`、`get_trade_penalty`、`game_get_item_buy_price_factor`、`game_get_item_sell_price_factor`、`get_army_size_from_slider_value`、`center_get_food_consumption`、`get_player_party_morale_values`。

`validate` 的期望输出：`opcode table entries 1054`、`scripts parsed 610`、`operations decoded 36740`、`scripts w/ failure 0`、`opcodes missing name 0`。

**数据统计的两种口径**：① 直接引用 `stats.txt`（等级/属性/技能/熟练度/装备分布）；② 本册额外统计（标"本册统计"的表）用 `python` 读 `data/*.json` 得到。**统计陷阱**：`data/troops.json` 里 73.7% 是英雄，含大量占位/模板兵；任何"兵种配平"表若不过滤 `is_hero`、升级路径或阵营，数字都会被稀释（例如"全体中位周薪 = 2"就是被 450 条 2 级占位兵拉出来的）。
