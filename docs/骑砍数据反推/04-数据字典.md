## 0. 读之前必须知道的四件事

### 0.1 三种标记

| 标记 | 含义 | 可以怎么用 |
| --- | --- | --- |
| **【实证】** | 由发行文件本身的字节、或模块系统的官方头文件（`_rea/modulesys/header_*.py`）直接确定 | 可以当事实写进代码 |
| **【推断】** | 头文件给了字段名、或由多处用法统计一致地指向同一含义，但没有一行官方文字明说 | 当设计意图用；写代码时留好注释 |
| **【未解】** | 没有找到任何证据 | 不要当 0、不要当默认值、不要编 |

本文中「实测」= 本机上跑 §12 的命令直接量出来的数字。

### 0.2 权威来源

| 来源 | 位置 | 本文用它来确定 |
| --- | --- | --- |
| 发行数据文件 | `Modules\Native\*.txt` | 一切数值、记录数、字段在文件里的次序 |
| 模块系统导出器 | `_rea/modulesys\process_*.py` | 每个数字**是按什么公式写进文件的**（位宽、缩放、填充） |
| 模块系统头文件 | `_rea/modulesys\header_*.py` | 位标记（bit flag）的名字与取值、掩码、位偏移 |
| 模块系统数据声明 | `_rea/modulesys\module_*.py` | 每个字段**作者视角**的含义（注释里的 1) 2) 3)…） |
| 本仓工具 | `tools\mb_paths.py`、`mb_data.py`、`mb_module.py`、`mb_decompile.py`、`mb_stats.py` | 复现抽取；`mb_module.py` 还负责校验操作码表 |
| 已产出 JSON | `data\*.json` | 聚合统计（免去每次重新解析） |

`tools\` 下**没有** `culture_extract.py`/`map_extract.py` 之外的东西；`_rea/modulesys/` 在**工程根目录**下（`G:\godot_project\MountAndBladeWarband\_rea\modulesys\`），不在 `tools\` 里面。

### 0.3 最重要的一条前提：编译后的数据文件里**没有字段名**

`troops.txt`、`item_kinds1.txt`、`parties.txt`、`factions.txt`、`skills.txt` 这些文件里：

* **一个字段名都没有**。整份文件除了第一行的版本串（或不多的几个 id 串）之外，全是空格分隔的十进制整数/浮点数。
* **记录的身份 = 它在数组里的位置（下标）**。`trp_swadian_knight` 之所以叫这个名字，只是因为它是 `troops.txt` 里第 44 条记录（0 基）。文件本身不写这个名字。
* 少数文件里仍保留了文本 id（`trp_`、`itm_`、`fac_`、`pt_`、`p_`、`skl_`），但那些也是编译期由模块系统拼出来的，**不是引擎回读的字段**。
* 一旦进入脚本字节码，所有实体都变成「标签 + 下标」的整数（§1.2）。例如 `0x05<<56 | 44` 就是 `trp_swadian_knight`。

**推论（写代码必须记住）**：

1. 「下标 → 名称」的对照表必须和同一份数据文件**同版本**。改一个 id、插入一条记录，会让所有脚本对它的引用整体错位。
2. 没有任何办法从二进制本身恢复字段语义。字段语义只能来自 `process_*.py`（怎么写的）+ `header_*.py`（位定义）+ `module_*.py`（作者注释）。
3. 因此本文对每个文件都给出**三层**描述：物理行序 → 字段在行里的位置 → 字段的位语义。

## 1. 通用编码（所有编译文件共用）

### 1.1 文件骨架

除 `module.ini` 外，所有 `.txt` 数据文件都是同一种形状（由 `process_operations.make_export` 写出）：

```
<version 字符串>\r\n        ← 例：troopsfile version 2 / itemsfile version 3 / factionsfile version 1
<记录条数>\r\n              ← skills.txt 例外，只有这一行，没有 version 串
<记录 1>
<记录 2>
...
```

* 行分隔符是 `\r\n`；数字之间是**空格**，经常出现连续两个空格（因为 `" %d "` 这种格式串两端都带空格）——**解析时必须用「按空白切分」而不是「按单空格切分」**。
* 记录内部换行不规律：`troops.txt` 一条记录跨 6 行，`scripts.txt` 跨 2 行，`item_kinds1.txt` 跨 3–5 行，`map_icons.txt` 记录之间还夹空行。**只有 `process_*.py` 能告诉你一条记录到哪里结束**，不要按行猜。
* 文件末尾多一个换行，会切出一个空字符串，解析时要丢掉。

### 1.2 操作数编码（operand）

**【实证】**（`header_common.py` 的 `op_num_value_bits = 24 + 32`，`mb_decompile.py` 用同一结论）

```
operand = (tag << 56) | index          # tag == 0 → 这个 64 位数就是字面量本身
```

`tag` 取值（**【实证】** `header_common.py` / `mb_decompile.py` 的 `TAG_*`）：

| tag | 含义 | 脚本里的写法 | tag | 含义 | 脚本里的写法 |
| --- | --- | --- | --- | --- | --- |
| 0 | 字面量 | `123`、`-5` | 13 | 脚本 | `script_xxx` |
| 1 | 寄存器 | `reg0`…`reg63` | 14 | 粒子系统 | `psys_xxx` |
| 2 | 全局变量 | `$xxx` | 15 | 场景道具 | `spr_xxx` |
| 3 | 字符串寄存器 | `s0`…`s63` | 16 | 音效 | `snd_xxx` |
| 4 | 物品 | `itm_xxx` | 17 | **局部变量** | `:xxx` |
| 5 | 兵种 | `trp_xxx` | 18 | 地图图标 | `icon_xxx` |
| 6 | 阵营 | `fac_xxx` | 19 | 技能 | `skl_xxx` |
| 7 | 任务 | `qst_xxx` | 20 | 网格 | `mesh_xxx` |
| 8 | 队伍模板 | `pt_xxx` | 21 | 展示 | `prsnt_xxx` |
| 9 | 队伍 | `p_xxx` | 22 | 快速字符串 | `qstr_xxx` |
| 10 | 场景 | `scn_xxx` | 23 | 音乐轨 | `trk_xxx` |
| 11 | 任务模板 | `mst_xxx` | 24 | 画面板 | `tab_xxx` |
| 12 | 菜单 | `menu_xxx` | 25 | 动作 | `anim_xxx` |

注意 tag 表里 **没有 26 及以上**；高 8 位只用到 0–25。【推断】`tag<<56` 保证 tag 与 index 不重叠（index 最多 56 位）。

### 1.3 语句与操作码

脚本体内的一条语句在字节流里是：

```
<opcode> <参数个数> <参数 1> ... <参数 n>
```

* `opcode` 是**裸整数**，不带名字。名字只能查 §13 的表（1053 个真操作码）。
* `参数个数` 是**内联**写出来的。**这一点极其重要**：不要用操作码表里声明的参数个数去切分字节流，要用内联的那个数；表里的参数个数只用来做一致性检查。
* `opcode` 的高两位是修饰位（**【实证】** `header_operations.py` 里的 `CRF_NEG`/`CRF_THIS_OR_NEXT` 语义，`mb_module.py` 的常量）：

| 位 | 值 | 含义 |
| --- | --- | --- |
| `neg` | `0x80000000` | 条件取反 |
| `this_or_next` | `0x40000000` | 与下一条语句构成「或」 |
| `BASE_MASK` | `0x3FFFFFFF` | 取出真正的操作码号 |

* 一条语句最多 **16** 个参数（`process_operations.process_statement` 在超过时直接抛错），所以 `参数个数` 最大 16。
* 变参操作码是常态：610 个脚本里有 **60** 个操作码名字在不同调用点出现不同参数个数（最高的 `call_script` 有 1648 处）。**这是内联参数个数存在的理由**，不是数据损坏。

### 1.4 触发器（trigger）块

触发器块在多个文件里复用，格式一致（**【实证】** `process_operations.process_triggers`）：

```
<触发器条数>
<时机 1 的浮点秒数> <第 1 条触发器的语句块>
<时机 2 的浮点秒数> <第 2 条触发器的语句块>
...
```

* **触发器条数单独占一个"位置"**（前面若已有换行，它就单起一行；例如物品记录里它独占一行）。
* **每条触发器的语句块**与脚本体写法完全一样，只有一处差别：**块的 `<语句条数>` 前面先写触发时机**（浮点秒数）：

### 1.5 数值约定

* **整数**：全部是有符号十进制；负数直接写 `-5`。脚本里的 64 位操作数写成十进制大整数（例：`144115188075856755`）。
* **除法**：脚本中的整除一律是**向零截断**（【实证】`process_operations` 生成的运算语义 + 引擎行为一致）。算产值/价格时不要用向下取整。
* **浮点**：一律 `%f`（6 位小数），例：`17.000000`、`0.150000`。整数字段和浮点字段**不能混**——同一行里两者交错出现。
* **定点小数**：
  * 物品重量：文件里存 `weight × 4`（整数）——见 §4.3。反解 `0.25 × 存值`。
  * 队伍方向：存弧度，不是度（`process_parties` 写 `%f` 弧度；本 build 实测值如 `2.96706` = 170°）。**【推断】**（弧度由数值验证：31 次出现 `2.96706`，恰好 π×170/180）。
* **字符串里的 `%`**：技能描述在文件里写成 `%%`，读出来要还原成 `%`（`mb_data.py` 就是这么做的）。

* `#` 之后到行尾是注释，**先剥注释再切 `=`**。
* 只在**第一个** `=` 处切分；右边整体作为值（值里可以再有 `=`）。
* 键名与值都做首尾去空白。键名重复时，后出现的覆盖前面的——**这就是 `load_resource` 的坑**：
  214 次出现不同的值，用 `dict` 解析只会留下**最后一条**。要拿完整资源清单必须**按行读、不要用字典**。

### 2.3 值与"策划视角"的要点

* **日期与尺度**：`time_multiplier = 0.25`——游戏内 1 天对应真实 0.25 天（1:4 加速）。所有"每天"的脚本计算（工资、士气、价格漂移）都建立在这个数上。
* **地图边界 `map_min_x/max_x/min_y/max_y` 是 `-180/180/-145/145`**，而 `map.txt` 实测顶点范围是 x∈[−404.5, 409.6]、y∈[−396.9, 399.7]（§10）——**地图网格比 `module.ini` 声明的边界大**。`data/calradia_map.json` 的 `within_module_ini_bounds` 因此为 `false`。**【实证】**不要假设两者一致。
* **战斗伤害公式的三个系数是成对给的**：`armor_soak_factor_against_*` 与 `armor_reduction_factor_against_*` × 三种伤害类型（cut/pierce/blunt）。本 build 的取值（0.8/0.65/0.5 与 1.0/0.5/0.75）**只影响 soak 与 reduction 两条路径**，不是"护甲减伤百分比"本身。
* **`disable_food_slot = 1`**：本 build 关掉了"食物槽"机制。这解释了 §3 里 `ek_food`(9) 槽的实测分布（见 §3.5）与物品里 14 件 `itp_food` 共存的现象——**数据还在，机制被关**。
* **`dont_load_regular_troop_inventories = 1`**：普通兵种的初始装备不由 `troops.txt` 决定，而由脚本在运行时装配。这是 §3.1 里「1072 条记录里 32 条完全没装备」的合理解释。**【推断】**

* **`map_*_tree_types`**：4 个数（17/3/5/4）之和 = 29，是地图林木的分区数。**【推断】**
* **多人开关**：`compatible_multiplayer_version_no = 1170`、`multiplayer_walk_enabled = 0`、`damage_interrupt_attack_threshold_mp = 1.0`、`restrict_attacks_more_in_multiplayer = 0`——再次印证 §0.4。

### 2.4 `load_resource` 行

* 形式：`load_resource = <资源相对路径>`，**214 行**，全部集中在第 113–368 行。
* 语义：把 `模块目录\Resource\` 下的这个文件登记为「本模块要加载的资源」（贴图 / 网格 / 材质 / 着色器）。

### 3.7 第 5 行：技能（**192 位打包 + 稀疏**）

```
level(i) = (skill_words[i // 8] >> ((i % 8) * 4)) & 0xF
```

  `skl_trade=2, skl_leadership=1, skl_prisoner_management=1, skl_inventory_management=2, skl_riding=5, skl_shield=5, skl_power_strike=5, skl_ironflesh=5`——对一名骑士完全合理，nibble 序得到确认。

* 也就是说：**"技能 = 0" 是绝大多数技能在绝大多数兵种上的实际取值**。把 0 当成"未设置"是错的——它就是 0 级。

> **必须注意的位陷阱【实证】**：类型值 1–15 直接占 `flags` 的低 4 位，但 **16–20 只用得了第 4 位**：
> `itp_type_pistol = 0x10`、`musket = 0x11`、`bullets = 0x12`、`animal = 0x13`、`book = 0x14`。
> 所以用 `flags & 0xF` 判类型时：
> * `itm_book_tactics` 的 `flags = 20 = 0x14` → `&0xF = 4`，**会被误判成长杆**；
> * `itm_cartridges` 的 `flags = 16875538` → `&0xF = 2`，**会被误判成单手**；
> * `itm_flintlock_pistol` 的 `flags = 4259856` → `&0xF = 0`，**直接判不出来**。
>
> **正确做法：用 `flags & 0x1F`。**（实测三例：`0x14`=书、`0x12`=弹药、`0x10`=手枪 ✓）
> 取值 0 的 3 件是哨兵记录：`itm_items_end`(602)、`itm_ccoop_new_items_end`(619)，外加 `itm_no_item`(下标 0，`flags` 低 nibble 恰好是 2 的占位物)。
> **做任何"物品池"统计前先剔除下标 0 和两个 `*_end`。**

### 4.3 128 位统计字：**双布局**（本字典最核心的一条）

物品的 13 个数值字段全挤在**一个 128 位整数**里（文件里写成十进制大整数）。**【实证】** `header_items.py` 的位定义表：

```
ibf_armor_mask       = 0xff          ibf_head_armor_bits  = 0     (8 位)
ibf_damage_mask      = 0x3ff         ibf_body_armor_bits  = 8     (8 位)
ibf_weight_mask      = 0xffff        ibf_leg_armor_bits   = 16    (8 位)
ibf_hitpoints_mask   = 0xffff        ibf_weight_bits      = 24    (16 位)
                                     ibf_difficulty_bits  = 40    (8 位)
                                     ibf_hitpoints_bits   = 50    (16 位)

iwf_swing_damage_bits        = 60    iwf_damage_type_bits       = 8
iwf_swing_damage_type_bits   = 68    iwf_thrust_damage_bits     = 70
iwf_thrust_damage_type_bits  = 78    iwf_weapon_length_bits     = 80
iwf_speed_rating_bits        = 90    iwf_shoot_speed_bits       = 100
iwf_max_ammo_bits            = 110   iwf_abundance_bits         = 120
iwf_accuracy_bits            = 16    (注释原文：reuse leg_armor for accuracy)
```

位段总表（**把上面拼起来**）：

| 位 | 宽 | 字段 |
| --- | --- | --- |
| 0 | 8 | head_armor |
| 8 | 8 | body_armor |
| 16 | 8 | leg_armor **/ accuracy / food_quality** |
| 24 | 16 | weight（存值 = 重量 × 4） |
| 40 | 8 | difficulty |
| 50 | 16 | hit_points ← **和下面 60 位重叠** |
| 60 | 10 | swing_damage（低 8 位数值，高 2 位伤害类型） |
| 70 | 10 | thrust_damage（同上） |
| 80 | 10 | weapon_length **/ shield_width / horse_scale** |
| 90 | 8 | speed_rating **/ horse_maneuver** |
| 100 | 10 | missile_speed **/ shield_height / horse_speed** |
| 110 | 8 | max_ammo（**盾牌耐久**也用它） |
| 120 | 8 | abundance（0 视为 100） |
| 118–119 | 2 | 未用 |

**"双布局"是什么**：同一套位段，按物品类型被**换名字**使用。`header_items.py` 用**函数别名**把这件事写死了（**【实证】** 原文）：

```python
shield_width(x)    = weapon_length(x)      shield_height(x) = shoot_speed(x)
horse_speed(x)     = shoot_speed(x)        horse_maneuver(x) = spd_rtng(x)
horse_charge(x)    = thrust_damage(x, 0)   horse_scale(x)  = weapon_length(x)
food_quality(x)    = head_armor(x)         accuracy(x)     = leg_armor(x)
# 源码注释原文： iwf_max_ammo_bits = 110 # use this for shield endurance too?
```

**【实证】重叠的算术证明**：`hit_points` 占位 50–65，`swing_damage` 占位 60–69，两者在 **60–65 位重叠**。
实测 `itm_no_item` 的 swing = `528 = 0x210`：低 8 位 = `0x10 = 16`（数值 16），位 8–9 = `0b10 = 2`（blunt），整个 10 位字段落在位 60–69。
于是 `get_hit_points(y) = (y >> 50) & 0xFFFF` = `(528 & 0x3F) << 10` = **16384** —— 一件武器"有 16384 点耐久"，显然是伪值。
`itm_tutorial_battle_axe` 的 swing = `27` → hit_points = 1024+2048+8192+16384 = **27648**，同样成立。
**【实证】** 全表 `hit_points > 1000` 的物品有 **161 件**，全部是单手/双手/长杆（77/39/45），**没有一件盾或马**；
盾与马的 `hit_points` 实测范围是 **0–700**（正常耐久）。
**结论：`hit_points` 只对盾和坐骑有意义；对武器读它就是读到了斩击伤害的一半。**

**【实证】** 伤害字段的编码：`damage_type_bits = 8`、`cut=0 / pierce=1 / blunt=2`，
故类型判定阈值为 `blunt_min_val = 2<<8 = 512`、`pierce_min_val = 1<<8 = 256`（`get_damage_str` 原文）：
`>= 512` 是钝击（数值 = 值 − 512）、`>= 256` 是穿刺（数值 = 值 − 256）、否则是砍击（值不变）。
实测自带类型判定的分布：斩击 164 次里 98 砍/58 钝/8 刺；刺击 227 次里 170 刺/35 钝/22 砍——**同一件武器的斩与刺可以类型不同**。

### 9.2 校验：操作码表被证明是完整的

**【实证】** 校验方法（`tools/mb_module.py` 的 `validate()`）：

> 用操作码表把 610 个脚本全部解码一遍，要求**解出来的语句条数 == 编译器写在同行第 1 个 token 的条数**。
> 只要有一个操作码的参数个数错，字节流就会错位，条数就对不上。

本机实测结果：

```
opcode table entries : 1054
scripts parsed       : 610
operations decoded   : 36740
scripts w/ failure   : 0
opcodes missing name : 0 []
variadic names       : 60
RESULT: the opcode table reproduces every shipped script exactly
```

* **610 / 610 通过，0 失败；36740 条语句；没有一个操作码查不到名字。**
* **60 个操作码是变参的**（不同调用点参数个数不同），最多的：`call_script`(1648 处)、`display_message`(269)、`try_for_agents`(58)、`prop_instance_set_position`(36)、`set_visitor`(29)。
  **再次强调：解码必须用内联的参数个数，表里的参数个数只能用来发现"这是变参"。**
* 表里 1054 条里**有 1 条是解析假象**：`header_operations.py` 第 1355 行有一句 Python 局部变量 `indent = 0`，被正则当成了操作码。
  所以**真操作码是 1053 个**（§13 只列 1053 个），`code 0` 不是操作码。

### 9.3 命名约定

* `cf_*` = "condition function"：返回真/假的辅助脚本，**54 个**。
* `game_*` / `party_*` / `troop_*` / `npc_*` = 引擎回调或常用工具。

### 9.4 用它反查规则

`tools/mb_decompile.py` 能把字节码还原成可读伪代码，这是"规则靠证据而不是靠猜"的主要手段：


## 11. 槽位（slot）：**本 build 没有单人模式的槽位名**

这是整个数据层最容易被想当然的地方。

### 11.1 事实

**【实证】** 实测 `_rea/modulesys/module_constants.py`：

| 项 | 实测 |
| --- | --- |
| 文件里的赋值总数 | 497 |

| `slot_party_*` | **0 个** |
| `slot_centre_*` | **0 个** |
| `slot_troop_*` 的 12 个全是多人装备槽 | `slot_troop_equipment_one_hand_begin=0` … `slot_troop_equipment_horse_begin=9`、`slot_troop_ranking=50`、`slot_troop_spawn_health_percent=51` |

* 该文件里的 `slot_scene_*` / `slot_player_*` / `slot_agent_*` / `slot_item_*` / `slot_faction_*` / `slot_ship_*` / `slot_animal_*` / `slot_array_*` / `slot_mission_data_*` / `slot_team_*` 全部是**多人玩法域**（出生点、管理员权限、兵种选择、船只、畜群、聊天的颜色……）。

### 11.2 那单人数据里的槽位号是怎么来的？

脚本里出现的槽位号全部是**裸整数**。它们的含义只能从**用法**反推。
本仓 `docs\RULES.md` 第 7 节做的正是这件事（**原文标题：`7. Slot map assembled from usage (all names INFERRED)`**，
并声明"本 build 没有任何发行文件给这些槽位命名；下面的每一项都至少来自 34 个脚本里一次被解码出来的读/写；
数字和观察到的用法是证据，名字是暂定的"）。

### 11.3 给程序员的结论

1. **不要把 `slot` 当枚举用。** 没有枚举，只有整数。
2. 要确定某个槽位的含义，唯一方法是：`mb_decompile` 出用到它的脚本 → 看它被写什么、被读去做什么。
3. **不同对象（party / centre / troop / faction / item）的槽位号是各自独立的编号空间**——槽 8 在 troop 上是"俘获者"，在 party 上可能是别的。访问前先确定对象类型。
4. 单人数据的槽位名在**另一世代的模块系统**里可能存在，但**不在本机这份头文件集里**——所以本字典不给出"标准名"。

## 15 附录 C：module.ini 全键表（引擎侧实测）

本节不是从 `module.ini` 抄出来的，而是**从 `mb_warband.exe` 里读出来的**：解析器
`FUN_00573560`（体 `0x573560–0x57572f`）对每一个键执行

```
push <键字符串>; lea ecx,[esp+0x10]; call 0x453050   ; HasKey → 返回 bool 在 AL
test al,al; je <下一个键>
lea ecx,[esp+0x9c]; call 0x452f30                    ; std::string::c_str
push eax; call 0x626c10 (atoi) 或 0x626cdc (atof); add esp,4
fstp/mov dword ptr [<全局>], ...                     ; 写入存储地址
jmp 0x575714                                         ; 完成
```

所以「键 → 存储地址 → 解析类型」三列是同一条指令流上的直接观测，不含推断。生成脚本见
`G:\rea_tools\mkkeytable.py`（可复现：`python mkkeytable.py`）。

**怎么读这张表**

- **解析类型** 是该键被交给 `atoi`（int）还是 `atof`（float）。引擎因此把该键当作整数或浮点存放，
  与 `module.ini` 里写成 `1` 还是 `1.0` 无关。
- **读 / 写 / 读改写** 是在整个 `.text`（`0x401000`–`0x7bdb6d`，1,225,011 条指令）里对该存储地址的
  绝对寻址访问计数。`读 = 0 且 写 = 1` 表示这个键解析后**从未被引擎读过**，即引擎不消费该键——
  这是判断「某键到底有没有用」最直接的证据，比社区文档可靠。
- **⚠** 表示两个键指向了同一地址，必有一个是扫描窗口越界造成的误配（见下文「已知瑕疵」）。
- **Native 取值** 是 `Modules\Native\module.ini` 实际写入的字面量；标「未设置 → 全局为 0」的是
  **引擎认识、但 Native 没有声明**的键。这类键的全局量停留在零初始化状态——原因见下一节。

### 15.2 零初始化：为什么「未设置的键」等于 0

`.data` 节的文件几何是 **vsize `0x2555438`（约 39 MB）而 rawsize 只有 `0xdc00`（56,320 B）**。
即 `.data` 只有开头 56 KB 有文件字节，其余全部由加载器置零。上面 134 个存储地址中，
属于 `0x0a6f180`–`0x0a6f3xx` 这一段（约 130 个键）落在零填充区：

- 它们**在 PE 文件里不存在**，`mbdis.py` 对 `0xa6f180` 以上地址报「未映射 / 零填充」是正确行为，
  不是工具缺陷。
- 扫描整个 `.text` 找不到任何 `mov dword ptr [0x0a6f...], <立即数>`，也找不到独立的初始化函数。
  唯一写入者就是解析器本身。

**结论【实证】**：一个既没有被 `module.ini` 声明、也没有在别处赋值的键，其全局量就是 **0**。
引擎没有「内置默认值表」。

### 15.3 引擎如何补默认值：使用点钳位

既然全局量是 0，引擎就必须在**使用点**兜底，否则未设置的键会写出 0.0 这种破坏性数值。
已完整读出的一个实例是 `attribute_required_per_skill_level`（存储 `0xa6f350`，int，Native 未设置）：

```
0x58cb72  mov edi, dword ptr [0xa6f350]     ; edi = 该键
0x58cb7b  cmp edi, 1
0x58cb89  jg  0x58cb90
0x58cb8b  mov edi, 1                        ; ← ≤1（含未设置的 0）一律当 1 用
0x58cb9f  idiv edi
```

即**未设置 ⇒ 有效值 1**。这解释了为什么 Native 不声明这些键游戏仍然能跑：
每个耗用点自带钳位，而不是有一张默认值表。

**给 MOD 作者的直接后果**：`module.ini` 里漏写一个键，得到的是「0 + 该使用点的钳位」，
而不是上游引擎文档里写的那个值。要复现某一条数值规则，必须去读使用点的钳位，
不能假设默认值。53 个 Native 未声明的键逐一的「有效默认值」属于未解项，
见 `05-未解项清单.md` §2 A21。

### 15.5 由本表直接解决的两个问题

1. **`damage_interrupt_attack_threshold` 与 `_mp` 是两个不同的全局量。**
   三个拼写（单 s 的 `_treshold`、双 s 的 `_threshold`、`_mp`）中前两个共用
   共享处理器 `0x57564f`，在该处 `fstp dword ptr [0xa6f210]`；只有 `_mp` 写 `0xa6f214`
   （`0x573a97`）。两个地址的**全部**读取点各 3 个，且成对出现在同两个函数里：

   ```
   0x4c05c2  fld dword ptr [0xa6f210]      ; 0x4c05ca fld dword ptr [0xa6f214]
   0x4c1c90  fld dword ptr [0xa6f210]      ; 0x4c1c98 fld dword ptr [0xa6f214]
   ```

   相隔 8 字节——引擎把单机阈值与联机阈值**各存一份**并按模式选用。
   于是 Native 的 `damage_interrupt_attack_threshold = 3.0`（单机）与
   `_mp = 1.0`（联机）**都是有效值**，此前「两个写法谁生效」的疑问至此关闭。

2. **`no_friendly_fire_for_bots` 就是 `FUN_004ec100` 里那个 `DAT_00a6f28c`。**
   该键存储于 `0x0a6f28c`，与伤害入口中 `DAT_00a6f28c != 0 && *(int*)(agent+0x270) == 1`
   的判断完全吻合：开启该键时，命中同阵营目标（`+0x270 == 1`）直接跳过伤害结算。
   这同时解释了 §10 里那个「含义不明的全局量」。
