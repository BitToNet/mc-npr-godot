# 骑马与砍杀：战团 —— 数值 / 玩法 / 架构 逆向文档集

> 目标：通过**反编译**与**数据提取**，还原《Mount & Blade: Warband》Windows 单机版（Native 模块）的数值设计、玩法设计与整体架构，产出面向策划与程序的中文文档。
>
> 本册是整套文档的导读，定义**证据标准**、**方法**、**复现步骤**与**文档地图**。其余各册中出现的任何结论，其可信度都以本册定义的标签为准。

## 0. 一句话说明这套文档的性质

这套文档**不是**攻略，也**不是** wiki 的翻译。它的每一条数值与规则，都来自本机安装的这份游戏本体的**随文件发布的字节**：

- 编译后的脚本字节码 `scripts.txt`（游戏实际执行的算术）
- 编译后的数据表 `troops.txt` / `item_kinds1.txt` / `parties.txt` / `factions.txt` / `skills.txt` 等
- 可调参数文件 `module.ini`
- 可执行文件 `mb_warband.exe`（引擎内部、脚本层看不到的那部分实现）

凡是从 wiki、论坛或"记忆"得来的内容，本套文档**不予采信**；确实需要外部知识时，会显式标注为【推断】并说明依据。

## 1. 证据标准

### 1.1 三级标签

| 标签 | 含义 | 判定依据 |
|---|---|---|
| **【实证】** | 结论的每一步都可复核 | 脚本层：解码出的操作码序列（给出脚本名与 op 序号）。数据层：随文件发布的字节（给出文件名、行号或字节偏移）。引擎层：反编译出的函数体（给出函数入口地址）。 |
| **【推断】** | 算术/数据本身是实证的，但**名称、单位或语义**是推出来的 | 例如某个槽位号在随文件发布的字节里没有名字，只能从脚本用法反推其角色。文中会说明推理依据。 |
| **【未解】** | 用现有素材无法确定 | 明确写出"无法确定"，并说明**为什么**无法确定（例如：该值由引擎内部计算，模块数据中不存在）。**绝不猜测数值。** |

### 1.2 两条贯穿全文的纪律

**（一）整数运算是截断整除。**
模块系统的所有除法都丢弃余数。这不是细节——多处规则会**连续累积截断误差**（例如 `update_trade_good_prices` 用三次连续整除做归一化）。任何按浮点重算的结果都会与游戏实际不符。

**（二）数组下标就是身份。**
编译后的数据文件**不携带名字**，引擎按位置解析。因此 `troops.txt` / `item_kinds1.txt` / `parties.txt` 等表的**顺序不可重排**；任何"整理排序"都会破坏语义。同理，`scripts.txt` 中引用兵种、物品、部队时用的都是裸下标。

### 1.3 本套文档明确不做的事

- 不把【推断】写成【实证】。
- 不给【未解】项填一个"看起来合理"的数值。
- 不声称还原了原始 C++ 源码。反编译得到的是**行为等价的重建**，不是原始工程。

## 3. 方法

### 3.1 脚本层：从 `scripts.txt` 反解算术

`scripts.txt` 把每个脚本存成"操作数 + 内联参数"的线性序列：

```
<script_name> -1
 <op_count> (<opcode> <argc> <arg> ...) (<opcode> <argc> <arg> ...) ...
```

`op_count` 是一个**独立校验和**：只有把每个操作边界（包括参数个数内联的可变参数操作）都切对了，才能精确复现它。全文 610 个脚本全部复现成功、0 失败——这是"读对了"的硬证据。

操作数编码为 `tag << 56 | index`，本项目确认用到的 tag 见下表。**这套 tag 语义本身是【实证】的**，因为它能一致地解释全部 36,740 条操作。

| tag | 含义 | 渲染为 |
|---|---|---|
| 0 | 整数字面量 | `100` |
| 1 | 寄存器 | `reg0` |
| 2 | 全局变量 | `$g_enemy_party` |
| 3 | 字符串 id | `str_happy` |
| 4 | 物品 | `itm_spice` |
| 5 | 兵种 | `trp_npc1` |
| 6 | 阵营 | `fac_player_faction` |
| 7 | 任务 | `qst_lend_surgeon` |
| 8 | 部队模板 | `pt_...` |
| 9 | 部队 | `p_main_party` |
| 10 | 场景 | `scn_...` |
| 13 | 脚本 | `script:calculate_main_party_shares` |
| 17 | **局部变量**（全模块出现最多） | `:0`、`:1` … |
| 19 | 技能 | `skl_tactics` |

### 3.2 数据层：从编译后的表提取记录

编译表是"头部行 + 逐记录行"的文本格式。`tools/mb_data.py` 按头部定义逐字段解析，并把结果显示名规范化（例如剥离 `{!}` 内部标记前缀）。提取结果落在 `data/*.json`，并带有一致性自检。

### 3.3 引擎层：反编译 `mb_warband.exe`

**为什么必须做这一步。** 脚本层只能看到"剧本"，看不到引擎。举一个具体例子：脚本 `game_get_upgrade_xp` 会调用 `get_level_boundary`，但 `get_level_boundary` 本身**不在 `scripts.txt` 里**——它是引擎内置函数。于是"升级所需经验曲线"这条最核心的数值，靠模块数据**永远拿不到**。类似地，伤害算法、行军速度、物品概率重置等，都只存在于引擎里。

**这一步的成果（2026-10 本轮）。** 上文举的两个"拿不到"的例子都已拿到：

| 曾经拿不到 | 现在 |
|---|---|
| 升级经验曲线 | 编译期常量表，`.rdata` `0x0080ecb4`，int32 × 63（等级 0–62）→ [01 §4.8](01-数值设计.md) |
| 伤害代数 | `FUN_004b3050`（`0x4b3050–0x4b36a5`），完整代数逐指令读出 → [01 §6.7.1](01-数值设计.md) |

**做法。** 用 REA 驱动 Ghidra 12.1.4 对 `mb_warband.exe` 做完整自动分析，再对目标函数逐个反编译取伪代码与汇编，并通过字符串引用（`module.ini` 的键名必须以字面串存在，是极好的锚点）定位引擎内部实现。

> **本轮新增的、更可靠的一条路径**：对**字节**直接分析，不经过 Ghidra。仓库内自带一个 4 KB 的 PE 解析器 + Capstone 反汇编封装（`mbdis.py`），配合一个全 `.text` 线性扫描器（`xscan.py`，1,225,011 条指令，约 40 秒）。读常量、读指令字节、统计某个全局量的全部读写点，都在 1 秒内完成，而 Ghidra 每次冷启动要 250–270 秒。**本轮的伤害代数与键表都是这样读出来的**。
>
> 这条路径还有一个 Ghidra 给不了的能力：**看编码字节**。x87 的 `D8 C8+i` 与 `DC C8+i` 反汇编文本相同但语义相反，只有读字节才能消歧（本轮曾因此写错一次，见 [05 §7](05-未解项清单.md)）。

**一个必须先说清的坏消息。** 游戏主体代码**已被剥离符号**：10,618 个函数中只有 353 个带名字，且这 353 个全部是 C 运行库（CRT）与异常处理函数（`Catch@`、`Fid_conflict:*` 等），**没有一个游戏逻辑函数带名字**。因此引擎侧的一切都必须靠"字符串锚点 → 交叉引用 → 所在函数"来定位，不存在按名字查函数的捷径。这使得引擎层的还原成本显著高于脚本层。

## 4. 如何复现

### 4.1 脚本与数据层（不需要 Ghidra）

```powershell
cd G:\godot_project\MountAndBladeWarband

# 校验操作码表能精确复现全部 610 个脚本（应输出 0 失败）
python tools\mb_module.py validate

# 反编译单个脚本为带语法糖的伪代码
python tools\mb_decompile.py game_get_troop_wage --sugar

# 重新提取全部数据表
python tools\mb_data.py

# 打印配平分布统计
python tools\mb_stats.py
```

### 4.2 引擎层（需要 Ghidra + JDK 21）

本项目使用 Ghidra 12.1.4 与 JDK 21.0.12.1，位置：

```
G:\rea_tools\ghidra     # Ghidra 12.1.4 发布目录
G:\rea_tools\jdk21      # JDK 21.0.12.1
```

REA 通过两个环境变量定位它们（**没有默认目录探测**，必须显式设置）：

```powershell
$env:GHIDRA_INSTALL_DIR = 'G:\rea_tools\ghidra'
$env:JAVA_HOME          = 'G:\rea_tools\jdk21'
```

首次分析约 200 秒，结果写入快照；后续调用复用快照。可直接使用本项目提供的封装脚本：

```powershell
. G:\rea_tools\rea.ps1
Rea analyze                       # 概览
ReaSearch -Pattern "armor_soak"   # 检索字符串/函数
ReaFunction -Procedure 0x00401234 # 取单函数完整档案（伪代码+汇编+引用+字符串）
```

> **注意（実测）**：REA 的 MCP 服务在进程启动时快照环境变量，之后无法更改；若 MCP 服务在安装 Ghidra **之前**就已启动，它会一直报 `GHIDRA_INSTALL_DIR is not set`。此时必须改用命令行 CLI（每次调用会重新导入目标，单次约 290 秒），或者从**全新打开的终端**重新启动宿主程序，使其继承到新设置的环境变量。

## 7. 已知的整体性限制

1. **符号被剥离**：引擎函数无名字，定位依赖字符串锚点，覆盖不可能是完备的。
2. **剧本与引擎的边界不总是清晰**：同一规则有时部分在脚本、部分在引擎（例如升级 XP 由脚本算，但等级曲线来自引擎）。
3. **运行时播种的数据不在模块文件里**：中心点归属、驻军、领主部队、志愿兵池等都是运行时生成的。`parties.txt` 里 240 个部队没有一个领主部队，180 个中心点全部是 `fac_neutral`。**这类数据无法从模块数据恢复**，必须在文档中如实标注。
4. **随文件发布的模块常量头文件是"多人/拿破仑世代"的**：它包含 `base_export_percentage`、`max_food_amount` 之类，却**不含任何单人模式的槽位名**。这是本套文档中"槽位"相关结论普遍只能标【推断】的根本原因。
5. **本套文档描述的是这一份具体构建**。换版本、换模块（如各种 MOD），数值与脚本都会变，唯独引擎机制大体不变。
6. **`.data` 的绝大部分在文件里不存在**：`.data` 虚拟大小约 39 MB，而文件字节只有 56,320 B。**所有 `module.ini` 设置全局量都落在零填充区**，所以「引擎内置默认值」不能从镜像里读，只能逐个去读使用点的钳位。

## 8. 本次修订（2026-10）：三处旧结论被推翻

本套文档是"活"的：本轮通过对 `mb_warband.exe` 的字节级分析，**推翻了自身三处旧结论**，并补齐了两条此前标注为【未解】的核心数值。逐条记录在 [05-未解项清单 §7](05-未解项清单.md)，此处列出影响面最大的三条：

| 旧结论 | 更正后 | 影响 |
|---|---|---|
| 护甲伤害代数"从随包数据不可知"，本套文档不给公式 | **已完全解出**：`absorbed = soak + (1-e^(-0.014·A·redF·k))·max(0, roll-soak)`，`roll = D·(0.9+0.1·u2)`，`soak = A·soakF·(0.45+0.55·u1)`，`k = 0.45+0.55·u3`，最终 `clamp(roll − round_half_down(absorbed), 0, 500)` × 后置倍率 → [01 §6.7.1](01-数值设计.md) | **全部战斗数值现在可算** |
| `level_boundary_multiplier` 是"引擎默认值表里的一项"，Native 未设置所以曲线不可知 | **不存在默认值表**：全局量在零填充区，未设置就是 0；引擎在各使用点钳位。曲线本体是编译期常量表 `0x0080ecb4`（int32 × 63，等级 0–62）→ [01 §4.8](01-数值设计.md) | **升级节奏现在可算**；且"漏写一个 `module.ini` 键会得到什么"的答案变了 |
| `damage_interrupt_attack_threshold` 的单 `s` / 双 `s` / `_mp` 是"同一项设置的三种拼写" | 单 `s` 与双 `s` 是别名（同写 `0xa6f210`）；**`_mp` 是另一项设置**（写 `0xa6f214`）。引擎把单机阈值与联机阈值各存一份，按模式选用 | Native 的 `3.0` 与 `1.0` **都生效，各管自己的模式** |

**方法论上的教训（一并记录）**：前两条错在**只看反汇编文本、不看编码字节**——x87 的 `D8 C8+i`（`FMUL ST(0),ST(i)`）与 `DC C8+i`（`FMUL ST(i),ST(0)`）字节不同，但 Capstone 对两者都打印 `fmul st(i)`。第三条错在**把"跳转到同一代码分支"当成"写入同一变量"**。两条都已写入 [05 §7](05-未解项清单.md)，作为本套文档后续复核的检查项。
