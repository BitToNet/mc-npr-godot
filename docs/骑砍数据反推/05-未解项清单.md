## 1. 为什么会有未解项

所有未解项都落在下列四种根因之一。**根因决定了突破路径**，因此本册按根因分表，而不是按主题分表。

| 根因 | 含义 | 突破路径 |
|---|---|---|
| **R1 · 在引擎里，且符号已剥离** | 逻辑存在于 `mb_warband.exe`，但函数无名字，需靠字符串锚点逐层定位 | 反编译（见 §3 的方法学）；成本高但可行 |
| **R2 · 在模块里，但不在这批被反编译的脚本内** | 调用方或被调方位于尚未处理的脚本/触发器中 | 扩大反编译范围即可解决 |
| **R3 · 数据未声明** | 发行数据里就没有这个信息（字段全 0、名字缺失、语义未定义） | 通常**无法**从发行文件解决，只能运行时探测或设计决策 |
| **R4 · 工具链缺口** | 本项目的解析工具或随包头文件缺件，导致信息读不出 | 补工具/补文件即可解决 |

> **重要**：R1 与 R2 原则上可解，只是成本问题；**R3 与 R4 中的一部分永远无法从发行文件解决**。重建时必须对 R3 做显式设计决策，而不是假装它等于某个"显然"的值。

### 2.1 A1 已解决：护甲伤害代数的终局结论【实证】

A1 已经**关闭**，不再是不确定项。完整推导见 [01 §6.7.1](01-数值设计.md)，此处只留可核对的最小事实集。

**定位链**

1. 结算函数 = `FUN_004b3050`，体 `0x4b3050–0x4b36a5`，1,622 字节，58 基本块，`RET 0x4`。
   **全程序只有两个调用点**：`0x4bb2c8`（`FUN_004bb290` 内）与 `0x4ec1ba`（`FUN_004ec100` 内）。
2. 系数读取点（**每个键恰好 1 个读点**，这是「代数已完整捕获」的强证据）：

   | 键 | 存储地址 | 唯一读点 | Native 值 |
   |---|---|---|---|
   | `armor_soak_factor_against_cut` | `0x00a6f218` | `0x4b3377` | 0.8 |
   | `armor_soak_factor_against_pierce` | `0x00a6f21c` | `0x4b3398` | 0.65 |
   | `armor_soak_factor_against_blunt` | `0x00a6f220` | `0x4b33b9` | 0.5 |
   | `armor_reduction_factor_against_cut` | `0x00a6f224` | 同区 | 1.0 |
   | `…_pierce` / `…_blunt` | `0x00a6f228` / `0x00a6f22c` | 同区 | 0.5 / 0.75 |
   | `extra_penetration_factor_soak` / `…_reduction` | `0x00a6f314` / `0x00a6f318` | 同区 | 1.0 / 1.0 |
   | `crush_through_treshold` | `0x00a6f31c` | 同区 | 2.4 |

   > **更正**：本册早期版本把 `0x00a6f21c` 标成 `armor_soak_factor_against_blunt`，**是错的**。
   > `0x00a6f21c` 是 **pierce**；blunt 在 `0x00a6f220`。

3. 随机化、舍入、钳位全部在同一个函数体内，已读完。

**核心代数（结论，不含近似）**

```
roll     = D * (0.9 + 0.1*u2)                       # [0.90,1.00)*D
soak     = A * soakF * (0.45 + 0.55*u1)             # [0.45,1.00)*A*soakF   ← 第一步：直接扣减
pen      = 1 - exp(-0.014 * A * redF * (0.45 + 0.55*u3))   # 第二步：百分比减免
absorbed = soak + pen * max(0, roll - soak)
N        = round_half_down(absorbed)                # 恰好 0.5 不进位
最终伤害  = clamp(roll - N, 0, 500) * 后置倍率
被吸收量  = N
u1,u2,u3 = ((LCG>>16 & 0x7fff) % 15817) / 15817.0   # LCG: s*0x343fd+0x269ec3 @ 0x0085f3a0
```

`A` 是按命中部位区取的整数护甲值（`this + 0x854 + r*4`，单机三区 / 联机一区），
`soakF`/`redF` 按伤害类型（0=cut/1=pierce/2=blunt）取上表。
`+0x44`（最终伤害）与 `+0x48`（被吸收量）**严格互补**，两者之和恒等于 `roll`。

**自洽性与三条独立佐证**

- `pen < 1` ⇒ `absorbed <= roll` ⇒ 只有 `roll < soak`（被完全吸收）时 `+0x44` 才会算出负数——
  **这正是 `[0,500]` 钳位存在的理由**，与 `module.ini` 第 66–68 行自述的「前三个直接扣减、后三个百分比减免」逐字吻合。
- `A = 0` ⇒ 伤害 `= D*(0.9+0.1*u2)`，即裸体吃满 ±10%。
- `0.45` 下限保证 soak 最多吸收 45%，重甲不可能 100% 免疫。

**A1 关闭后仍留的残余**（已拆为 A21、A22、A23）

- `this` 指向的那个 >0x6008 字节单例对象的**名字**没有符号可依（它带 `+0x28` 模式、
  `+0x854/858/85c` 三区护甲值、`+0x5ea0` 受击记录标志）。它**不是** agent 结构（agent 步长 `0xc38`）。
- 单机「背向/高度」加成项 `A += FUN_004a13d0(ecx) + 10` 里，`FUN_004a13d0` 返回的是什么装备分量、
  以及 `agent+0xc10 * 0.01` 这个阈值代表什么，未定。
- `FUN_004a13d0` 的逐槽位增量表（−4…+6，字节表 `0x4a145c`）语义未定。

## 8. 重建时的处理原则

1. **R1/R2 类（A、B 表）**：可以继续通过反编译收敛。在收敛前，**不要把占位值写进正式实现**，或至少把它隔离在一个显式命名的常量里并注明来源。
2. **R3 类（C 表）**：**必须做设计决策**，并在代码里标注这是决策而非还原。例如"据点驻军从哪来"——原版是运行时播种，重建必须自己定规则。
3. **R4 类（D 表）**：补件优先。`header_item_modifiers.py` 若能取得，`imodbits_*` 立即可解。
4. **绝不做的事**：给【未解】项填一个"看起来合理"的数值然后当作实证。本套文档全部五册均遵守此纪律，合计标注【未解】约 99 处，**没有一处被补全**。
