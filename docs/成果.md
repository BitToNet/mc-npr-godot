### 4. 过程中发现并修掉的缺陷

| # | 缺陷 | 根因 | 处理 |
|---|---|---|---|
| 1 | 验收运行器退出码被覆盖（用法错误返回 1 而非 2，且子进程会莫名多跑一次截图批次） | `verify.gd` 与 `capture.gd` 都读 `OS.get_cmdline_user_args()`，且 `capture.gd` 把 `--case=` / `--out=` 当作**触发条件**；Capture 是 autoload，其 `get_tree().quit(1)` 覆盖了运行器先前的 `quit(2)` | `capture.gd` 触发条件收紧为**仅** `--shots` / `--shot=` / `--capture` / `--bench`；`--case=` / `--out=` / `--frames=` / `--warmup=` 降为纯修饰符。已登记 §3.4 与 §16 |
| 2 | `ROADMAP` 原风险描述「`SceneTree` 脚本无法访问 autoload」不准确 | 实测：autoload **节点**确实挂在 root 上（`get_root().get_node("Style")` 可用），真正的问题是 `--script` 模式下 autoload **标识符编译期不可解析**（`Identifier not found: Style`） | 已按实测改写 §5 S0.2 风险条目；`verify.gd` 文件头写明该硬约束 |
| 3 | `quit()` 之后仍会被调用一次 `_process`，导致 `--list` / 用法错误被当成一次真实运行 | Godot 主循环在 `_initialize` 中 `quit()` 后仍进入一次迭代 | 增加 `_halt` 早退标记 |

### 5. 重要发现：`B-` 视觉门禁阈值不可达（→ Q13）

实测**同参数、同构建、同 seed**的三次独立窗口渲染，两两差异为
**1.62% / 5.67% / 5.05%**（像素比，通道阈值 8/255）——比原定门禁 `< 0.1%` 高一到两个数量级。

原因已定位（架构性的，不是参数没调好）：

- `shaders/toon.gdshader:49` 植被风摆用内建 `TIME`；
- `shaders/water.gdshader:33/51/60` 水波与泡沫用内建 `TIME`；
- `scripts/clouds.gd:81` 云的高度漂移直接读 `Time.get_ticks_msec()`（连 `time_scale` 都无法冻结）。

⇒ `--frames=N` 只能对齐帧数，无法对齐动画相位；**当前工程在字节层面不存在可复现帧**。

这是 S0.1 的**阻塞项**：不改判据，S0.1 的 `B-` 项会恒失败。三个候选方案（见 `ROADMAP §14 Q13`）：
(a) 以「同构建噪声底」做相对门禁；(b) 增加 `--static` 截图模式屏蔽水/云/植被后要求逐位一致；
(c) 立项把动画时钟改为可注入（`TIME` → `u_time` uniform）。

**本次未擅自修改阈值**（`§0.5` 变更控制），仅在 ROADMAP 中登记 + 加注「裁定前不得判通过」。

### 3. 过程中发现并修正的三个坑（均已写进代码注释与用例）

1. **`RenderingServer.global_shader_parameter_get_list()` 是编辑器专用 API**，运行期调用会报
   `This function should never be used outside the editor`。最初用它做"参数是否注册"的检测，
   结果是每次窗口运行都刷 ERROR 日志、且判定恒假。改用
   `ProjectSettings.has_setting("shader_globals/render_time")`；"值是否真的进了着色器"改由
   **帧数反向对照**实质验证，不靠渲染服务读回。
2. **除着色器与云外还有两处隐性不可复现源**：`player.gd` 竖直跟随的收敛程度取决于**物理步数**
   （随真实帧率浮动），以及 `main.gd` 的 **HUD FPS 读数**（HUD 在取景范围内）。前者在确定性模式下
   直接落到静止高度并清零 `_squash`，后者固定报 `Clock.hz`；交互模式两者的原行为都保留。
3. **漏写 `--` 分隔符会让整个验收套件静默挂死**：`OS.get_cmdline_user_args()` 只认 `--` 之后的参数，
   少了它 `capture.gd` 收不到 `--shots` 便不 `quit()`，而 `OS.execute` 没有超时——实测挂死 10 分钟。
   新增 `_exec_user()` 强制插入 `--` 并以 `--quit-after` 兜底，此类问题退化为"清单没写出"的显式失败。

### 6 顺手修掉的既有缺陷：注入点击缺鼠标移动

`_click_control()` / `_click_path()` 只注入 press/release，**没有 `InputEventMouseMotion`**。
Godot 的 `Viewport` 用 `gui.mouse_focus` 决定把按键投给谁，而该焦点**由鼠标移动更新**；
没有移动，按键就落在失效焦点上。

| 项 | 内容 |
|---|---|
| 症状 | 失败点每次不同：有时"读取没跳宫格"、有时"另存为没进宫格"、有时两轮截图 sha256 不一致 |
| 先证明是既有的 | `git show HEAD:tools/verify.gd` 导成临时脚本跑同一用例 —— **同样红**（5 跑 2 红），才确认不是本步引入 |
| 修法 | 点击前先发一个落在目标中心的 motion 事件；**不动产品码**，只让注入序列符合真实输入（真人点击前一定先移动鼠标） |
| 结果 | `s0_3_slots` 连跑 **18 次全绿**；`--all` 连跑 **2 轮全绿** |
| 附带 | `_shoot_menu_case()` 失败时打印子进程末尾 20 行——原来只知道"少了一次自证"，不知道少在哪一步 |

1. **"偶发失败"要先证明它是既有的**，做法是把 HEAD 的版本导出来跑同样的用例。

### 2 为什么这么实现

`--scene=` 看着像"调一下 `change_scene_to_file()`"，但这个工程里两条捷径都不通：

1. **不能调 `change_scene_to_*()`**。`scene_change_owner` 守卫只放行 `SceneRouter`（ROADMAP §3.2），
   而这条规则的用处就是"切场景只有一个入口"。把 `capture` 加进属主清单，等于为了让工具过关而
   在规则上开口子 —— 所以走 `SceneTree` 公开成员手动换，且**不动** `current_route`（那是路由器的事实）。
   `s1_0_scene_arg` 反向断言属主清单仍只有 1 条、`capture.gd` 不在其中。
2. **不能改 `run/main_scene` 让引擎开机就加载它**。实测无效：引擎在 autoload 的 `_ready()` 之前
   就把主场景路径取走了，改设置只影响下一次开机。这条路最阴的地方不是"不起作用"，而是
   **自证会空洞通过** —— 如果只断言"当前场景 == `--scene=` 要求"，那么当要求恰好是默认场景时，
   什么都没发生也会绿。所以自证改成四条：新实例接管 `current_scene` / 新实例路径等于要求 /
   旧场景真的被释放 / 相机组最多 1 台；并加了"换成 `battle_stub` 哈希必须变"的反向对照。

### 2 为什么这么实现

**① `Canon` 是静态类，不是 autoload。** 全局服务预算 9 / 10，余量要留给 M1–M6 的真服务；
`Canon` 无状态、无 `_ready`、无时钟，做成 `class_name` 静态类既够用又不占额度。

**② 数字规则改成"整数值写整数"，不是为了好看。** 实测 `JSON.parse("12")` → `12.0`、`-0` → `0.0`：
只要经过一次解析，纯 `%.6f` 就把整数永久写成浮点形态，"表文件 == 规范化(表文件)"这条**文件级**

### 2 为什么这么实现

**① 高度返回世界米，另给一个显式的归一化函数。** 战略地形要直接顶点定位、聚落要判"是否在水下"、
镜头要算包围盒 —— 这些都吃米。归一化只留给配色 ramp 这类消费方，且必须是**另一个函数名**：
"我拿到的是米还是比例"不能靠猜。

**② 高度场里一个随机都不放。** 噪声种子全部由 `world_seed` 派生，偏移写死；采样顺序不可能影响结果。
于是"同 seed 逐位相同"可以用整张 75×75×3 采样表的 `==` 来断言，而不是抽样近似。
随机只出现在 **region 中心**，因此 `WorldRegions` 显式收一个 `RandomNumberGenerator` ——
游戏侧传 `Rng.stream("world_gen")`，`verify.gd` 在 `--script` 模式下从 `root.get_node("Rng")` 取。
**不读 autoload、不裸 `randf()`**，同一 seed 的重放才不会取决于"之前谁抽过随机"。

**③ 频率用"跨地图周期数"而不是"每米频率"。** 前者让 `map_size` 变成缩放器（地形形状不变、尺度变），
后者会让改地图尺寸时"山里能放几座山"跟着变。这个差别要到 S1.2 接上渲染才看得出来，所以现在定死。

**④ Voronoi 而不是矩形网格分区。** 矩形网格会让"面积分布"退化成算术恒等式；Voronoi 的每块面积
真的跟着噪声地形走，`A-` 的"region 面积分布"才有内容。每个陆地格恰属一个 region、水格 `owner = -1`，
于是"面积和 = 陆地格数 × 32²"可以独立算出来对账，不需要额外记账。

**⑤ 浮点字段单列，是因为整数闸门会悄悄抹平地形。** 批 1 的 `validate()` 对所有字段
`int(roundf(v))`；`hill_amplitude = 120.4` 会被取整成 `120` 并附一条告警 —— 而**地形已经按 120 算了**。
告警在 `warnings` 里，截图看不出来，只会让"表里写的数"与"实际地形"永久对不上。见 §5 陷阱 24。

**⑥ 不动 `terrain.gd`。** 它是 6 机位 `B-` 基线的承载者，也是 S0.3 `spawn_point` / `height_at` 断言的
输入。`HeightField` 借鉴它的手法（掩码 + 岛屿幂 + 噪声叠加 + 山脊），但尺度、参数、返回语义全部另立
（63 米演示岛 ↔ 2400 米战略图）。改它的签名或常量会同时改动 6 张基线图。

### 2 为什么这么实现

**① 先钉锚点，再撒随机。** 锚点是"这块地必须在这儿"的手工事实（村庄在东坡、要塞在北岬）。
反过来做的话，随机点会先占掉锚点周围的最小间距，就只能"删随机点给锚点腾位" —— 于是同 seed 的世界
会依赖锚点表的**长度**，表一改整张图全变。现在锚点排在最前，`settlements[0..2]` 永远是它们。

**② 落点是四条闸门 + 有上限的重试，不是"重试到成功"。** 离边界 80 m、不落水、坡度 ≤ 0.35、
与已放聚落 ≥ 120 m；每点最多试 200 次。放不下就**告警 + 按实际数量降级**（`ok` 仍 true），
绝不死循环。默认地形上 `slope ≤ 0.35` 的陆地只占 38.7%（中位坡度 0.42），所以"能放几个"真会随
地形变 —— 两个阈值因此进参数表，不当常量。

**③ 道路是图，不是网格。** 每条路只记 `{a, b, length}`。这个批次里铺路面网格等于提前决定
S1.2 的形状（避水寻路、桥、隧道都在那边），而相机一换就得推翻。连通性用并查集保证，
测试则用**另写一遍的 BFS** 去查 —— 拿被测实现验证被测实现，只能证明它和自己一致。

**④ 首都用最远点采样，不抽随机。** 换 seed 时城镇自己会动，首都若再抽一次随机，"同 seed 可复现"
就多了一个需要额外记账的随机点。最远点采样是纯几何的：先取离地图中心最远的城镇，之后每次取离
已选集合最远的。副作用正是想要的 —— 三个首都尽量分散。

**⑤ 锚点坏掉只跳过，绝不"挪到附近合法处"。** 锚点的全部价值是"它在那儿"。落水就告警跳过，

而不是"差不多在附近"。地形参数一改导致锚点落水，用例会立刻红：这是特性，不是误报。

### 4 五个坑

**① 单数 / 复数两套命名，配额静默变 0。** `KINDS` 用单数（`village` 是聚落自己的 `kind`），
参数表的键是复数（`villages` 是计数）。第一版直接 `params.get(kind, 0)`：三个配额全取到 0 ⇒
三条锚点各报"超出配额：跳过"、随机点一个不放、`settlements` 为空、`build()` 返回 `ok = false`。
**没有崩溃、没有报错**，只有三条措辞像"参数表配错了"的告警。`Dictionary.get(k, 0)` 缺键不告警，
是它能静默的直接原因。修法：显式 `KIND_PARAM` 映射，且用"配额全部放出来"这条断言当回归锁。

**② 反向对照写错了方向：删一条边不断开。** 最近邻骨架（每点连 2 个最近邻）本身带环，

### 4 坑

**① 同一个 seed 生成了两个不同的世界 —— 子流的入口状态没钉住。** 单跑 `--case=s1_1_gen` 是 24 条边 /
7936.7 m，`--all` 里同一个 seed 变成 26 条边 / 8916.9 m。原因不是随机不稳定，而是用例**共享**同一条
`Rng.stream("world_gen")`：前面用例多抽了几个数，后面用例的"世界"就完全不同了。`WorldData` 只承诺
"从传入的 stream 当前状态开始重放"，从不承诺"同一个 `world_seed` 永远同一个世界"。修法是把入口钉死：
夹具先 `Rng.reset()`（把每条子流拨回 `(master_seed, 名字)` 派生的起点）再建世界 —— 两种跑法随即逐字节
一致，且与批 3 记录的 24 条边 / 7936.7 m 完全吻合。**这条对 S1.2 是硬前置**：组合根必须先 `Rng.reset()`
或 `seed_from(world_seed)`，否则"同一个存档种子重建同一个世界"会随玩家这一局先抽了多少随机数而漂移。

**② `snappedf(v, 3)` 是把 `v` 吸到 3 的整数倍，不是"保留 3 位小数"。** 用它格式化陆地占比（0.629），
打印出来是 `0.0`，而断言照样是绿的 —— 差点把"数值爆炸"当成"显示问题"漏过去。米制/比例量一律用
`snappedf(v, 0.001)` 这类**步长**写法。

**③ 每条边只存 6 位小数，累加会攒出 ~1e-5 的差。** 拿"文本里的 `length` 之和"跟"内存里的总长"比，
浮点末位必然不等；容差要给到 1 cm，不能按 `1e-6` 卡。

**④ `Canon.to_text()` 返回 `{ok, text}`，不是 `String`。** `WorldData.to_text()` 第一版写成 `-> String`
直接编译失败（`Cannot return value of type "Dictionary"`）。这是**契约型返回值**在起作用：想忽略错误
就必须显式忽略 `ok`。顺手也踩到它的兄弟问题 —— 读回后整数变浮点（`20` → `20.0`），拿 `str()` 比对
"内存 metrics 与文本 metrics 一致"必假；改成比两者各自的 **Canon 规范文本**才成立。

**⑤ 引擎会悄悄重写 `project.godot`。** 注释整段消失、`[shader_globals]` 挪到文件尾，`git status` 变脏。
处置：不提交它，`git checkout -- project.godot` 复原；跑完引擎先看一眼 `git status --short`。
（`ENGINEERING.md` §5 陷阱 27。）

### 2 为什么这么实现

**① 入口必须是"一个函数"，不能是一条约定。** `HeightField` / `WorldRegions` / `WorldData` 都是被动的：
它们从传入的生成器的**当前状态**接着抽数，谁先抽、抽了几个，它们一概不知道。所以"同一个 seed 同一个
世界"在它们的契约里根本不成立 —— 只在"调用方先拨回起点"时成立。批 4 量到的 26 条边 vs 24 条边就是
这句话的反证。把顺序、重置、参数装载、告警汇总全收进 `boot()`，后来加多少场景都不会各建各的。

**② `Rng` 用参数注入，不取 autoload。** 两个理由都很硬：`tools/verify.gd` 是 `--script` MainLoop，
autoload 标识符在那里不可编译；更实际的是，**能注入才测得动** —— 用例要拿真身去对比"污染子流前后的
世界"，如果 `boot()` 自己去 `get_node("/root/Rng")`，这条反向对照就写不出来。

**③ 失败分三级，不是一个 `bool`。** `ok` 说世界有没有建出来，`errors` 说为什么没有（参数表坏了 /
拿不到子流 / region 一个都没落下），`warnings` 说"建出来了但缺了什么"（锚点表坏了、配额没放满）。
锚点表故意降级成告警：手工地标是"更好看"，不是"能不能开局"；参数表坏了才是致命的 —— 没有地图尺寸
就没有世界。

**④ 场景按路径取 autoload，`_ready()` 只 boot 一次。** 路径取法让同一个场景在 `--script` 模式下也能
实例化（用例就是这么验接线的）；只 boot 一次是因为本批还没有"重建世界"的需求 —— 有需求时 `boot()`
本身就可以重入（先丢旧 session 再建），不必让场景自己管缓存。

**⑤ 顺手改了 S1.0 的两条断言，不是"删掉挡路的断言"。** 它们原本说"根节点无脚本"，挡的是"提前造一个
什么都不做的 `strategic_map.gd`"—— 现在脚本真的做事了，判据就换成"脚本在 `_ready()` 里启动、且真的
接上 `WorldSession.boot()`、不含 TODO / 占位字样"。挡的东西没变，只是认得出"真入口"了。

### 4 坑

**① 母种子是会话级可变输入，不是常量。** 写用例时顺序是 `boot(20250929)` → `boot(20250930)` →
调既有夹具 `_world_fixture()` 想证明"入口与夹具是同一个世界"，结果 `region_areas` 全不一样。问题不在
世界，而在**母种子已被上一步换成 20250930**：夹具用 `reset()` 按当前母种子派生，对照文本却来自
20250929。教训：`Rng.master_seed` 谁都能改，跨阶段比对前把母种子显式拨回要对照的值。（§5 陷阱 28）

**② `reset()` 只拨回"已存在"的子流。** 它的语义是"回到 `seed_from()` 之后再按同样顺序 `stream()`
一次的状态"，不是"清空重来"。所以 `seed_from()` 与 `reset()` 不能混着当同义词用 —— 前者清表，后者
保表。夹具里写的是前者还是后者，决定了它对照的是"开局"还是"当前局"。

**③ 夹具的注释会过期，而过期的注释比没注释更坏。** `_world_fixture()` 的注释还写着"子流种子在这里
显式钉住（`stream.seed = p_seed`）"，实际批 4 早已改成 `Rng.reset()`。本批一并改正 —— 否则下一个人
会照着注释去钉 `seed`，又造出一个"只在单跑时成立"的夹具。

**④ 工具坑（与产品无关）**：用 PowerShell 数组拼接插入多行 GDScript 时，嵌套数组会被 `-join` 压成
一行，报 `Parse Error ... found "var" instead`。改用 `List[string]` 逐行 `Add()` 才稳。

## S1.4b 变速与暂停（2026-10-21）

S1.4 批 2。玩家终于能"等一等"和"快一点"：顶部常驻四个按钮 + 一个日期读数。核心不是 UI，而是**一条判据** ——
"4 倍速跑完的一天"必须和"1 倍速跑完的一天"逐字段相同，否则倍速就是在偷偷改游戏规则。

### 1 做了什么

| 项 | 内容 |
|---|---|
| 变速 | `speed ∈ {1, 2, 4}` 只放大 `_tick_residual` 的**流入**（`delta × 60 × speed`），tick 本身恒为 1 游戏秒 ⇒ `game_time` 保持整数、4x 只是把 1x 的循环多跑几遍；非法档（0 / 3 / -1 / 5）被拒且**当前档不变**（`set_speed()` 返回 `false`） |
| 步长 | `TICK_REAL_SECONDS = TICK_GAME_SECONDS / GAME_SECONDS_PER_REAL_SECOND = 1/60`，是全仓"一步多长"的唯一来源 |
| 暂停 | `get_tree().paused`，不是"0x 档"：只停时钟的话队伍会在 HUD 后面继续走。`GameState` 用默认进程模式自动停摆，`Clock` / 时间条 / 菜单 / Toast 在 `PROCESS_MODE_ALWAYS` 照常 ⇒ 渲染时钟、相机拖拽缩放、UI 都没被冻住 |
| 模拟入口 | 新信号 `GameState.simulation_tick(step, seconds)`，每 tick 一条；`strategic_map` 用它驱动 `party.step(seconds)`，**删掉** `_process(delta)` 那条老路。步长随信号下发，业务代码不再自己写 1/60 |
| 时间条 | `scripts/ui/time_bar.gd`（新，无 `class_name`）：顶部居中，`暂停 / 1x / 2x / 4x` + `第 Y 年 M 月 D 日 HH:MM ×N`。当前档黄底、其余纸色；暂停后按钮变「继续」并转粉。`layer 10` / `PROCESS_MODE_ALWAYS` / `#hud` 组。读数只取 `date_text()`，自己不存第二份状态 |
| 取证 | `capture.gd` 新增 `--game-time=`（默认 `43200` = 第 1 天 12:00）并在取样前 `pin_time()`；`strategic_shots.gd` 新增 `--hud=1`、默认隐藏；`perf_map.gd` 采样前隐藏 `#hud` |
| 用例 | 新增 `s1_4_speed`（**43 断言**）与 `s1_4_hud`（**28 断言**）；`s0_3_router` 结构指纹 6 → 7 子节点并加一条能力断言 |

### 2 怎么验的

| 判据 | 结果 |
|---|---|
| `A-` 倍速等价性 | 4x 跑 4 帧 vs 1x 跑 16 帧（喂进余量累加器的和相同）⇒ `game_time` 相同、`time_parts()` 逐字段相同、**除 `playtime` 外的存档快照逐字段相同**；同时 4x 的 `playtime` 更小（同一段模拟用了更少现实时间） |
| `A-` 每 tick 一步 | 8 次 `_advance_one_tick()` ⇒ 恰好 8 条 `simulation_tick`，`step` 逐次 +1，`seconds` 恒 `1/60` |
| `A-` 暂停 | 暂停 8 个物理帧 `game_time` 一动不动，而 `Clock.t` 仍在前进；继续后 `game_time` 重新前进 |
| 档位合法性 | `SPEED_TIERS == [1,2,4]`；0 / 3 / -1 / 5 / 8 全部被拒且档位仍是 1x（拒绝不等于半改） |
| 取证可复现 | `pin_time(43200)` 后物理帧照跑而 `game_time` 不动；`pin_time(-1)` = 就地钉住；`pin_time(INF)` 被拒（与存档同一套 `is_valid_time`） |
| HUD 接线 | 时间条进 `#hud` 组、`PROCESS_MODE_ALWAYS`、层 10；读数 = `date_text()`；**真点** 2x / 4x / 1x 会让 `GameState.speed` 跟着变；**真点**暂停会让整棵树暂停并变「继续」 |
| 回归 | headless **40 用例 / 0 失败 / 7 跳过 / 42.5 s**；窗口 **40 / 0 / 0 / 157.2 s**；`B-` 图 `.shots/s14b/s14b_hud.png`（1600×900，678 130 B，`30e4e693…`，第 1 天 12:00） |
| 没碰坏旧图 | S1.3d 四张 `B-` 相册逐字节不变（`strategic_shots` 默认隐藏时间条）；`s1_2_perf` 三角面仍是 **18 032**（隐藏 `#hud` 后只数 3D） |

### 3 三个坑

1. **HUD 一上屏，截图就不再可复现**：时间条渲染 `game_time`，而 `game_time` 随物理帧推进 —— 两次同参数运行
   会差在"窗口打开时跑了几个物理帧"。所以 `--game-time=` + `pin_time()` 是**这一批的必需品**，不是锦上添花。
2. **字体光栅的面数不能进三角面断言**：时间条一出现，`perf_map` 量到的全球档从 18 032 变成 18 340，多出的 308
   是字形三角。数字随平台字体变化 ⇒ 采样前隐藏 `#hud`，让那条断言继续只数 3D。
3. **`--script` 下 autoload 标识符不参与编译**：时间条要读 `GameState.SPEED_TIERS`，却不能在源码里写这个名字
   （`verify.gd` 实例化它时会编译失败）。改成运行时从属主脚本的**常量表**里读，档位清单仍然只有一个来源。

### 4 明确没做

- 没有 v1→v2 存档迁移（S1.4c）：`SNAPSHOT_FIELDS` 仍 10 项 —— **档位与暂停是瞬时 UI 状态，不入档**

- 没有 365 日长跑与 04:00 / 12:00 / 21:00 三张 `B-` 板（S1.4d）。
- 没有动 `Clock` / `render_clock.gd` / `data/**` / autoload（仍 **9 / 10**）/ 三档镜头 / 地形。

## S1.4c 存档 v1→v2 迁移（2026-10-21）

S1.4 批 3。这一步没有新画面、没有新玩法，只有一个问题：**上一批改了时间的单位，老存档里的那个数怎么办？**

答案不能是"顺手兼容一下"。v1 的 `170` 在新语义下是"第 1 天 00:02:50" —— 读得出来，但日期全错。
这是最坏的一类错误：安静地错。

### 1 做了什么

| 项 | 内容 |
|---|---|
| schema 版本 | `SaveSystem.SCHEMA_VERSION = 1 → 2`。`SNAPSHOT_FIELDS` 仍 **10 项**：`day_length` 换成 `visual_day_length`（**同一个数**，纯改名）；`DEFAULT_DAY_LENGTH` → `DEFAULT_VISUAL_DAY_LENGTH`，注释明说"数据字段、无读者" |
| 时间换算 | `t_v2 = round(fposmod(t_v1, 170) / 170 × 86400)`。先按 v1 的周期折叠（`170`/`340` → `00:00`，不跳天），再等比拉到游戏秒 ⇒ `42.5 → 06:00`、`85 → 12:00`、`21.25 → 03:00`、`1.0 → 00:08`。比计划原文（只取整小时）多保了**分钟**，这是对齐时定的 |
| 钩子 | `migrations[1] = _migrate_v1_to_v2`，本项目**第一个真迁移钩子**。**惰性注册**（`load_slot()` 里 `_ensure_migrations()`，不用 `_ready()`：`s0_3_no_autosave` 有"启动零动作"的既有断言）。钩子不会写 warning，需要提示就把句子放进保留键 `_notice`，由 `load_slot()` 取出 → 转 warning → **删键** |
| 拒读边界 | **数字但不可能**（负 / `NaN` / `±INF`）⇒ **整档拒读**、`GameState` 一字不改（校验放在 `restore()` 之前，一个字段都还没应用）；**不是数字**（`"早晨"`）⇒ 仍走字段级告警；**缺字段** ⇒ 告警 + 保留当前值。界线是"值不可能"和"字段脏了"，后者是老契约 |
| 一次性提示 | `load_slot()` 返回值新增 `migrated_from`（0 = 没迁移）。菜单在它 > 0 时说一句「槽位 2 是 v1 存档，已迁移到 v2：时间已按新历法重标定（现在 第 1 天 06:00）」。**不塞进 `warnings`**（迁移不等于档脏），也**不做持久"已提示"标记**（不做状态位就没有第二份真相） |
| 用例 | 新增 `s1_4_migrate`（**66 断言 / 111 ms**），全程走**真文件 + 真 `load_slot()` + 真 `menu_page`** |
| 既有固件 | `s0_3_state` / `s0_3_roundtrip` / `s0_3_dirty` / `s0_3_slots` 九张卡 / `_slot_text_is_complete` / `_world_facts` 全部跟到 v2（卡片的正文仍取 `meta` ⇒ **像素不变**） |

### 2 怎么验的

| 判据 | 结果 |
|---|---|
| `A-` v1 存档迁移 | 手写 v1 文件（`game_time: 42.5`、`day_length: 170.0`）→ 迁移后 `game_time == 21600`、`clock_text() == "第 1 天 06:00"`、`date_text() == "第 1 年 1 月 1 日 06:00"`、`visual_day_length == 170.0`、快照里**已无** `day_length` |
| `A-` 小时落在 `[0,23]` | 6 个相位点逐个断言：`0` / `170` / `340` → `00:00`，`21.25` → `03:00`，`85` → `12:00`，`1.0` → `00:08`（`22:58` 这类边界由 `round` 到整秒自然满足） |
| `A-` 非法值被拒读而不是崩溃 | v2 负值、v1 负相位两个真文件都被拒且原因点名 `game_time`；拒读后 `money` / `game_time` 一字不改；校验器另做 7 条正反例（`INF` / `-INF` / `NAN` / 负 / `0` / 字符串 / 缺字段） |
| `A-` 一次性提示 | 真 `new()` 一个 `menu_page`：读 v1 后 `hint_text()` 里同时有「迁移」「重标定」「06:00」；读 v2 后**不再**出现「迁移」 |
| 钩子真的接上了 | 断言写在第一次 `load_slot()` **之后**（第一版写在之前，红了一次 —— 注册是惰性的），并另断言 `migrations.has(1)` |
| 不重复迁移 | v2 文件读到 `migrated_from == 0`、`game_time` 原样应用（没被当相位再缩放一遍） |
| 不伪造 game 段 | v1 缺 `game` 段时仍报原来的「缺少 game 段」，钩子不替它造一个 |
| 回归 | headless **41 用例 / 0 失败 / 7 跳过 / 42.9 s**；窗口 **41 / 0 / 0 / 158.1 s**；0 `ERROR` 行 |

### 3 四个坑

1. **"启动零动作"是有断言的**：第一版把 `_ensure_migrations()` 挂在 `_ready()`，`s0_3_no_autosave` 立刻红
   —— 那条用例明确断言「SaveSystem 没有 `_ready`」。就算注册只碰内存，也不该为了省一次懒判断去破它。
   改成 `load_slot()` 里惰性补齐，`migrations.has(1)` 的断言挪到第一次读档之后。
2. **"数字非法"与"字段类型错"必须分开**：一开始校验器连 `"早晨"` 也拒，`s0_3_dirty` 的
   「类型错误字段不拒绝整个存档」当场失效。最后划的线是：**值不可能**（负数/`NaN`/`±INF`）才整档拒，
   类型错仍走老告警通道。

### 4 明确没做

- 没做"迁移失败写一份备份"：迁移是纯内存操作，写盘只发生在保存时；多一份副本就是多一份真相。
- 没在 v2 里同时留 `day_length`：两个名字就是两处真相，钩子已经把旧名合成新名。
- 没做"靠内容猜版本"：`schema_version` 缺失按当前版本读是既有契约（`s0_3_dirty` 断言着）。
- 没有 365 日长跑与 `B-` 三张时分 + 时间条入画后的基线重定（S1.4d）。

### 5 关联

`ROADMAP` §6 S1.4（S1.4c 记录）、§15（S1.4 → 🟨 批 1–3 ✅）、§16（v2.17）；`docs/ENGINEERING.md` §9.18；
提交 `821aa9e`（feat(core) 迁移）、`b88b8dc`（test(tools) 用例）、`2f294ff` / `346a4bb`（docs）；本行由紧随的回填提交补。

### 3 四个坑

1. **`_process` 根本不存在，而且错误会被吞掉**：时钟在 `GameState._physics_process()` 里，第一版 `call("_process", 60.0)`
   只拿到一条 `Nonexistent function`；`--script` 下的步骤级运行时错误会**静默结束协程**（陷阱 37），用例照样打印
   `PASS (15ms)`。教训不是"记住函数名"，而是：**31.5M 次 tick 只用 15 ms 跑完，本身就是红灯** —— 时间尺寸要跟数字互相校验。
2. **取样时机不等于契约**：`SceneTree.process_frame` 在节点的 `_process` **之前**发信号，窗口模式的帧排布又比 headless 松
   ⇒ "等两帧再比较相位"在窗口全量里偶发失败（单跑该用例却过）。改成**有界帧内收敛**（最多 12 帧，判据仍是
   "相位 == 时钟相位"），测的是联动而不是调度顺序。
3. **暂停会穿过用例**：菜单是 `paused` 的唯一来源，而有的窗口用例只把 UI 藏起来、不解除暂停 ⇒ 后面所有用例都在
   **冻结的树**里跑。headless 跳过那些用例，所以只在窗口全量里现形；上一批没被发现，是因为老断言不依赖 `_process`。
   修法不是给 camera 打补丁，而是 `_run_one()` 开头统一 `paused = false` —— 每个用例都从"树在跑"开始。
4. **性能探针量到了不该量的东西**：`strategic_map` 打开 `auto_cycle` 之后，`perf_map` 的采样里每秒夹进一次换相位，
   而它**只让"空天空"那档掉得更多**（本来最快、最敏感）⇒ 反向对照 1.4 倍、判据 1.5 倍，飘红。探针量的是稳态场景，
   采样前 `pin_time(43200)` 把时钟钉住，与 S1.2d 的历史数字回到同一条尺子。
